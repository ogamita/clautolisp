#+TITLE: clautolisp cadgui — specification (the Qt6 GUI CAD host on embedded ECL)
#+AUTHOR: clautolisp
#+STARTUP: overview

cadgui is the fourth clautolisp HOST: the GRAPHICAL UI-tree host, the Qt6 peer of
cadtui on the cador core, invoked as =clautolisp --host cadgui=. Tracking issue:
=issues/open/cadgui-2-qt6-gui-host.issue= (epic: =cadgui-release-3.0-epic.issue=).

This document grows per implemented slice.

* Architecture

The cadgui shell is the host PROCESS: a thin Qt6 Widgets C++ app that boots
EMBEDDED ECL (=cl_boot=), loads the =clautolisp/cadgui= system (which pulls
cador), and renders the cador model. The split:
- *Common Lisp owns the model and regen* and produces a DISPLAY LIST.
- *C++ owns the window and the per-frame paint*, plus pan/zoom and input capture.
- The boundary is the cadgui protocol (below), crossed only on REGEN and on
  INPUT events, never per frame.

*Threading.* Qt's event loop and all QWidget work run on the process MAIN
thread. The cador runtime is multi-threaded (2 threads per document lisp image +
2 for the application, cooperative scheduler with park-by-threads), so under the
cadgui host the APPLICATION LISP runs on a NEW thread, not the main thread (Qt
owns main). The main thread is the GUI driver: a document runner that parks on
getpoint/entsel is RESUMED across threads by the Qt main thread once it has the
mouse point; model changes post a regen to the main thread, which repaints a
thread-safe display-list snapshot. The CURRENT shell is the DEGENERATE
single-document / no-scheduler case: lisp and Qt share the main thread with a
nested QEventLoop inside getpoint (no scheduler => synchronous read), which is
correct for one document. See cadgui-2-qt6-gui-host.issue "Threading
architecture" for the multi-document target.

* The display list (slice B — cador scene view)

=clautolisp.cador:cador-scene-display-list= (host) returns the drawable view of
the current model space, the render peer of =host-ssget "X"=: a list of

: (:POLYLINE HANDLE LAYER ACI CLOSED (X0 Y0 X1 Y1 ...))

in world coordinates, in creation order (back to front). HANDLE is the entity's
creation-order handle (string, for pick/highlight), LAYER the layer name, ACI
the colour index (256 = BYLAYER, 0 = BYBLOCK), CLOSED whether the polyline
closes, and the last element a flat double-float coordinate list. LINE/ARC/
LWPOLYLINE/POINT use the exact outline; CIRCLE is sampled to a closed polyline;
TEXT/MTEXT/INSERT/... fall back to a bounding-box rectangle placeholder.
=cador-scene-extents= returns =(XMIN YMIN XMAX YMAX)= for zoom-extents.

* The protocol (slices C/D/E/F — package clautolisp.cadgui)

The narrow surface the shell calls:
- =(cadgui-start)= — create a session on a fresh cador document; =cadgui-session=
  holds the host. One session per shell process (multi-document later).
- =(cadgui-display-list)= / =(cadgui-extents)= — pull the scene to paint (regen).
- =(cadgui-add-line X1 Y1 X2 Y2 &key layer color)= / =(cadgui-add-circle CX CY R
  &key layer color)= — populate the model through the real cador HAL
  (=host-entmake=).
- =(cadgui-eval-command STRING)= (slice E) — evaluate an AutoLISP string against
  the drawing through the real engine (=run-autolisp-string= + the core builtins,
  with the session host bound), so a LISP =C:= command or =(command ...)= /
  =(entmake ...)= runs and DRAWS; returns the new scene entity count (regen
  signal). Any =getpoint=/=entsel= it performs reads the canvas (slice D).

* Interactive input (slice D — input.lisp)

cador's =host-getpoint=/=entsel=/=ssget= all read a line through the single
chokepoint =read-prompt-line=, from =(cador-prompt-stream host)= -- the seam
=--mock-input= uses. =cadgui-start= binds that stream to a =cadgui-input-stream=
(a gray input stream) whose empty-buffer read BLOCKS via =*cadgui-input-hook*=:
the shell sets the hook to its C nested-Qt-event-loop await (run the loop until a
mouse click, format it as the point line "x,y", return it); a test sets it to a
scripted provider. So bare =(getpoint)= / =(entsel)= drive from the canvas --
both await a world point, which cador turns into the point (getpoint) or the
entity picked there via =%pick-entity= (entsel). =*cadgui-pending-input*= is
=:point= while a read blocks, for the shell's crosshair/pick mode.

* The canvas (slice C — cadgui-shell.cpp)

The Qt6 app pulls the display list + extents and paints polylines in ACI colours
over axes through a pan/zoom =View= transform (Y flipped so world-up is
screen-up). It runs in three modes:
- LIVE (default): a real interactive window -- left-click drives getpoint/entsel
  (device->world, with a crosshair while picking), the wheel zooms
  cursor-anchored, middle-drag pans, =e= zoom-extents, and a command-line widget
  at the bottom evals AutoLISP (=cadgui-eval-command=) then repaints.
  =QApplication::exec()=.
- =--render FILE=: render the current scene offscreen to FILE and exit (CI /
  screenshots).
- =--demo FILE=: offscreen, drive SYNTHETIC mouse events through the REAL
  handlers (device->world->getpoint) + a command eval, then save FILE -- the
  headless validation of the live input path.
Build: =clautolisp/cadgui/shell/build.sh= (pkg-config Qt6Widgets + ecl-config);
run headless: =run.sh= (=--demo=); live: =cadgui-shell= with no args on a display.

* Status (per slice)

- A (module + host launch): the =clautolisp/cadgui= CL module + the C++ shell
  that boots embedded ECL and loads it. DONE (shell renders offscreen).
- B (scene exporter): =cador-scene-display-list= / =-extents=. DONE + tested
  (cador suite).
- C (canvas): DONE. A LIVE interactive window -- pan/zoom (cursor-anchored
  wheel, middle-drag), zoom-extents (e), a crosshair while picking, real
  left-click -> getpoint/entsel (device->world), and a command-line widget that
  evals AutoLISP and repaints. Plus --render / --demo (offscreen) modes. The
  live path is validated headless via --demo (synthetic clicks through the real
  handlers).
- D (input bridge): DONE + tested. =cadgui-input-stream= backs cador's
  prompt-stream; getpoint/entsel drive from scripted/real canvas clicks through
  =read-prompt-line=. Shell wires the nested-event-loop await.
- E (command + regen): DONE + tested. =cadgui-eval-command= runs AutoLISP against
  the drawing (entmake / (command ...) draw); the shell repaints by re-pulling
  the display list. A LIVE command-line widget + regen-on-dbmod (vs re-pull):
  NEXT.
- F (the C boundary): the display-list + input + command surface above, exercised
