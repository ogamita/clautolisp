* Scope
This manual documents the ~clautolisp~ standalone executable: how to
invoke it, what options it accepts, and what it does in each mode.

It does *not* document the AutoLISP / Visual LISP language. For the
language reference — surface syntax, builtins, semantics, and
host-product divergences — see the companion ~autolisp-spec~
subproject (sibling directory ~../../autolisp-spec/~).

This document must be kept in sync with the implementation. Whenever
~clautolisp/tools/clautolisp/source/main.lisp~ changes its option
parsing, banner, exit codes, or supported modes, this file must be
updated in the same commit.

The rendered PDF (~user-manual.pdf~, sibling of this file) is also
checked in. Whenever this Org file changes, run ~make user-manual~
(or ~make documentation~) to regenerate the PDF and stage both files
in the same commit.

* Synopsis
#+BEGIN_EXAMPLE
clautolisp [options] FILE.lsp
clautolisp [options] -x EXPRESSION
clautolisp [options]                 (interactive REPL)
#+END_EXAMPLE
#+TEXINFO_FILENAME: clautolisp-user-manual.info
#+TEXINFO_DIR_CATEGORY: clautolisp
#+TEXINFO_DIR_TITLE: clautolisp: (clautolisp-user-manual).
#+TEXINFO_DIR_DESC: Clautolisp standalone interpreter user manual.

The implementation is shipped as two image-built executables, one per
supported Common Lisp host:

- ~clautolisp-sbcl~ — built on SBCL via ~make build-clautolisp-sbcl~.
- ~clautolisp-ccl~  — built on CCL  via ~make build-clautolisp-ccl~.

Both binaries are produced under
~clautolisp/tools/clautolisp/bin/~ and accept the same command-line
surface. The rest of this manual treats them interchangeably and
refers to the binary as ~clautolisp~.

* Modes of Operation
~clautolisp~ has three mutually exclusive modes; the mode is
determined by the operands. In every mode the runtime installs the
core builtin function bindings before evaluation begins.

** File mode
A non-option argument is treated as a path to an AutoLISP source
file. The reader loads the file under the active dialect, the
evaluator processes every form sequentially, and the binary exits
once the file has been fully consumed.

#+BEGIN_EXAMPLE
clautolisp drawing-tools.lsp
clautolisp --bricscad path/to/script.lsp
#+END_EXAMPLE

** Expression mode
The ~-x EXPRESSION~ option evaluates the supplied string as if it
were the entire source of a file, then exits.

#+BEGIN_EXAMPLE
clautolisp -x "(setq x 7) (+ x 3)"
clautolisp --bricscad -x "(princ (atof \"0x1p4\"))"
#+END_EXAMPLE

The expression is read with the source name ~<-x>~, which appears in
diagnostic messages.

** Interactive REPL
With no ~FILE~ and no ~-x~, ~clautolisp~ drops into an interactive
read-eval-print loop on standard input.

- Primary prompt: ~_$ ~
- Continuation prompt (printed when an expression is incomplete): three spaces.
- Each balanced top-level form is evaluated and the result is printed
  using the AutoLISP value formatter (the same formatter used by
  ~prin1~).
- A reader or runtime error is reported as a one-line diagnostic; the
  REPL then re-prompts.
- Closing standard input (Ctrl-D on a fresh line) ends the REPL.

The REPL accepts multi-line input: as long as the parser reports
~:unexpected-eof~, the REPL keeps reading continuation lines and
appends them to the in-progress form before retrying.

An empty line just re-prompts.

*** REPL commands

A line whose first non-blank character is a comma is a /REPL command/,
not an expression (at a top-level read the comma is unambiguous —
AutoLISP has no backquote). Each command has a short key and a word
form:

| ~,d~ / ~,date~   | print the current date and time (ISO 8601)     |
| ~,u~ / ~,uptime~ | print how long this clautolisp process has run |
| ~,h~ / ~,help~   | list the REPL commands                         |
| ~,q~ / ~,quit~   | exit the REPL (useful when ~(quit)~ is not     |
|                  | available in the active dialect)               |

The commands live in a command dictionary of the REPL's /interactor/ —
the same mechanism behind the debugger's command dictionaries — so the
vocabulary can grow (and user commands can shadow it) uniformly across
all the interaction loops.

*** Recording the session: the dribble

The REPL can record its interactions — input lines, standard output,
error output, and condition reports — into an append-mode log file,
the /dribble/.

Activation:
- ~--dribble~ :: start recording into
  =${XDG_STATE_HOME:-~/.local/state}/clautolisp/dribbles/YYYYMMDDTHHMMSS.log=
  (the timestamp is the start of the dribble, ISO-8601 basic format;
  directories are created as needed).
- ~--dribble=FILE~ :: start recording into FILE (appended to when it
  exists). Both forms take effect after the banner, before the first
  prompt.
- ~(clal-dribble [path [interactors]])~ :: at runtime. Without
  arguments it toggles: on (default file) when off, off when on. With
  a ~path~ it closes any active dribble and starts one appending to
  ~path~. Returns the absolute path of the file just opened, or ~nil~
  when it just stopped. A bare ~(dribble)~ is *not* predefined — if
  you want it, alias it in your =~/.autolisp= init file:
  ~(defun dribble (/ ) (clal-dribble))~.

Interactor filtering: by default only the ~AUTOLISP~ (~LISP~) REPL
is recorded. Functions that stack another interactor —
~(clal-break)~ → the ~ALDO~ debugger, ~(clal-sedit …)~, the
inspector, navi — pause the recording for their interaction (their
call and result are still recorded), and popping back to the REPL
resumes it. To record more, set the interactor list:
- ~--dribble-interactors=IS~ :: ~IS~ is ~t~ (record every
  interactor) or a comma-separated list of interactor
  names/aliases, e.g. ~AUTOLISP,ALDO~. Also sets the AutoLISP
  variable ~*clal-dribble-interactors*~.
- ~*clal-dribble-interactors*~ :: ~nil~ (default: ~AUTOLISP~ only),
  a list of names/aliases, or ~T~ for all. Consulted when a dribble
  *starts* and captured for its duration — changing it while a
  dribble is active does not change the active set; stop and
  restart to apply. The optional second argument of ~clal-dribble~
  supersedes it.

File format: a header line, then interaction blocks — the input
line raw, each output line prefixed by its source (~O~ standard
output, ~E~ error output), and condition reports on ~;; C:~ lines
(possibly redundant with the error report that follows; that is
intended). Prompts are not recorded.

#+begin_example
$ clautolisp --dribble-interactors=t --dribble=trace.sexp
clautolisp 1.5.11 — REPL (STRICT dialect, mock-host host) — Ctrl-D to exit.
_$ (+ 1 2 3)
6
_$ (/ 0)
clautolisp: runtime error: DIVISION-BY-ZERO: Division by zero in /.
AutoLISP backtrace (most recent call first, 2 frames):
  in SUBR /: (0)
  in EVAL: (/ 0)
_$ (clal-dribble)
nil
_$ (- 1 2 3)
-4
#+end_example

produces a dribble file =trace.sexp=:

#+begin_example
;; H: clautolisp 1.5.11
(+ 1 2 3)
;; O: 6
(/ 0)
;; C: DIVISION-BY-ZERO: Division by zero in /.
;; E: clautolisp: runtime error: DIVISION-BY-ZERO: Division by zero in /.
;; E: AutoLISP backtrace (most recent call first, 2 frames):
;; E:   in SUBR /: (0)
;; E:   in EVAL: (/ 0)
(clal-dribble)
#+end_example

Nothing after the ~(clal-dribble)~ line: the toggle closed the file
before its own result was printed.

* Debugger

Clautolisp ships an interactive source-level debugger, *aldo*. It steps
through AutoLISP code, sets breakpoints on forms, inspects the call
stack and live values, and evaluates expressions in the context of a
stopped frame. The full command vocabulary is in the companion
/aldb Command Reference/ (=clautolisp-debugger-command-reference.org=);
this section is an orientation and a guide to the three user interfaces.

** Entering the debugger

Clautolisp is *always debugging*: the aldo thread is ready for the
lifetime of the process, so there is no "run" or "start" step. Control
reaches the debugger in one of three ways:

- *interrupt* — pressing =C-c= breaks into aldo at the current poll
  point; a second =C-c= while the first is being handled exits the
  process immediately, skipping the debugger. The behaviour is the
  ~--on-interrupt debug|ignore|quit~ policy (default =debug=), mirrored
  by the AutoLISP variable ~*CLAL-ON-INTERRUPT*~ which is re-read *live*
  at each interrupt — ~(setq *CLAL-ON-INTERRUPT* 'IGNORE)~ makes =C-c=
  a no-op from then on. With no debug session active, =debug= degrades
  to =quit= (exit status 130).
- *programmatic* — the AutoLISP forms ~(clal-break)~ and
  ~(clal-invoke-debugger [message])~ drop into aldo from your own code
  (the analogues of Common Lisp ~break~ / ~invoke-debugger~).
- *on error* — an uncaught AutoLISP error enters the debugger when the
  error policy asks for it. The policy is the ~--on-error
  quit|debug|ignore~ option (and the ~*clal-on-error*~ variable your
  code may rebind).
- *on quit* — with ~--on-quit debug~ (default =quit=), a ~(quit)~ /
  ~(exit)~ call enters the debugger *before* the stack unwinds:
  =continue= resumes the quit, =quit=/abort cancels it and returns to
  the toplevel REPL. Mirrored by ~*CLAL-ON-QUIT*~, also re-read live at
  each call; the QUIT event cannot be ignored.

Only *instrumented* functions can be stepped into or stopped in;
instrument exactly what you want to debug (uninstrumented code runs at
full speed and is stepped over).

** The three user interfaces

aldo presents *one* command set through three interchangeable
interfaces; a feature available in one is available in all.

- *TUI* — the line-mode terminal interface. You type a short command
  token (or an AutoLISP form) and press =RET=. It needs nothing beyond a
  plain terminal, styles its output with ANSI colour where the terminal
  allows, and pages long output (see /Settings/ below). It is the
  fallback that always works, including inside an Emacs ~shell~ buffer.
- *ncurses* — a full-screen, four-pane interface (stack, source,
  interactor, REPL). Commands fire on a single keypress; you move the
  cursor onto a form and act on it (no line numbers to type). It runs on
  the terminal's alternate screen, so your program's display is restored
  when you resume.
- *aldb* — the Emacs interface (an SLDB-style minor mode). The debugger
  listens on a socket; from Emacs you connect with =M-x aldb-connect RET
  address:port RET=. Navigation and history reuse Emacs's own buffers and
  mark ring.

*Choosing the interface.* The default is the ~default-user-interface~
setting (=tui=, =ncurses= or =aldb=; persisted in =aldo.conf=). A single
run can override it on the command line with ~--debugger-ui~, without
changing the saved default; the aldb channel is configured with
~--aldb-listen [HOST:]PORT~ (HOST defaults to 127.0.0.1; port 0 picks a
free port) or ~--aldb-stdio~ (the process's stdin/stdout become the RPC
channel — incompatible with ~--interactive~). An aldb channel option
implies ~--debugger-ui aldb~:

#+begin_example
  clautolisp --debugger-ui ncurses          program.lsp
  clautolisp --aldb-listen 127.0.0.1:4301   program.lsp
#+end_example

When aldb is selected and Emacs is not yet connected, aldo prints the
=M-x aldb-connect= line to the terminal and waits — you may instead pick
the TUI or ncurses there.

** Common commands

The same verbs work in every interface (typed as tokens in the TUI,
single keys in ncurses/aldb). The most used:

- Execution: ~continue~ (=c=), ~into~ (=i=, step into), ~next~ (=n=,
  step over), ~out~ (=o=, finish), ~quit~ (=q=, abort the run).
- Breakpoints: ~break~ (=b=) at a form / line; ~list breakpoints~ (=lb=);
  ~enable~ / ~disable~ / ~delete~ / ~condition~ / ~ignore~ a breakpoint.
- Stack: ~list frames~ (=lf=, the backtrace); the ~frame~ family —
  ~frame N~ (=f=), ~frame inner~/~outer~ (=fi=/=fo=),
  ~frame top~/~bottom~ (=ft=/=fb=); ~list locals~ / ~parameters~ /
  ~variables~ (=ll=/=lp=/=lv=).
- Data: ~print EXPR~ (=p=); typing a bare ~(form)~ evaluates it in the
  current frame; ~visit EXPR~ (=v=) opens the structured inspector.
- Source: ~list source~ (=ls=); ~help~ (=h= or =?=).

In ncurses and aldb you never type a line number: put the cursor on the
target form and the command takes the form at point.

** Navigating the source

The ~navigator~ setting chooses how each *stop* (a breakpoint, a step, an
error) presents itself:

- =sexp= (the default) — the debugger enters the *form navigator* directly:
  the source is shown with the current poll-point selected (~【…】~), the
  prompt is =NAV>=, and the motion keys below apply at once. =q= drops to
  the flat =DBG>= command loop.
- =line= — the flat presentation: a window of source lines around the
  current line (marked =>>=), at the =DBG>= prompt.

Beyond stepping, you can browse the source structurally — over one tree
that runs from a sub-expression out to the file system:

- =d= / =u= — descend into / ascend out of the selected node;
- =>= / =<= — next / previous sibling; =<<= / =>>= first / last;
- ~goto~ (=g=) — jump by name or path (=goto FILE:LINE=, =goto FN=, or a
  qualified path into nested local functions);
- ~definition~ (=.=) — open the definition of the selected call;
  ~back~ / ~history~ — return through where you have been.

Browsing never changes what executes; ~print~, ~setq~ and friends always
act in the current frame.

In the navigator every debugger command is also available directly (the
navigator's dictionary is stacked over the debugger's). Two escape words
systematize reaching a shadowed command (~debug~ is the debugger
interactor's alias — ~aldo~ and ~debug~ are interchangeable):

- ~aldo CMD~ — route CMD to the debugger, dispatching normally: user
  commands first, then the built-ins (e.g. ~aldo b LOC~, while bare =b=
  breakpoints the selection). The same prefix the sedit editor uses.
- ~command CMD~ (or ~aldo command CMD~) — like bash's ~command foo~:
  skip the *user* commands and reach the built-in meaning; this is how a
  user command that shadows a built-in calls the built-in. (~debugger
  CMD~ is the historical spelling.)

** Settings and configuration

Per-session options are read and set from any interface:

- =,settings= — list every option and its value; =,settings NAME= —
  print one.
- =set NAME VALUE= — set one (names and values are case-insensitive).
  Common options: ~navigator~ (=sexp= | =line=), ~theme~ (=unicode= |
  =ascii= | =white-on-black= | =black-on-white= | =green-on-black= |
  =attributes=), ~pager~ (=on= | =off=), ~pager-height~,
  ~source-window-height~, ~value-line-width~, ~break-on-caught~.

The complete set of aldo settings, with their types:

| Setting                          | Type / values                                                     |
|----------------------------------+-------------------------------------------------------------------|
| ~navigator~                      | =sexp= \vert{} =line=                                             |
| ~directory-listing~              | =long= \vert{} =column= \vert{} =short=                           |
| ~directory-window~               | integer — context lines around the selection                      |
| ~navigation-history-max~         | integer (1000) — how many previous browse stacks the navigation history keeps; the oldest are dropped past this |
| ~sedit-on-quit~                  | =auto-save= \vert{} =do-not-save= \vert{} =ask=                   |
| ~break-on-caught~                | boolean                                                           |
| ~source-window-height~           | integer                                                           |
| ~value-line-width~               | integer                                                           |
| ~pager~                          | =on= \vert{} =off=                                                |
| ~pager-height~                   | integer                                                           |
| ~theme~                          | =unicode= \vert{} =ascii= \vert{} =white-on-black= \vert{} =black-on-white= \vert{} =green-on-black= \vert{} =attributes= |
| ~default-user-interface~         | =tui= \vert{} =ncurses= \vert{} =aldb=                            |
| ~default-aldb-listening-address~ | string (=127.0.0.1=) — address the aldb (Emacs) transport listens on when no ~--aldb-listen~ / ~--aldb-stdio~ is given |
| ~default-aldb-listening-port~    | port (=4301=) — the matching port                                 |

~decorations~ is not in this table: it is structural (the theme glyphs,
edited as data in the configuration file) rather than something =set=
changes.

The configuration lives in an AutoLISP sexp bound to
~*clal-aldo-configuration*~, read at start-up from
=$XDG_CONFIG_HOME/clautolisp/aldo.conf= (or searched along
=$XDG_CONFIG_DIRS=) *before* your rc/init files, which may then modify
it. Changes made with =set= update the variable in memory only; nothing
is written automatically. Save and reload explicitly:

- =,settings save= — write the configuration to
  =$XDG_CONFIG_HOME/clautolisp/aldo.conf= (UTF-8);
- =,settings reload= — re-read it.

The same is available from AutoLISP as ~(clal-save-aldo-configuration)~
and ~(clal-load-aldo-configuration)~.

*** The REPL has its own configuration, and the two stack
Configurations stack the way interactors do. The Lisp REPL — the bottom
interactor — carries its own =lisp.conf= alongside the debugger's
=aldo.conf=:

- =,set= — list the REPL's settings (each marked =(default)= while you
  have not overridden it);
- =,set NAME VALUE= — set one;
- =,write-settings= — write them to
  =$XDG_CONFIG_HOME/clautolisp/lisp.conf= (UTF-8). As with =aldo.conf=,
  nothing is written automatically.

Its first setting is ~sedit-on-quit~ (=auto-save= | =do-not-save= |
=ask=), governing ~(clal-sedit …)~ invocations made *from the REPL*,
while aldo's setting of the same name governs debugger-side ones.

*** Running a shell command: the =!= escape
A line whose *first* character is the shell-escape character sends the
rest of the line to your =$SHELL=, with standard input, output and error
*inherited* — so an interactive command can prompt, page, or draw:

#+begin_example
_$ !pwd
/Users/pjb/src/ogamita
_$ !ls -l | less
#+end_example

This is what ~startapp~ cannot do: it launches a program but does not
hand it the terminal.

Three details worth knowing:

- *nothing may precede the character*, not even a space — ~ !pwd~ is an
  ordinary line, not a shell escape. That is what makes the rule
  unambiguous;
- a command ending in ~&~ is backgrounded, and a non-interactive shell
  prints neither the PID nor a job-control notice, so ~echo $!~ is
  appended for you and the PID is printed. Spaces around the command do
  not defeat this; ~a && b~ does not end in ~&~ and is left alone;
- a line ending in a backslash *continues* onto the next, so a long
  command can be typed over several lines.

The character is the ~shell-escape-character~ setting of the REPL's own
configuration, ~!~ by default. Set it as a character or as a Unicode
code point — the second is the way to choose one that is awkward to
type:

#+begin_example
_$ ,set shell-escape-character "%"
_$ ,set shell-escape-character 182
_$ ,write-settings
#+end_example

The setting lives in =lisp.conf= because the escape belongs to the Lisp
interactor. The same character is in force in the debugger and the
editors too — they read this setting, not one of their own — so the
escape looks the same wherever you are.

The stacking rule: at the REPL only =lisp.conf= is active; inside the
debugger *both* are, aldo over lisp. So a setting you did not put in
=aldo.conf= but did put in =lisp.conf= is taken from =lisp.conf= even at
the =DBG>= prompt. Writes always go to the *active* interactor's own
configuration — =set sedit-on-quit …= at =DBG>= changes only aldo's (and
from then on shadows lisp's), =,set sedit-on-quit …= at the REPL changes
only lisp's.

Both files record only what you have explicitly set; anything you have
not touched keeps following the built-in default. That is what makes the
fall-through above possible — otherwise every key would always look
"set" on the aldo layer and =lisp.conf= could never be reached from the
debugger.

*** Editing a configuration file by hand
The files are meant to be readable, so a saved file also *documents
itself*: below the settings you actually changed, every remaining
setting is written out *commented*, at its built-in default value and
followed by the values it accepts. Uncomment a line and edit its value to
override it. A freshly saved =lisp.conf= therefore looks like this:

#+begin_example
;;;; clautolisp lisp.conf - the configuration of the LISP (REPL) interactor.
;;;;
;;;; One list of (name . value) settings, read at start-up.
;;;; Only the settings you changed are stored.  The lines commented
;;;; out below are at their built-in default: they are listed so you
;;;; can see what exists -- uncomment one and edit its value to
;;;; override it.  The accepted values follow each line.
;;;;
;;;; Saving (,write-settings) rewrites this file; comments you
;;;; add by hand are not kept.
(
 (sedit-on-quit . do-not-save)

 ;; Defaults -- uncomment a line to set it.
 ;;(navigator . sexp)               ; sexp | line
)
#+end_example

Two consequences worth knowing:

- the commented lines are *documentation, not data*: they are skipped by
  the reader, so a loaded file still sets only its live entries — the
  documented defaults do not become explicit settings, and the stacking
  rule above keeps working;
- saving *rewrites* the file, so comments you add by hand are not kept.

The values in the file use the file's own syntax rather than =set='s: a
boolean is written =t= or =nil= there (=on= would read back as a symbol,
which is true). The generated comments spell out the accepted values for
each setting, so this is visible on the spot.

** Long output and the pager

Commands whose output exceeds the screen — =help=, a long
=list source=, a big value — are shown a page at a time in the TUI when
~pager~ is =on= (the default on a size-limited terminal; you typically
turn it =off= under an Emacs ~shell~, which scrolls). The pager accepts
the familiar =less= keys (=SPACE=/=f= forward, =b= back, =q= quit). The
ncurses interface uses a scrollable window instead, and aldb relies on
Emacs's own buffer scrolling.

* sedit and the aldo form navigator

Clautolisp includes *sedit*, an S-expression *structural* editor: you edit
a program as a tree of forms rather than as characters. It is the same tool
in two guises — a standalone editor you call from AutoLISP with
~(clal-sedit …)~, and the *form navigator* the aldo debugger opens over live
code. This section is an orientation; the normative specification is
=clautolisp/documentation/clautolisp-sedit-spec.org=.

** Two modes: navigate and edit

sedit is always in one of two modes.

- *Navigate* (NAV) — the selection moves over the *evaluable* sub-forms of a
  program (the same poll-points the debugger stops at); structure is not
  changed. This is the mode the debugger uses; its keys are the ones in
  /Debugger → Navigating the source/ above (=d= =u= descend/ascend, =>= =<=
  siblings, =<<= =>>= first/last, =±N= skip).
- *Edit* (EDIT) — the selection moves over *every* sub-form and comment, and
  the full editing command set is available.

The selection is shown in brackets, e.g. ~(list [nil])~. Motion and mode
switching:

| Key / word          | Effect                                                    |
|---------------------+-----------------------------------------------------------|
| =d= =u=             | descend into / ascend out of the selection                |
| =>= =<= (=f= =b=)    | next / previous sibling (=<<= =>>= first / last, =±N= skip)|
| ~edit~              | switch to EDIT (an editing command by *word* also does)   |
| ~nav~               | switch back to NAV                                         |
| ~debug CMD~ / ~aldo CMD~ | from EDIT, run a debugger command CMD, then return to NAV |
| =q=                 | leave the editor, returning the edited object             |
| =h= / =?=           | help                                                      |

Because single letters mean different things in the debugger and the editor,
an editing command is recognised in NAV *by its word* (~insert~, ~wrap~, …):
typing one enters EDIT and performs it.

** Editing commands (EDIT)

- *Insert / replace* — ~insert σ~ (before the selection), ~add σ~ (after),
  ~replace σ~ (in place); each reads the new form σ after the command and
  selects it. Comment variants ~ic~ / ~ac~ / ~rc~ attach a comment.
- *Structural* — ~wrap~ (put the selection in a new list), ~splice~ (its
  inverse), ~slurp~ / ~barf~ (pull the next sibling in / push the last out),
  ~split~ / ~join~.
- *Clipboard* — ~copy~ (=c=), ~cut~ (=x=), ~paste~ (=v=); see /The clipboard/.
- *Undo* — ~undo~ (=z=): one level; a second ~undo~ redoes.
- *Evaluate* — ~eval~ (=e=) evaluates the selection; ~macroexpand~ (=m=)
  replaces it by the result. Typing a bare Lisp *form* (~(+ 1 2)~) at the
  prompt evaluates it and prints the result, like the REPL — in every mode
  (=DBG>=, =NAV>= and =SEDIT>=).
- *Files & directories* — ~load~ (=l=) and ~save~ (=s=); in a directory,
  ~new~ (=n=), ~rename~ (=r=) and ~delete~ (=x=).

sedit preserves *formatting*: an unmodified form is written back byte-for-byte
(comments and layout intact), and a form you edit is re-indented by AutoLISP's
own rules.

** Starting sedit from AutoLISP

#+begin_example
(clal-sedit)                 ; a fresh stand-alone form, starting at nil
(clal-sedit 'foo)            ; recall and edit the definition of FOO
(clal-sedit "prog.lsp")      ; edit a file (its first top-level form selected)
(clal-sedit "~/src/")        ; browse a directory
(clal-sedit '(+ 1 2))        ; edit a value as a sexp
#+end_example

~clal-sedit~ runs the editor on the terminal and returns the edited object.
Recall by name works because the interactive REPL *records* every top-level
form you evaluate, so ~(clal-sedit 'foo)~ finds the ~defun~ / ~setq~ you
typed. The initial and final forms are left in ~*clal-sedit-initial-form*~ and
~*clal-sedit-last-result*~.

** Editing while debugging

From the aldo form navigator, issuing an editing word (~edit~, ~insert~,
~wrap~, …) opens sedit on the *current function's* source. Edit it, then
leave the editor (=q=): the new definition is *installed* in the running
system, so the next call runs the edited code. Breakpoints set by poll-point
identity carry across the redefinition. While editing, ~debug CMD~ / ~aldo
CMD~ still reach the debugger, and ~nav~ returns to plain navigation.

** The clipboard

sedit keeps *two* clipboards in sync: an in-process one (full structural
fidelity, the source of truth) and the *system* clipboard (a textual
rendering other applications see). Copy/cut write both; paste reads the
system clipboard and parses it back into a form, falling back to the
in-process clipboard when the system one is empty. The AutoLISP surface:

| Function                          | Effect                                        |
|-----------------------------------+-----------------------------------------------|
| ~(clal-clipboard-copy-sexp OBJ)~  | copy OBJ (internal + system as source text)   |
| ~(clal-clipboard-paste-sexp)~     | the clipboard parsed back to a form, or ~nil~ |
| ~(clal-clipboard-put-text S)~     | set the system clipboard to string S          |
| ~(clal-clipboard-get-text)~       | the system clipboard as a string, or ~nil~    |

Paste *never evaluates* its input (a foreign ~#.(…)~ on the clipboard cannot
run code). The system clipboard is reached through a provider that
auto-selects among X11, Wayland, macOS, Windows and OSC 52, and degrades to
in-process only when none is available — clautolisp needs no GUI-toolkit
dependency. Providers, serialization and security are specified in
=clautolisp/documentation/clipboard-interface.org=. Toggle the system
mirroring off by binding ~*system-clipboard-enabled*~ to ~nil~.

** Dialect selection
The dialect descriptor controls reader strictness, host-specific
permissive parsing, and the runtime knobs documented in
~autolisp-spec~. The default is the conservative ~strict~ profile.

- ~--dialect NAME~       :: Select the named dialect. NAME is one of
                            ~strict~, ~autocad-2026~, ~bricscad-v26~,
                            ~clautolisp~, ~lax~.
- ~--strict~             :: Equivalent to ~--dialect strict~.
- ~--autocad~            :: Equivalent to ~--dialect autocad-2026~.
- ~--bricscad~           :: Equivalent to ~--dialect bricscad-v26~.
- ~--clautolisp~         :: Equivalent to ~--dialect clautolisp~.
- ~--lax~                :: Equivalent to ~--dialect lax~. Silences
                            every encoding-dispatch diagnostic
                            globally; useful when consuming code from
                            multiple vendors. The runtime still
                            honours each form; only the diagnostic
                            is suppressed.

The ~clautolisp~ dialect includes `clautolisp extensions`
(eg. variadic functions).

Whatever the dialect selected, all the operators are available. Only
those that are not specifically inside the set defined by the dialect
produce warnings when compiled and when used.

Unknown dialect names produce a diagnostic on standard error and exit
code 1.

*** Where the dialect changes a returned value
A few operators return a genuinely different value per dialect, because
the vendors themselves differ. These are behaviour differences, not
warnings, and they are listed in the AutoLISP Spec entry for each
operator under its ~*** clautolisp~ note.

- ~vl-file-systime~ — the day-of-week element (third position) is
  ~0~ for Sunday under ~strict~, ~clautolisp~, ~lax~ and the
  ~autocad-*~ dialects, and ~7~ under ~bricscad-v25~ /
  ~bricscad-v26~. Monday to Saturday are ~1~..~6~ in every dialect.
  This is not an arbitrary choice: both vendors' reference pages say
  only "Monday is day 1 ... and so on" and never state a value for
  Sunday, so each engine filled that silence its own way — AutoCAD
  with the POSIX ~struct tm~ numbering, BricsCAD with ISO-8601.
  clautolisp keeps the POSIX one.

  Because the two values are ~0~ and ~7~, one operation normalises
  every engine and every dialect:

  #+BEGIN_EXAMPLE
  (mod day-of-week 7)
  #+END_EXAMPLE

  ~(mod 0 7)~ and ~(mod 7 7)~ are both ~0~, and Monday to Saturday
  (~1~..~6~) pass through unchanged, so the result is always the POSIX
  numbering — Sunday ~0~ through Saturday ~6~ — with no test for which
  engine or dialect is in use. Read position 3 through ~mod 7~ rather
  than avoiding it.

  The list has eight elements — the eighth is milliseconds, currently
  always ~0~.

** Host backend
The Host Abstraction Layer (HAL, Phase 8 of the implementation
roadmap) decides where CAD-host effects land. The dialect descriptor
controls the *language*; the host backend controls the *target*.
Both axes are independent.

- ~--host NAME~          :: Select the backend. Currently accepted:
                            ~cador~ (default): the headless in-process
                            CAD core — an in-memory deterministic
                            CAD-database capable of entget / ssget /
                            getvar / getstring etc. (~mock~ is a
                            deprecated alias of ~cador~). ~nihil~: the
                            trivial backend — every CAD-host operation
                            signals ~:host-not-supported~ — useful for
                            programs that should not touch a host at all
                            (~null~ / ~none~ are deprecated aliases of
                            ~nihil~). A remote wire host is reserved for
                            a later phase.
- ~--mock-input PATH~    :: Attach the file at PATH as the
                            MockHost's prompt-stream. Lines are
                            consumed in order by ~getstring~,
                            ~getreal~, ~getint~, ~getpoint~, etc.
                            so headless test rigs can feed
                            deterministic answers to interactive
                            scripts.

The ~command~ special form (and ~command-s~ / ~vl-cmdf~) routes its
token sequence through the selected backend's command channel. The
MockHost has no CAD command engine: it *records* each normalized
token sequence — strings verbatim, numbers and points in their
command-line spellings (~"X,Y[,Z]"~ for points), ~""~ as the RETURN
token, ~"\\"~ (the predefined variable ~pause~) as the PAUSE token —
on a per-session log, echoes a ~Command: ...~ line, and returns
~nil~. Read the log back with ~(clal-command-log)~ (see the
~CLAL-~ extensions below). Under ~--host null~ every ~command~ call
signals ~:host-not-supported~ (~vl-cmdf~ instead returns ~nil~, per
its T / nil success contract).

*** The ActiveX / COM object model (~vla-*~ / ~vlax-*~)

Visual LISP exposes the CAD object model through ActiveX. clautolisp
provides that surface through the host backend:

- The ~vlax-*~ primitives — ~vlax-get-property~, ~vlax-put-property~,
  ~vlax-invoke-method~, ~vlax-get-acad-object~, object lifecycle
  (~vlax-create-object~, ~vlax-release-object~, ~vlax-object-released-p~),
  SAFEARRAY and VARIANT helpers — operate on VLA-objects backed by the
  selected host. On ~--host mock~ they run against an in-memory COM
  object graph (~AutoCAD.Application~ with a live ~ActiveDocument~,
  ~AutoCAD.Document~, …); on ~--host null~ they signal
  ~:host-not-supported~.
- The ~vla-*~ *accessors* are resolved **dynamically**, exactly as in
  Visual LISP: after ~(vl-load-com)~, calling ~(vla-get-<Prop> obj)~
  reads property ~<Prop>~, ~(vla-put-<Prop> obj v)~ writes it, and
  ~(vla-<Method> obj args…)~ invokes method ~<Method>~ — the name after
  the prefix is taken verbatim and matched case-insensitively. There is
  no fixed list of ~vla-get-Foo~ functions; any property/method name
  works. Before ~(vl-load-com)~ these names are undefined, and a user
  ~(defun vla-get-foo …)~ shadows the façade for that name.

- The document's *collections* are live and drawing-backed:
  ~(vla-get-blocks doc)~, ~(vla-get-layers doc)~,
  ~(vla-get-modelspace doc)~ and ~(vla-get-paperspace doc)~ return
  identity-stable collection objects whose members and ~Count~ are
  recomputed from the drawing database on each access — a
  block-record created by ~entmake~, a DXF load or ~Blocks.Add~ is
  immediately visible. Every collection answers the generic ~Item~
  method with a 0-based integer index or a case-insensitive name
  (~(vla-item blocks "*Model_Space")~); a missing item raises an
  error catchable through ~vl-catch-all-apply~, as the vendor ActiveX
  exception is. ~Blocks.Add~ / ~Layers.Add~ create table records;
  ~Delete~ on a block object erases the definition and its owned
  entities (the ~*Model_Space~ / ~*Paper_Space~ layout blocks refuse,
  as in AutoCAD). A block object is itself a collection of the
  entities it owns, so ~vlax-for~ walks block contents; its members
  are entity-backed VLA-objects that ~vlax-vla-object->ename~
  round-trips.
- Block definitions are also created the AutoLISP way: ~entmake~ of a
  ~(0 . "BLOCK")~ header opens a definition run, the entities entmade
  next belong to it, and the closing ~(0 . "ENDBLK")~ registers the
  block and returns its *name* (redefining an existing name replaces
  its contents; ~"*U"~ with flag bit 0 allocates an anonymous name).
  Block contents never appear in ~ssget "X"~, ~entlast~ or the
  top-level ~entnext~ walk; ~(entnext (tblobjname "BLOCK" name))~
  walks the block's own entities (the classic ATTDEF scan), a BLOCK
  record's ~tblsearch~ / ~tblnext~ view carries the vendors'
  ~(-2 . <first-entity>)~ walk entry, and ~entget~ works on a
  symbol-table record's ename.
- The mock host executes the model-only *drawing commands*: a
  ~(command "._line" p1 p2 "")~ (and ~CIRCLE~, ~TEXT~ with
  ~_Justify~, ~DONUT~, ~SOLID~) creates real entities on the current
  layer — the create-by-command / collect-by-~entlast~ idiom works
  headless. Every call is still recorded on the command log
  (~clal-command-log~) and echoed per ~CMDECHO~; commands outside the
  engine's subset remain record-only.
- A ~(command ...)~ argument may be a *selection set* (the vendor
  contract for object-selection prompts): ~(command "._erase" ss "")~
  erases the set's members (and their subentity runs); ~MOVE~ and
  ~COPY~ take a selection, a base point and a second point. Entity
  handles and ~_Last~ work as selection input too.
- ~ROTATE~ (selection, base point, angle) and ~-BLOCK~ (name, base
  point, selection) complete the block-factory path: ~-BLOCK~
  registers the definition and absorbs the selected entities,
  translated to the base point, out of model space. A leading ~-~ is
  part of the command's *name* (each console form is defined
  explicitly), unlike the ~.~ / ~_~ prefixes which are modifiers.
- Entity ActiveX *properties* read and write the entity's DXF groups:
  on an entity-backed VLA-object, ~TextString~ / ~TagString~ /
  ~Layer~ / ~Color~ / ~Height~ / ~Rotation~ (radians, the entget
  convention) / ~Alignment~ (acAlignment enum) / ~Name~ and
  ~EffectiveName~ (INSERT) / ~Handle~ and ~ObjectName~ (read-only) /
  … are live views of the entity data, and the point-valued
  ~InsertionPoint~ / ~TextAlignmentPoint~ come back as
  VARIANT-wrapped double SAFEARRAYs —
  ~(vlax-safearray->list (vlax-variant-value …))~ — and accept
  ~vlax-3d-point~ results (or plain lists) on writes.
- Block references work end-to-end: ~(vla-insertblock space pt name
  xs ys zs rot)~ creates the INSERT with an ATTRIB per non-constant
  ATTDEF of the definition (transformed to the placement);
  ~(vla-getattributes ref)~ returns them as a VARIANT array —
  or ~(vlax-invoke ref 'GetAttributes)~ as a plain list, since
  ~vlax-invoke~ / ~vlax-get~ / ~vlax-put~ implement the vendor
  plain-LISP-data contract. Entity methods ~Move~ / ~Rotate~ /
  ~Copy~ / ~Delete~ / ~Erase~ / ~Update~ mutate the drawing, and
  ~(vla-getboundingbox obj 'll 'ur)~ assigns the two quoted output
  symbols, as the vendors do.

Example (headless, against the mock host):

: (vl-load-com)
: (setq doc (vla-get-activedocument (vlax-get-acad-object)))
: (vla-get-name doc)            ; => "Drawing.dwg"
: (setq blocks (vla-get-blocks doc))
: (vla-get-count blocks)        ; => 2   (*Model_Space, *Paper_Space)
: (vla-get-name (vla-item blocks 0)) ; => "*Model_Space"
: (vlax-for b blocks (princ (vla-get-name b)) (princ " "))

** DCL dialogs — renderer selection and the "-" convention
An AutoLISP program that puts up a DCL dialog (~load_dialog~ /
~new_dialog~ / ~action_tile~ / ~start_dialog~) is driven by a
*renderer*. clautolisp ships two:

- the *terminal (TUI) renderer* — a pure line-oriented rendering of the
  dialog, so a dialog runs headless (piped stdin, CI, a script); and
- the *GUI renderer* — a subprocess GUI driver (e.g. the Qt app in
  ~tools/clautolisp-gui-qt~) selected with ~--gui CMD~ or the
  ~$CLAUTOLISP_GUI~ environment variable, speaking a sexp wire protocol.

~--dcl MODE~ chooses between them:

- ~--dcl tui~   :: Force the terminal / command-line form, even when a GUI
                   driver is configured. This is clautolisp's spelling of
                   AutoCAD's ~-command~ convention: in AutoCAD, prefixing a
                   command with ~-~ runs its command-line (non-dialog)
                   form; clautolisp has no per-command dispatcher, so the
                   whole-session ~--dcl tui~ flag requests that form for
                   every dialog the run puts up.
- ~--dcl gui~   :: Use the subprocess GUI driver. If none is configured
                   (~--gui~ / ~$CLAUTOLISP_GUI~), clautolisp warns and
                   falls back to the TUI.
- ~--dcl auto~  :: (default) Use the GUI when a driver is configured *and*
                   stdout is a terminal; otherwise the TUI. So every
                   headless / piped / redirected run — exactly the
                   ~-command~ scenario — automatically gets the
                   command-line form with no extra flag.

*Driving the TUI.* The terminal renderer paints the tile tree, then reads
one command per line until a button's action calls ~done_dialog~ (or EOF,
which cancels). A command is:

| input        | effect                                                     | ~$reason~ |
|--------------+------------------------------------------------------------+-----------|
| ~KEY~        | activate KEY: press a button, flip a toggle, select a       |         1 |
|              | radio_button / list item                                    |           |
| ~KEY=VALUE~  | set KEY's value — an edit_box / slider change (~$reason~ 2), |     2 / 1 |
|              | or a list_box / popup_list / toggle selection (~$reason~ 1) |           |
| ~KEY==VALUE~ | double-click select KEY                                     |         4 |
| ~KEY!~       | KEY loses focus after the edit                              |         3 |

A ~list_box~ / ~popup_list~ value is the selected item's 0-based *index*
(a name is resolved to its index); ~get_tile~ returns that index string,
as in AutoCAD/BricsCAD. A ~radio_column~ / ~radio_row~ with its own key
returns the selected ~radio_button~'s key from ~get_tile~. The predefined
clusters (~ok_cancel~, ~ok_only~, ~ok_cancel_help~, …) expand into real
~accept~ / ~cancel~ / ~help~ button tiles, so ~(action_tile "accept" …)~
is reachable.

See ~examples/all-widgets/~ (one of every tile type, with a labelled
value report you can diff against AutoCAD / BricsCAD) and
~examples/greet~ / ~examples/listpick~.

** Interactive user input (~get*~ functions)
AutoCAD and BricsCAD gather the answers to the interactive input
functions — ~getstring~, ~getint~, ~getreal~, ~getpoint~, ~getcorner~,
~getdist~, ~getangle~, ~getorient~, ~getkword~ — through the graphical
drawing editor: a command-line prompt combined with pointer and keyboard
interaction in the drawing window. That is implicitly a GUI.

clautolisp is a terminal program with no drawing editor. Under the
MockHost (the default) each ~get*~ call writes its prompt to standard
output and reads one line of text from standard input — a TUI
interaction. In the interactive REPL that line is what you type at the
terminal after the calling form; with ~--mock-input PATH~ the lines are
read from PATH instead, so scripted runs stay deterministic. Invalid
input returns ~nil~ rather than triggering the GUI host's retry prompt,
and end-of-input (EOF) also returns ~nil~ (AutoLISP's cancellation
convention). A future ~live~ host will restore the native GUI behavior.

This is a clautolisp implementation deviation; it does not change the
language-level contract of these functions. The per-function pages of the
AutoLISP specification carry the same note in their ~clautolisp~ section.

Input formats read on the TUI:
- ~getstring~ :: the whole line; the ~cr~ flag applies as specified (a
                 blank ends the input when ~cr~ is nil).
- ~getint~ :: an integer.
- ~getreal~ / ~getdist~ :: a real number (~getdist~ does not support
                 two-point picking on the TUI).
- ~getpoint~ / ~getcorner~ :: whitespace-separated coordinates, ~X Y~ or
                 ~X Y Z~; a 2D entry gets Z = 0.0. No crosshair,
                 rubber-band, or direct-distance entry.
- ~getangle~ / ~getorient~ :: an angle, returned in radians. Accepted
                 forms: a bare number (radians, e.g. ~0.5~); degrees
                 (~45 deg~, ~45.3321 degree~); degrees-minutes-seconds
                 (~43 deg 23' 15"~, where ~'~ = minutes and ~"~ =
                 seconds, summed in any order); and radians (~2.34 rd~,
                 ~pi rd~, ~2pi rd~, ~4/3 pi rd~, ~-3/2 pi rd~ — an
                 integer, decimal or rational magnitude, optionally
                 multiplied by ~pi~).
- ~getkword~ :: matched against the keywords set by the preceding
                 ~initget~; a non-matching line returns ~nil~.

** Colour output
~clautolisp~ accents AutoLISP-symbol names in error messages,
backtraces, and trace output with an ANSI colour when standard
output is a terminal. The default is conservative (yellow on
assumed-dark) and never fires when the output is being captured
(pipe, file redirect, test harness).

- ~--no-color~           :: Disable colour for this invocation.
                            Equivalent to setting ~$NO_COLOR~ to
                            any non-empty value (see https://no-color.org).
- ~$NO_COLOR~            :: Universal no-color convention; honoured
                            equivalently to ~--no-color~.
- ~$CLAUTOLISP_SYMBOL_FOREGROUND=NAME~ ::
                            Force the foreground colour for printed
                            AutoLISP symbols. Accepted names (case
                            and whitespace insensitive): ~black~,
                            ~red~, ~green~, ~yellow~, ~blue~,
                            ~magenta~, ~cyan~, ~white~ and their
                            ~bright-~ prefixed variants
                            (~bright-black~ is also ~grey~ / ~gray~).
                            ~default~ / ~none~ / ~off~ leaves the
                            foreground axis bare.
- ~$CLAUTOLISP_SYMBOL_BACKGROUND=NAME~ ::
                            Force the background colour for printed
                            AutoLISP symbols. Same vocabulary as the
                            foreground sibling; either or both env
                            vars may be set. Both win over the
                            automatic luminance probe so the user
                            gets a deterministic look without
                            depending on terminal detection.
- ~$CLAUTOLISP_BACKGROUND=dark|light~ ::
                            Override the terminal-background guess
                            without specifying a colour. ~dark~ keeps
                            the yellow accent; ~light~ flips it to
                            blue.
- ~$CLAUTOLISP_PROBE_OSC11~ ::
                            Opt-in to the active OSC 11 terminal
                            query (spawns ~/bin/sh~ + ~stty~ + ~dd~
                            against ~/dev/tty~). Off by default
                            because on some platforms — notably
                            macOS arm64 — the helper subprocess
                            receives SIGTTOU and hangs CLI startup.
                            Safe to set on most Linux desktops and
                            iTerm2 / Terminal.app launched from a
                            normal shell.

Example: yellow symbols on a dim-blue background, deterministically,
no probing:

#+BEGIN_SRC sh
  export CLAUTOLISP_SYMBOL_FOREGROUND=bright-yellow
  export CLAUTOLISP_SYMBOL_BACKGROUND=blue
  clautolisp -x '(foreach x t (princ x))'
#+END_SRC

** Source-file and terminal encoding
- ~-e ENC~                :: Set the default source-file encoding for
                             every ~load~ in the session, including
                             nested ~(load …)~ calls from init files.
                             ENC is one of ~utf-8~, ~iso-8859-1~,
                             ~latin-1~, ~windows-1252~, ~cp1252~.
                             Overrides the dialect default and the
                             POSIX-locale guess (~LC_ALL~ /
                             ~LC_CTYPE~ / ~LANG~). Surfaced to user
                             code as the ~*AUTOLISP-FILE-ENCODING*~
                             global.
- ~-E ENC~                :: Declared terminal-IO encoding for the
                             session. Surfaced to user code as the
                             ~*AUTOLISP-TERMINAL-ENCODING*~ global so
                             code that emits raw bytes can adapt. No
                             stream rebinding is performed at the CL
                             level — set this when your downstream
                             tooling needs the declared encoding to
                             match what you actually emit. Same ENC
                             vocabulary as ~-e~.

*** Writing sources that load on every engine
If your sources are going to be loaded by a CAD host as well as by
clautolisp, write them as *UTF-8 with a byte-order mark*. That is the
one spelling every post-2021 engine identifies without guessing.

The reason is a rule of the CAD engines, not of clautolisp, and it is
worth knowing because it fails silently. ~open~ gained an encoding
argument in AutoCAD 2021 and BricsCAD V21 (~"utf8"~, ~"utf8-bom"~,
~"utf16-bom"~), but ~load~ never did: the encoding of a source file is
decided by its first bytes alone. With no BOM the host system codepage
decides — and as Bricsys puts it, "UTF-8 without BOM can not be
distinguished from normal ANSI".

So a source written as UTF-8 without a mark loads correctly wherever the
host codepage happens to match the author's, and wrongly elsewhere: on
macOS, where ~SYSCODEPAGE~ is MAC_ROMAN, the same bytes decode to
different characters. Nothing raises an error — the file reads, the
program runs, and the strings are wrong. A BOM removes the guess.

The full rules, with the vendor sources, are in the ~open~ and ~load~
entries of the AutoLISP specification.

*** Launch-chain resolution and the degenerate case
At startup the runtime resolves the file encoding via
~or-else(LC_ALL, LANG, LC_CTYPE, -e flag)~ and pushes the result
into two slots: ~SYSCODEPAGE~ (read-only host sysvar) and
~*AUTOLISP-FILE-ENCODING*~ (read-write global the user may
~setq~ at the REPL or in init files).

When ~-e~ is absent AND all three locale env vars are unset or
empty (the *degenerate case* — common in CI containers and
freshly-provisioned cloud hosts), the two slots diverge:

- ~SYSCODEPAGE~ / ~DWGCODEPAGE~ -> ~"US-ASCII"~. The safest 7-bit
  assumption a vendor-compatible host sysvar can carry. User code
  that branches on ~(getvar "SYSCODEPAGE")~ gets a non-empty
  deterministic value.

- ~*AUTOLISP-FILE-ENCODING*~ -> ~""~ (the **empty string**). The
  global is bound to a non-nil autolisp-string, but the empty
  value is a sentinel meaning "no preference — LOAD/OPEN should
  consult the dialect default." The runtime's
  ~LOOKUP-AUTOLISP-FILE-ENCODING~ helper treats empty the same
  way it treats an unbound global, so the LOAD precedence chain
  falls through to the dialect default:
  ~--clautolisp~ / ~--autocad-2026~ / ~--bricscad-v26~ -> UTF-8;
  ~--strict~ -> ISO-8859-1.

Observable from AutoLISP under the degenerate case:

#+BEGIN_SRC autolisp
*AUTOLISP-FILE-ENCODING*           ; => ""           (bound, non-nil)
(strlen *AUTOLISP-FILE-ENCODING*)  ; => 0
(getvar "SYSCODEPAGE")             ; => "US-ASCII"
(load "lib/has-utf8-bytes")        ; loaded with UTF-8 under --clautolisp
#+END_SRC

Why the asymmetry: pinning ~*AUTOLISP-FILE-ENCODING*~ to
~"US-ASCII"~ in the degenerate case would make every source-file
~load~ strict ASCII regardless of dialect, and the first
non-ASCII byte in any init file raises a stream decoding error.
A 1-to-1 8-bit fallback (~ISO-8859-1~) would avoid the crash —
every byte is a valid ISO-8859-1 character — but at the cost of
silently mojibake'ing UTF-8 multi-byte sequences into pairs of
Latin-1 characters. The empty-string sentinel cleanly hands the
decision back to the dialect, which already declares what
encoding its source files use.

The full design rationale is in
~issues/closed/encoding-dispatch.issue~ §"Degenerate launch case."

*** Which encodings you actually get (and why it no longer depends on the host)
Run ~clautolisp --list-encodings~ for the catalogue on the machine in
front of you. It has up to three sections: the mandatory four, whatever
else the underlying Common Lisp implementation ships, and — since
1.8.28 — a *Provided by clautolisp* section.

That last section exists because the codec set a Common Lisp
implementation ships is its own business, and the two clautolisp
supports disagree badly. Measured:

| encoding         | SBCL | CCL |
|------------------+------+-----|
| CP-1252          | yes  | no  |
| CP-1250/51/53/54 | yes  | no  |
| KOI8-R           | yes  | no  |
| CP-932           | yes  | yes |

So ~(open "f" "w" "CP-1252")~ — an ordinary call naming the historic
Windows ANSI code page — used to work when clautolisp ran on SBCL and
signal when it ran on CCL. That is a host artefact leaking into the
language. clautolisp now carries its own single-octet codec and uses it
exactly where the host has none, so the same AutoLISP program behaves
the same way on every host. Nothing changes where the host does ship
the encoding: the native path is used unchanged.

The built-in codec covers single-octet encodings only. That is the
range over which a byte offset and a character offset coincide, which
is what keeps the wrapper exact; it also happens to cover every gap
measured above. A multi-byte encoding neither the host nor clautolisp
provides (CP-950, say) still fails, rather than half-working — you get
an ~enc-unsupported-target~ diagnostic naming it.

*** Encoding names the hosts spell differently
A codec the host *does* ship can still be out of reach, if the two
hosts register it under different names. Mac Roman is the case in
point — and unlike the code pages above it cannot be repaired with a
codec of our own, because babel (which every table in the built-in
codec is derived from) ships no Mac Roman mapping at all:

| spelling    | SBCL | CCL | babel |
|-------------+------+-----+-------|
| ~MAC-ROMAN~ | yes  | yes | no    |
| ~MACINTOSH~ | yes  | yes | no    |
| ~MACROMAN~  | no   | yes | no    |

So — since 1.8.44 — clautolisp normalises the spelling instead, and
every path that takes an encoding name accepts every spelling in
circulation: the ~-e~ / ~-E~ options, ~(open path mode ENCODING)~, and
~(load path [onfailure] ENCODING)~. Case, dashes, underscores and
spaces are all ignored, so ~"mac-roman"~, ~"MACROMAN"~, ~"Mac Roman"~,
~"macintosh"~, ~"x-mac-roman"~ and ~"CP-10000"~ all resolve to the
~:MAC-ROMAN~ external-format both hosts accept.

This matters most on macOS: BricsCAD there reports
~(getvar "SYSCODEPAGE")~ as ~"MAC_ROMAN"~, so

#+begin_src lisp
(setq *AUTOLISP-FILE-ENCODING* (getvar "SYSCODEPAGE"))
#+end_src

is the obvious thing for portable user code to write. Before 1.8.44 it
resolved to a keyword SBCL does not register, and the next ~LOAD~ died
with =Undefined external-format: :MACROMAN= — on an SBCL build only.

* Environment variables
Two kinds live here, and the difference matters: *knobs* you set to
change what clautolisp does, and *probes* clautolisp reads to find out
where it is running. Setting a probe is legitimate — it is how you
correct a wrong guess — but it is not its purpose.

** Knobs
- ~$CLAUTOLISP_GUI~ :: DCL GUI driver command, used when ~--gui~ is
  omitted. See /DCL dialogs/ above.
- ~$CLAUTOLISP_DCL_DEBUG~ :: when set and non-empty, trace the DCL
  subprocess renderer on standard error, each line prefixed
  ~[dcl-debug]~. The first thing to set when a dialog does not appear
  or the driver does not shut down.
- ~$CLAUTOLISP_BACKGROUND~ :: ~dark~ or ~light~; overrides the detected
  terminal background. See /Colour output/ above.
- ~$CLAUTOLISP_DEBUG_PATHMAP~ :: when set to any value, dump the
  build and run path-mapping frames at startup. See /Paths on Windows/.
- ~$CLAUTOLISP_DWG_LIBDIR~ :: explicit directory for the DWG codec
  shared library, tried *before* the development tree and the installed
  layout. The way to point clautolisp at a codec you built yourself.
- ~$CLAUTOLISP_PREFIX~ :: the ~$PREFIX~ used to build the trusted
  search path for ~findtrustedfile~ and secure loading; omitted from
  the path when unset.
- ~$CLAUTOLISPCASEINSENSITIVEPATHS~ :: initial value of the system
  variable of the same name; ~1~ resolves every path against the
  filesystem without regard to case, and returns real names. See /Paths
  whose case does not match the disk/. It carries the sysvar's exact
  name, with no underscores — that is how the variables that seed a
  system variable are spelled here, as against clautolisp's own
  ~$CLAUTOLISP_*~ knobs. Honoured under every dialect but ~--strict~,
  the CAD emulation dialects included.
- ~$AUTOLISP_NO_INIT~, ~$CLAUTOLISP_NO_INIT~ :: equivalent to
  ~-norc~ / ~--no-init~.
- ~$NO_COLOR~ :: disable ANSI colour ([[https://no-color.org][no-color.org]]).
- ~$XDG_CONFIG_HOME~, ~$XDG_CONFIG_DIRS~ :: where ~lisp.conf~ and
  ~aldo.conf~ are read and written.
- ~$XDG_DATA_HOME~ :: contributes ~$XDG_DATA_HOME/autolisp/~ to the
  trusted search path (falling back to ~$HOME/.local/share~).
- ~$XDG_STATE_HOME~ :: where the default dribble file is written.

** Probes
- ~$LC_ALL~, ~$LANG~, ~$LC_CTYPE~ :: consulted in that order for the
  default source and terminal encoding when ~-e~ / ~-E~ are absent.
- ~$COLORFGBG~, ~$TMUX~ :: consulted, after ~$CLAUTOLISP_BACKGROUND~,
  to work out whether the terminal is dark or light.
- ~$COLUMNS~ :: the width the debugger's ~:column~ directory listing
  fills, when it parses as an integer above 20; otherwise 80. A dumb
  terminal often cannot report its size, which is why this is read at
  all.
- ~$MSYSTEM~, ~$OSTYPE~ :: detection inputs for classifying the run
  environment on Windows (MSYS2 / Cygwin / WSL / native). If
  ~$CLAUTOLISP_DEBUG_PATHMAP~ shows a classification you did not
  expect, these are what produced it.
- ~$HOME~, ~$PATH~, ~$SHELL~ :: the usual meanings. ~$SHELL~ is the
  shell the ~!~ escape runs your command in.

** Build-time
- ~$CLAUTOLISP_STRICT_BUILD~ :: when set to 1, a build that produces
  any non-style warning aborts instead of completing with the warnings
  merely logged. Read by the build, not by the program.

* Image-introspection variables (~*AUTOLISP-…*~)
At startup ~clautolisp~ publishes a set of globally-bound variables
in the running AutoLISP image describing how it was invoked. User
code can read them to branch on backend, dialect, encoding, etc.
See ~issues/closed/transmit-options.issue~ for the full design and
the alfe-side counterpart.

** Static — bound once, before the first user action
- ~*AUTOLISP-FRONTEND*~         :: The symbol ~CLAUTOLISP~ — clautolisp
                                   was the entry point. (Under alfe
                                   this is ~ALFE~.)
- ~*AUTOLISP-BACKEND*~          :: The symbol ~CLAUTOLISP~ — the
                                   engine running this code.
- ~*AUTOLISP-DIALECT*~          :: The active dialect's canonical
                                   name as a symbol — ~STRICT~,
                                   ~AUTOCAD-2026~, ~BRICSCAD-V26~.
                                   Bound at launch, but *writable*:
                                   ~(setq *AUTOLISP-DIALECT* 'lax)~
                                   switches the dialect immediately
                                   for every dialect-sensitive

                                   reader and the debugger's and
                                   inspector's form reads, which

                                   read.
- ~*AUTOLISP-HOST*~             :: The HAL backend's name as a symbol

- ~*AUTOLISP-MOCK-INPUT*~       :: Pathname (string) passed to

- ~*AUTOLISP-GUI-COMMAND*~      :: Subprocess renderer command
                                   passed to ~--gui~, or nil.
- ~*AUTOLISP-TRACE*~            :: T when ~--trace~ was on at startup.
- ~*AUTOLISP-FILE-ENCODING*~    :: Always a string (never nil).

** Dynamic — bound only while the matching action runs
- ~*AUTOLISP-LOAD-PATHNAME*~    :: The pathname of the file being
                                   loaded by a ~-l~ action. Bound to
                                   the path string for the duration
                                   of the ~load~ call; reset to nil
                                   on return (success or signal).
- ~*AUTOLISP-EXPRESSION*~       :: The source text of a ~-x~ action,
                                   bound while the expression is
                                   evaluated. Cleared on return.
- ~*AUTOLISP-INTERACTIVE*~      :: T while the REPL is active.

Code running inside an init file can therefore distinguish "loaded

path" (~*AUTOLISP-LOAD-PATHNAME*~ is nil).

* Banner
In REPL mode (and only in REPL mode) ~clautolisp~ prints a one-line
banner before the first prompt:

#+BEGIN_EXAMPLE
clautolisp 0.0.9 — REPL (STRICT dialect, null-host host) — Ctrl-D to exit.
#+END_EXAMPLE

The version string, dialect name, and host backend name reflect the
current build and the selected ~--dialect~ / ~--host~. Pass
~--quiet~ to suppress the banner.

* Exit Codes
~clautolisp~ uses the following exit codes. They are stable and may
be relied upon by shell scripts.

- ~0~  :: Successful completion (file or ~-x~ ran without error;
          REPL exited cleanly via end-of-input; ~--help~ /
          ~--version~ printed and exited; an AutoLISP ~exit~ /
          ~quit~ termination was raised cleanly).
- ~1~  :: A runtime error escaped the AutoLISP error-handling layer,
          or the option parser rejected an unknown flag.
- ~2~  :: The requested file could not be opened (caught Common-Lisp
          ~file-error~).

Within the REPL, individual evaluation errors are reported but do
*not* terminate the loop; the binary will still exit 0 once stdin
closes.

** Choosing your own exit status
The three codes above are what clautolisp itself produces. An AutoLISP
program can also *choose* the status, through a small channel that
mirrors the one the CAD engines' bootstrap provides — so a single
~run-tests.lsp~ or ~C:MAIN~ is portable across BricsCAD, AutoCAD and
clautolisp with no per-engine branch:

- ~(autolisp-set-status N)~ :: record integer ~N~ as the pending exit
  status, and return it. Nothing terminates.
- ~(autolisp-status)~ :: read the pending status back; 0 when it was
  never set.
- ~(quit [N])~ :: with an argument, terminate with exit code ~N~;
  without one, terminate with the *pending* status. ~(exit [N])~ takes
  the same optional argument and behaves identically.

So the status can be decided early and consumed later, which is the
usual shape of a test script:

#+BEGIN_SRC autolisp
(autolisp-set-status (if all-tests-passed 0 1))
;; … more work, possibly in another function …
(quit)                       ; exits 1 if a test failed
#+END_SRC

These three are *clautolisp extensions*. They are available under the
~clautolisp~ dialect and usable under ~lax~; under ~strict~, ~autocad~
or ~bricscad~ they still work but emit the ~[exit-status-extension]~
portability diagnostic, like every other out-of-dialect extension (see
/Errors and Diagnostics/). ~autolisp-set-status~ is deliberately named
and typed exactly like the CAD-side bootstrap function — minus its
STATUSFILE write — while ~autolisp-status~ has no vendor counterpart and
is clautolisp's own way of letting ~quit~ consult the pending value.

Because a program may pick any integer, the guarantee stated above is
narrower than it looks: codes 0, 1 and 2 are stable *when clautolisp
itself decides them*. A script that calls ~quit~ with its own status
owns the meaning of that code, and a shell caller cannot tell the two
apart from the exit status alone.

* Paths whose case does not match the disk
A corpus written on Windows or macOS has never had its path spellings
checked. Those filesystems fold case, so nothing there sanctions a
mismatch: a program can write ~DIAL/SIGFIC.LSP~ in one place and
~dial/sigfic.LSP~ in another and work. Bring it to Linux and it fails:

#+begin_example
Erreur: LOAD could not locate /…/schms/dial/sigfic.LSP
#+end_example

— while the file is there, named ~DIAL/SIGFIC.LSP~.

Reading the code does not help. In the incident this feature comes from,
the path was not a literal at all: it was derived from a class name,
~/es/schms/dial/sigfic~, whose case is a naming convention with no
relation to the disk.

** Turning it on
Set the system variable ~CLAUTOLISPCASEINSENSITIVEPATHS~ to ~1~ and every
path clautolisp receives is validated against the filesystem without
regard to case, and returned under its real name:

#+begin_example
_$ (setvar "CLAUTOLISPCASEINSENSITIVEPATHS" 1)
1
_$ (findfile "dial/sigfic.lsp")
: [path-case]: FINDFILE "dial/sigfic.lsp": found as "DIAL/SIGFIC.LSP" -- the case differs, and only a case-insensitive filesystem forgives it
"/…/schms/DIAL/SIGFIC.LSP"
#+end_example

A program can therefore switch it on for itself. To treat a whole corpus
— a batch of inherited files, a CI job — without editing any of it, use
the environment variable of the same name:

#+begin_example
$ CLAUTOLISPCASEINSENSITIVEPATHS=1 clautolisp run.lsp
#+end_example

It applies everywhere a path goes in: ~load~, ~open~, ~findfile~, the
~vl-file-*~ functions, ~vl-directory-files~ and ~vl-mkdir~. A uniform
rule, so behaviour does not depend on which function you happened to
call.

** It works under the CAD dialects too
The system variable exists under *every dialect except ~--strict~*, so
this works:

#+begin_example
$ CLAUTOLISPCASEINSENSITIVEPATHS=1 clautolisp --dialect bricscad-v26 run.lsp
#+end_example

That is the case that matters most, and it is why the variable is not
reserved to ~--clautolisp~: you run a corpus under ~--bricscad~ or
~--autocad~ to exercise it as it will actually run, and a corpus written
for Windows is exactly the one whose path spellings have never been
checked by anything.

~--strict~ is the exception. It exists to report what a portable engine
would refuse, and a path whose case does not match the disk is precisely
that — so there, the variable does not exist and nothing is folded.

*** Switching dialect at runtime moves the sysvar table with it

~(setq *AUTOLISP-DIALECT* …)~ changes the dialect for everything that
follows, and *the system-variable table follows too*: leaving ~--strict~
reveals the clautolisp system variables, and entering the ~bricscad~
dialect hides the ones BricsCAD does not define. Both directions.

#+begin_example
$ CLAUTOLISPCASEINSENSITIVEPATHS=1 clautolisp
_$ (getvar "CLAUTOLISPCASEINSENSITIVEPATHS")   ; strict: not there
nil
_$ (setq *autolisp-dialect* 'bricscad)
BRICSCAD
_$ (getvar "CLAUTOLISPCASEINSENSITIVEPATHS")   ; revealed, and seeded
1                                              ;   from the environment
#+end_example

The first time a variable is revealed it is initialised by the full
precedence — ~setvar~ over the environment over the dialect default — so
the environment reaches it, exactly as it would have at launch.

*A value you have set is masked, not destroyed.* Passing through a
dialect that hides the variable makes it invisible for as long as you
are there; coming back gives you *your* value, not the environment's:

#+begin_example
_$ (setvar "CLAUTOLISPCASEINSENSITIVEPATHS" 0)
0
_$ (setq *autolisp-dialect* 'strict)
STRICT
_$ (getvar "CLAUTOLISPCASEINSENSITIVEPATHS")   ; masked
nil
_$ (setq *autolisp-dialect* 'bricscad)
BRICSCAD
_$ (getvar "CLAUTOLISPCASEINSENSITIVEPATHS")   ; your 0, not the env's 1
0
#+end_example

A remembered value is re-applied *as a ~setvar~ would be*: under a
dialect where the variable is absent or read-only it stays remembered
and unapplied, rather than being forced into a cell the emulated engine
would not have.

*The default stays ~0~ under the CAD dialects as well*, and that is
deliberate. One could argue that emulating Windows should mean folding
case by default, since Windows filesystems do; but BricsCAD on Linux is
not believed to fold case on a case-sensitive filesystem, so folding by
default would be clautolisp inventing behaviour rather than reproducing
the engine it emulates. You ask for it, explicitly, or it does not
happen.

** What it returns is the real name
~findfile~ hands back the name *on disk*, not the one you asked with.
This is not a detail: a resolved path is typically stored and used again,
and returning your spelling would work once and fail on the next round.

** Creating is not resolving
The two are treated differently, deliberately. For a file that must
exist, the whole path is resolved. For a file being *created*, the last
component is taken exactly as you wrote it:

#+begin_example
_$ (open "Rapport.txt" "w")     ; creates Rapport.txt
#+end_example

even when a ~RAPPORT.TXT~ is sitting next to it — otherwise you would
silently overwrite a file you never named. The directories leading to it
are still resolved, so writing into ~dial/~ works when the disk says
~DIAL/~. Mode ~"a"~ is the mixed case: an existing file is appended to
under its real name; a new one is created under the name as written.

** Two entries differing only by case
On a case-sensitive filesystem ~dial/~ and ~DIAL/~ can both exist. An
exact match always wins, without ambiguity. Failing that, a single
case-insensitive match is taken. When several match, clautolisp *refuses
to choose* and reports an error naming them: reading a file nobody asked
for would be worse than the failure this feature removes.

** Why it still warns
The ~[path-case]~ diagnostic is the point, not a nuisance. A strict
filesystem is the only one that *validates* the case of your paths — in
the original incident the defect survived macOS development, BricsCAD and
AutoCAD, because all three fold case, and only the Linux run revealed it.
The warning keeps both halves: your program runs, and you learn which
spelling is wrong and what the real name is. Without it the sysvar would
merely sweep the problem under the carpet.

** Why it is off by default
The default is ~0~, and not out of timidity. At ~1~ a program reaches
files an exact spelling would not have reached — ~"/ETC/PASSWD"~ becomes
readable — so a program building paths from user input has a wider
surface. Switching it on is a deliberate act of the program or of the
test harness.

* Paths on Windows
On macOS and Linux this section does not apply: the mapping layer
detects an identity environment and every path you write is used
verbatim. It matters on Windows, where the *same machine* offers
several incompatible ways to spell the same file.

AutoLISP works with path *strings*, not Common Lisp pathnames — that is
the vendors' API and clautolisp keeps it. But on Windows a string like
~/c/work/a.lsp~ is meaningful in an MSYS2 shell, ~/cygdrive/c/work/a.lsp~
in Cygwin, ~/mnt/c/work/a.lsp~ under WSL and ~C:/work/a.lsp~ to a native
Windows program — four spellings, one file. clautolisp can also be
*built* in one of those environments and *run* from another, so the
form baked into the image at build time need not be the form you type at
run time.

clautolisp therefore recognises five kinds of environment — ~posix~,
~native-windows~, ~cygwin~, ~msys2~ and ~wsl~ — and records two frames:
the *build frame*, frozen into the image when the executable was made,
and the *run frame*, detected at startup. Paths coming *in* (~open~,
~load~, the file arguments of the command line) are understood in the
frame you are actually running in, and paths going *out* — notably
~findfile~ and ~findtrustedfile~ — are handed back in that same frame.
The practical consequence is the one you want: *you write paths the way
your shell spells them*, and a path that clautolisp gives you can be
pasted straight back into that shell.

The drive mappings are not guessed from convention alone. Cygwin and
MSYS2 record the truth in ~/etc/fstab~ and WSL reports it through
~mount~; clautolisp reads whichever applies and *prefers* it, keeping
the conventional layout (~/cygdrive/c~, ~/c~, ~/mnt/c~) underneath for
anything the system does not mention. So an MSYS2 installed somewhere
other than ~C:\msys64~, a mapped network share, or an extra WSL drive
are all handled, and a machine with no readable mount table still
starts — it simply falls back to the conventions.

To see how your host was classified, set ~CLAUTOLISP_DEBUG_PATHMAP~ to
any value; the build and run frames are dumped to standard error at
startup:

#+BEGIN_EXAMPLE
$ CLAUTOLISP_DEBUG_PATHMAP=1 clautolisp --version
build-environment: kind=:MSYS2 drive-style=:POSIX-MOUNT drive-mount-prefix="/"
    home=… mount-table=…
    probe=…
run-environment: kind=:MSYS2 drive-style=:POSIX-MOUNT drive-mount-prefix="/"
    …
#+END_EXAMPLE

Each frame reports its ~kind~, how it spells drives, the mount table in
force, and a ~probe~ plist recording what the detection actually saw —
including how many entries came from the live system rather than the
conventions.

This is the first thing to look at if a path that works in your shell is
not found by ~load~ or ~findfile~: it tells you whether clautolisp
believes it is in the environment you think it is in.

Two related behaviours are documented elsewhere in this manual: ~".."~
segments are resolved uniformly and warn outside ~--lax~ (see the
dialect diagnostics below), and relative paths resolve against the
launch directory rather than the build directory.

* Errors and Diagnostics
- Reader errors are produced by the AutoLISP reader and surface as
  ~simple-error~ conditions whose printable form embeds a structured
  ~diagnostic~ (severity, code, message, source span). They are
  printed to standard error in batch modes and to standard error in
  REPL mode while the loop continues.
- Runtime errors are signalled as ~autolisp-runtime-error~ with a
  symbolic ~code~ (e.g. ~UNDEFINED-FUNCTION~, ~UNBOUND-VARIABLE~,
  ~TYPE-ERROR~) and a human-readable message.
- Termination conditions raised by ~exit~ / ~quit~ (~autolisp-termination~)
  surface as a one-line notice on standard error and exit cleanly.

The exact set of error codes lives in the runtime; see
~autolisp-runtime/source/api.lisp~ for the canonical mapping.

** Dialect-portability diagnostics (~lambda-list-extension~, ~ext-bricscad-undocumented~)
Separate from the encoding diagnostics below, and following the same
advisory principle: a construct that is not portable across CAD
vendors still *runs*, but says so on standard error when the active
dialect targets a host that lacks it.

*How to see them.* Nothing to enable — they print to *standard error*
during a normal ~clautolisp~ or ~alfe~ run, and no quiet/verbosity
knob suppresses them. If you have never seen one, that is the
expected outcome of running under ~--dialect clautolisp~ or ~--lax~,
which are deliberately quiet; run the same file under ~--strict~ (the
default) or ~--autocad~ to surface them. Each site reports at most
once per run, so a loop around a non-portable form warns once, and a
form that is never reached never warns at all.

*What a diagnostic looks like.* Every one is a single line carrying a
bracketed *tag*, the place, and what is wrong:

: [lambda-list-extension] drawing.lsp:12 in COMPUTE-AREA: DEFUN `&REST': rest parameter not portable to strict

The *tag* is the stable identifier: it is what to grep for, and what to
look up. The location is ~FILE:LINE in FUNCTION~ with whichever parts
are known — the file and line require the source map (a debug load),
while the function is always reported.

The line is deliberately short, because the explanation belongs
somewhere it can be as long as it needs to be. Every tag is documented
in the annex /Dialect portability warnings/
(~clautolisp-dialect-warnings.org~, shipped with the manual): what the
construct is, exactly how each engine diverges, why it matters, and the
reference material. The annex is *generated* from the same register the
diagnostics are formatted from, so it cannot disagree with what you see
on screen.

The tags fall into five families:

| Family             | What it means                                                 |
|--------------------+---------------------------------------------------------------|
| portability        | a construct one engine has and another does not               |
| extension notice   | a clautolisp extension used outside ~--dialect clautolisp~     |
| vendor divergence  | clautolisp follows the spec where a vendor does not           |
| encoding           | the ~enc-*~ codes — encoding controls and codepages            |
| trust              | the ~sec-*~ codes — SECURELOAD's warn-and-proceed path         |

*Turning them into errors.* The dialect descriptor carries
~:portability-warning-mode~, default ~:warn~. Set it to ~:error~ and
the first non-portable construct actually reached aborts the run with
a ~:non-portable-construct~ error instead of printing. This is
non-conforming by design — it changes whether a program runs — so it
is never a dialect default; it exists for a portability audit, in the
same spirit as ~:unbound-variable-mode :strict-error~.

*Constructs clautolisp declines to implement.* A few BricsCAD
constructs are deliberately absent rather than merely unimplemented,
and calling one prints an ~ext-bricscad-undocumented~ note explaining
the refusal before the usual undefined-function error:

- ~setf~ — on a real BricsCAD V26 this returns a constant sentinel
  ~2~ for every value and does *not* assign, so imitating it would
  propagate a broken operator. If clautolisp ever gains ~setf~ it
  will be a clean generalised assignment, not this.
- ~let*~ — BricsCAD has no ~let*~ either, so it is not a vendor
  extension that anyone's portable code can depend on.

That note is *not* dialect-gated, because the error fires under every
dialect and a ~--dialect bricscad~ user is the likeliest to be
surprised — on the real engine, ~setf~ does exist.

The decisions behind all of this live in one table,
~clautolisp/autolisp-runtime/source/portability.lisp~, which records
for each construct the dialects whose host provides it, the dialects
that stay quiet regardless, and the evidence the entry rests on.

** Encoding-dispatch diagnostics (~enc-*~)
Each dialect dispatches a distinct diagnostic when user code uses an
encoding-related extension that belongs to a different dialect. The
diagnostics are *advisory*: the runtime always honours the form so
user code stays runnable across dialects; the diagnostic just
surfaces the portability concern.

Eight codes, all prefixed ~enc-~:

| Code                        | When                                             |
|-----------------------------+--------------------------------------------------|
| ~enc-foreign-dialect~       | a form belonging to a non-selected dialect       |
| ~enc-extension-used~        | ~--strict~ only: any encoding extension          |
| ~enc-unsupported-target~    | selected encoding has no host expression         |
| ~enc-invalid-value~         | bad encoding name string                         |
| ~enc-lispsys-out-of-range~  | ~(setvar "LISPSYS" n)~ with ~n \notin {0,1,2}~   |
| ~enc-codepage-mismatch~     | ~DWGCODEPAGE~ differs from ~SYSCODEPAGE~         |
| ~enc-unknown-codepage~      | unknown ~SYSCODEPAGE~ string                     |
| ~enc-host-dependent~        | ~"ANSI"~ used in a write context (info)          |

Diagnostics print to standard error as
~[enc-<code>] <message>~. The output stream is overridable for
tests via the CL parameter
~clautolisp.autolisp-runtime:*enc-diagnostic-stream*~; emission is
silenced entirely by binding
~*enc-diagnostic-suppress-p*~ non-nil (the runtime side-door for
the per-file pragma mechanism described below).

*Two user-facing suppression knobs:*

- *Per-code pragma.* Inside a source file:

  #+BEGIN_SRC autolisp
  (clal-suppress-enc-diagnostic 'enc-extension-used 'enc-foreign-dialect)
  ;; remainder of the file emits nothing for the two listed codes
  #+END_SRC

  Re-enable via ~(clal-enable-enc-diagnostic 'enc-extension-used)~
  or, without arguments, ~(clal-enable-enc-diagnostic)~ to clear
  the entire suppression set. Code names accept either a string
  (~"enc-extension-used"~) or a symbol (~'enc-extension-used~);
  the leading ~enc-~ is optional.

- *--lax dialect.* Run clautolisp with ~--lax~ (or
  ~--dialect lax~) to silence *every* encoding diagnostic
  globally for the session. Useful when consuming code from
  multiple vendors and you don't want to commit to one
  dialect's portability rules. The runtime still honours each
  encoding form; only the diagnostic is suppressed.

*Static encoding-extension linter*:

~(clal-lint-encoding-extensions FORM)~ walks FORM recursively
and emits the same enc-* diagnostics the runtime would, without
actually evaluating any call. Useful for catching dead-code
encoding extensions before they ship — pipe a file's parsed
form-tree through the lint at compile time:

#+BEGIN_SRC autolisp
;; Hypothetical CI gate:
(clal-lint-encoding-extensions
  (read-from-string-or-something-like-it
   (slurp "lib/encoding-aware.lsp")))
;; -> [enc-extension-used] LOAD's positional [encoding] argument...
;;    [enc-foreign-dialect] OPEN CCS-SUFFIX ...
#+END_SRC

The lint shares SIGNAL-ENCODING-DIAGNOSTIC with the runtime
emitters, so dialect / pragma / --lax gates apply identically.
Returns ~T~ when the walk completes.

Currently wired:

- ~LOAD~ with the positional ~[encoding]~ argument under
  ~--strict~ (~enc-extension-used~), ~--autocad~ /
  ~--bricscad~ (~enc-foreign-dialect~), silent under
  ~--clautolisp~.
- ~OPEN~ encoding forms, all three routed:
  - positional ~"utf8"~ / ~"utf8-bom"~ — native under
    ~--autocad~; foreign under ~--bricscad~ / ~--clautolisp~;
    extension-used under ~--strict~.
  - positional ~"UTF-8"~ / ~"UTF-8-BOM"~ / ~"CP-NNNN"~ / … —
    native under ~--clautolisp~; foreign under ~--autocad~ /
    ~--bricscad~; extension-used under ~--strict~.
  - ~,ccs=ENC~ mode-suffix — native under ~--bricscad~;
    foreign under ~--autocad~ / ~--clautolisp~; extension-used
    under ~--strict~. The suffix is stripped from the
    mode-string before CL ~OPEN~ sees it.
- ~GETVAR~ / ~SETVAR~ on ~LISPSYS~ under every dialect except
  ~--autocad~ (the native dialect of ~LISPSYS~):
  - ~--strict~ -> ~enc-extension-used~.
  - ~--bricscad~ / ~--clautolisp~ -> ~enc-foreign-dialect~ with
    the dialect sub-tag.
- ~SETVAR "LISPSYS" <n>~ with ~n \notin {0,1,2}~ emits
  ~enc-lispsys-out-of-range~ regardless of dialect (the spec mandates
  the domain). The write proceeds — matching the vendor "permissive
  but warn" behaviour.
- ~OPEN~ with an encoding the active host can't natively express
  (e.g. ~"UTF-16-LE"~ under ~--autocad~) emits
  ~enc-unsupported-target~. Informational; the runtime still
  attempts the open.
- ~OPEN~ in WRITE direction with ~"ANSI"~ / ~"MBCS"~ emits
  ~enc-host-dependent~ (info-level): output resolves through
  the host's SYSCODEPAGE at I/O time and isn't portable across
  hosts. Reading under those encodings is silent.
- The internal SET-DRAWING-CODEPAGE wrapper (CL-level; hook for
  future drawing-load paths) emits ~enc-codepage-mismatch~ when
  the incoming DWGCODEPAGE canonical form differs from
  SYSCODEPAGE — catches the "Czech-authored drawing on a French
  host" failure mode before string decode time.
- ~%CANONICAL-CODEPAGE-STRING~ emits ~enc-unknown-codepage~ when
  asked to canonicalise a spelling not in the known table (typos,
  unsupported vendor aliases). The raw value passes through.

The full set of codes, the per-dialect dispatch table, and the
roadmap for the remaining hooks (~OPEN~, BricsCAD ~,ccs=~ parsing,
~DWGCODEPAGE~ mismatch detection at drawing-load time) is in
~issues/closed/encoding-dispatch.issue~.

* Building the Executable
From the ~clautolisp/~ subproject root:

#+BEGIN_EXAMPLE
make build-clautolisp-sbcl   # produces tools/clautolisp/bin/clautolisp-sbcl
make build-clautolisp-ccl    # produces tools/clautolisp/bin/clautolisp-ccl
#+END_EXAMPLE

Both targets reuse the ~read-autolisp~ build harness. The SBCL build
sets ~:save-runtime-options t~ so the saved core forwards every
command-line argument to ~clautolisp~ rather than letting SBCL
intercept ~--help~ or other runtime flags.

~make install~ also installs the Common Lisp sources and the libraries.
A native library that is missing — in practice the DWG codec, which only
~clautolisp/drawing-dwg~ needs — does *not* fail the install: everything
else is installed and a warning names the affected system and the
commands to add it later. Pass ~REQUIRE_NATIVE_LIBRARIES=1~ to turn that
warning back into a hard error, which is what you want when an
incomplete tree is a defect rather than a local inconvenience; the
release targets pass it, so a published tarball cannot silently ship
without its codec.

* Versioning
The version string is stored in
~clautolisp/tools/clautolisp/source/version.lisp~ as
~*version*~. The format is ~MAJOR.MINOR.DEVELOP~. The DEVELOP
counter is bumped on every change that touches clautolisp source
code; the running binary's ~--version~ output is therefore a stable
identifier of the build.

* clautolisp Extensions
The core builtin registry installed by ~clautolisp~ is a *superset*
of the operators listed in the local AutoLISP / Visual LISP
specification draft. The extras documented in this section are
convenience extensions and compatibility helpers that real-world
AutoLISP code relies on without going through the spec process.

Code that targets the strict shared standard (the AutoCAD/BricsCAD
intersection) MUST NOT depend on the operators below; tests
written against ~autolisp-test/harness/inventory.sexp~ are
intentionally restricted to the spec, and the inventory does not
list these names.

** Compositional list accessors (~Cxxxr~ / ~Cxxxxr~ family)
The local specification documents ~CAR~, ~CDR~ and ~CADR~. Beyond
those, ~clautolisp~ also installs:

- two-level :: ~CAAR~, ~CDAR~, ~CDDR~
- three-level :: ~CAAAR~, ~CAADR~, ~CADAR~, ~CADDR~, ~CDAAR~,
  ~CDADR~, ~CDDAR~, ~CDDDR~
- four-level :: ~CAAAAR~, ~CAAADR~, ~CAADAR~, ~CAADDR~, ~CADAAR~,
  ~CADADR~, ~CADDAR~, ~CADDDR~, ~CDAAAR~, ~CDAADR~, ~CDADAR~,
  ~CDADDR~, ~CDDAAR~, ~CDDADR~, ~CDDDAR~, ~CDDDDR~

Each composition delegates to ~CAR~ / ~CDR~ so a non-list argument
anywhere along the chain still surfaces a CAR-shaped or CDR-shaped
runtime error under the proper operator name.

#+BEGIN_SRC autolisp
$ clautolisp -x "(cadddr '(a b c d e))"
D
#+END_SRC

** ~ERROR~
~(error MESSAGE-OR-STRING ...)~ raises an AutoLISP-visible
runtime error with code ~:user-error~ and the supplied message.
Modeled after the common Visual LISP idiom of calling ~(error ...)~
to abort with a user-facing message, and catchable with
~vl-catch-all-apply~.

#+BEGIN_SRC autolisp
$ clautolisp -x "(vl-catch-all-error-message
                   (vl-catch-all-apply 'error '(\"oops\")))"
"oops"
#+END_SRC

** ~LCM~, ~LOGXOR~
Convenience numerics that complement the in-spec ~GCD~, ~LOGAND~ and
~LOGIOR~. ~LCM~ takes two or more integers and returns their least
common multiple; ~LOGXOR~ takes two or more integers and returns
their bitwise exclusive-or.

#+BEGIN_SRC autolisp
$ clautolisp -x "(lcm 4 6)"
12
$ clautolisp -x "(logxor 12 10)"
6
#+END_SRC

** ~VL-BT~ — full backtrace
The local specification reserves ~VL-BT~ as a Visual LISP backtrace
operator. ~clautolisp~ implements it as a real backtrace printer
rather than a stub: ~(vl-bt)~ prints the AutoLISP call stack at the
current evaluation point, one line per frame, most recent first.

The runtime tracks the stack through ~*autolisp-call-stack*~, a
dynamically-bound list of evaluator frames pushed by ~autolisp-eval~
and by every SUBR / USUBR call. Frame kinds are ~:eval~,
~:special-op~, ~:subr~ and ~:usubr~.

** ~VL-CATCH-ALL-ERROR-STACK~ — captured backtrace
~(vl-catch-all-error-stack OBJECT)~ is a clautolisp-only extension
companion to the standard ~vl-catch-all-error-message~. Given a
catch-all error object, it returns the AutoLISP call-stack snapshot
captured at the time the underlying ~autolisp-runtime-error~ was
raised. Each frame is a cons ~(KIND . PAYLOAD)~, where ~PAYLOAD~ is
either the form being evaluated (for ~:eval~ / ~:special-op~) or
the cons ~(NAME . ARGS)~ of the function call (for ~:subr~ /
~:usubr~).

This is the operator the ~autolisp-test~ harness calls to render an
AutoLISP backtrace inside a FAIL detail when a tested function
raises. AutoCAD and BricsCAD do not expose the captured stack, so
the harness gracefully falls back to message-only reporting on those
hosts.

#+BEGIN_SRC autolisp
$ clautolisp -x "(setq c (vl-catch-all-apply 'car '(7)))
                 (length (vl-catch-all-error-stack c))"
;; one or more frames captured at the time CAR was rejected
3
#+END_SRC

Code that needs to remain portable should test for the operator
before calling it:

#+BEGIN_SRC autolisp
(if (boundp 'vl-catch-all-error-stack)
    (vl-catch-all-error-stack object)
    nil)
#+END_SRC

** The ~CLAL-~ namespace (clautolisp-only helpers)
The four other sub-sections above (~Cxxxr~ accessors, ~ERROR~,
~LCM~/~LOGXOR~, ~VL-BT~/~VL-CATCH-ALL-ERROR-STACK~) cover
extensions that complete an established AutoCAD/BricsCAD idiom
without inventing a new one. From clautolisp 1.0.76 onward, a
second class of extensions ships under a reserved ~CLAL-~ prefix:
helpers that have *no* vendor counterpart and that we want to make
trivially distinguishable from any future Autodesk- or Bricsys-
documented name. Code that calls one of these functions is
explicitly opting into the clautolisp dialect.

The probing convention for portable code:

#+BEGIN_SRC autolisp
(if (boundp 'clal-sysvar-list)
    (clal-sysvar-list)
    ;; vendor fallback -- there isn't one; either accept that the
    ;; query is unavailable or fall back to the SETVAR command.
    nil)
#+END_SRC

*** ~CLAL-COMMAND-LOG~ -- the recorded ~command~ token sequences
~(clal-command-log)~ returns the token sequences that ~command~ /
~command-s~ / ~vl-cmdf~ have routed through the host's command
channel in this session, oldest first — a list of lists of strings,
exactly as sent (~""~ = RETURN, ~"\\"~ = PAUSE, points as
~"X,Y[,Z]"~). Under the MockHost, which has no command engine, this
log is the whole observable effect of a ~command~ call — the
deterministic assertion surface for headless test rigs. Raises
~:host-not-supported~ under a backend without a command log
(~--host null~).

#+BEGIN_SRC autolisp
$ clautolisp -x "(progn (command \"._LINE\" (list 0.0 0.0 0.0) (list 10.0 10.0 0.0) \"\") (print (clal-command-log)))"
(("._LINE" "0.0,0.0,0.0" "10.0,10.0,0.0" ""))
#+END_SRC

*** ~CLAL-SYSVAR-LIST~ -- list every sysvar known to the host
~(clal-sysvar-list)~ returns a list of strings: the sysvar names
the active host (mock or live) reports, sorted in case-sensitive
ASCII order. On a default ~MockHost~ the list has 1836 entries --
the same universe as the autolisp-spec §16 *System Variables*
catalogue.

#+BEGIN_SRC autolisp
$ clautolisp -x "(length (clal-sysvar-list))"
1836

$ clautolisp -x "(car (clal-sysvar-list))"
"3DCONVERSIONMODE"
#+END_SRC

*** ~CLAL-SYSVAR-APROPOS~ -- substring search over sysvar names
~(clal-sysvar-apropos PATTERN)~ returns the subset of
~(clal-sysvar-list)~ whose names contain ~PATTERN~ as a
case-insensitive substring. Useful at the REPL when you remember
"there's something with ~ANG~ in it" but not the exact name.

#+BEGIN_SRC autolisp
$ clautolisp -x "(clal-sysvar-apropos \"ANG\")"
("ANGBASE" "ANGDIR" "INPUTHISTORYMODE" ...)

$ clautolisp -x "(clal-sysvar-apropos \"ang\")"     ;; case-insensitive
("ANGBASE" "ANGDIR" "INPUTHISTORYMODE" ...)

$ clautolisp -x "(clal-sysvar-apropos \"ERRNO\")"
("ERRNO")

$ clautolisp -x "(length (clal-sysvar-apropos \"\"))"   ;; empty -> all
1836
#+END_SRC

A non-string PATTERN raises ~:invalid-argument~. A pattern that
matches nothing returns ~nil~.

*** ~CLAL-SYSTEM-CODEPAGE~ -- canonical SYSCODEPAGE
~(clal-system-codepage)~ wraps ~(getvar "SYSCODEPAGE")~ and returns
the canonical clautolisp codepage spelling. Vendor
~"ANSI_NNNN"~ and clautolisp ~"WINDOWS-NNNN"~ inputs both fold
onto ~"CP-NNNN"~; Unicode names (~"UTF-8"~, ~"ISO-8859-1"~,
~"US-ASCII"~) pass through; the pre-Phase-1 empty placeholder
becomes ~"ANSI"~.

#+BEGIN_SRC autolisp
LC_ALL=fr_FR.WINDOWS-1252 clautolisp -x "(clal-system-codepage)"
"CP-1252"

LC_ALL=en_US.UTF-8 clautolisp -x "(clal-system-codepage)"
"UTF-8"
#+END_SRC

*** ~CLAL-DRAWING-CODEPAGE~ -- canonical DWGCODEPAGE
~(clal-drawing-codepage)~ is the same canonicalisation applied to
~(getvar "DWGCODEPAGE")~. At launch ~DWGCODEPAGE~ defaults to
~SYSCODEPAGE~; loading a drawing that carries its own codepage
overrides it.

*** ~CLAL-CODEPAGE-MISMATCH-P~ -- defensive comparison
~(clal-codepage-mismatch-p)~ returns ~T~ when the canonical
~SYSCODEPAGE~ and ~DWGCODEPAGE~ differ, ~nil~ otherwise. Cheap
defensive check before loading drawing-authored text: a mismatch
means strings authored under one ANSI codepage may garble when
interpreted under another.

The comparison runs on the canonicalised form, so
~"ANSI_1252"~ vs ~"WINDOWS-1252"~ correctly registers as no
mismatch.

*** ~CLAL-FILE-ENCODING~ -- BOM-sniffing file-encoding probe
~(clal-file-encoding PATH)~ opens ~PATH~, reads the first four
bytes, and returns the canonical clautolisp encoding implied by
the byte-order mark:

| BOM bytes      | Returned string |
|----------------+-----------------|
| ~EF BB BF~     | ~"UTF-8-BOM"~   |
| ~FF FE~        | ~"UTF-16-LE"~   |
| ~FE FF~        | ~"UTF-16-BE"~   |
| ~FF FE 00 00~  | ~"UTF-32-LE"~   |
| ~00 00 FE FF~  | ~"UTF-32-BE"~   |
| no BOM         | ~"ANSI"~        |

(UTF-32-LE / UTF-16-LE share the same two leading bytes;
~CLAL-FILE-ENCODING~ checks UTF-32 first so the two-byte UTF-16
prefix doesn't mask a four-byte UTF-32 BOM.)

Mirrors BricsCAD's ~VLE-FILE-ENCODING~ but preserves the
UTF-8-BOM / plain-UTF-8 distinction the BricsCAD function flattens.
A nonexistent ~PATH~ returns ~nil~ and sets ~ERRNO~ 73, matching
~LOAD~'s missing-file behaviour.

#+BEGIN_SRC autolisp
$ clautolisp -x "(clal-file-encoding \"~/.autolisp\")"
"ANSI"
#+END_SRC

*** ~CLAL-SEDIT~ -- the structural editor
~(clal-sedit [OBJECT])~ opens the *sedit* S-expression editor
(see /sedit and the aldo form navigator/) and returns the edited
object. With no argument it starts a stand-alone form at ~nil~; a
symbol recalls its recorded ~defun~/~setq~; a string is a file or
directory path; any other value is edited as a sexp. The initial and
final forms are left in ~*clal-sedit-initial-form*~ /
~*clal-sedit-last-result*~.

*** ~CLAL-CLIPBOARD-*~ -- the editor clipboard
~(clal-clipboard-copy-sexp OBJ)~ / ~(clal-clipboard-paste-sexp)~ copy
and paste a form through the in-process and system clipboards;
~(clal-clipboard-put-text S)~ / ~(clal-clipboard-get-text)~ are the
plain-text forms. Paste never evaluates its input. The system
clipboard auto-selects an X11 / Wayland / macOS / Windows / OSC 52
backend and degrades to in-process only
(=clautolisp/documentation/clipboard-interface.org=).

*** ~CLAL-NAV-*~ / ~CLAL-BREAK~ -- the debugger surface
~(clal-break)~ and ~(clal-invoke-debugger [MSG])~ enter aldo
programmatically; ~(clal-nav-function 'NAME)~,
~(clal-nav-file PATH [LINE])~ and ~(clal-nav-directory [PATH])~ open
the form navigator on a function, a file, or a directory *before* the
code runs — ~b~ on a form of a file that is *not loaded yet* records a
*virtual breakpoint* (listed by ~lb~ as ~vbN~, removed by
~delete vbN~), kept relative to its ~defun~ so it survives the file
being edited above it, and armed automatically when the file is loaded
and the function instrumented; the directory browser's listing obeys
the ~directory-listing~ setting (~short~ / ~long~ / ~column~, an
ls -C-style grid) and ~directory-window~ (context lines around the
selection). ~(clal-select-file PATH LINE)~ points ~list source~ at a
location; ~(clal-define-command "INTERACTOR" NAMES FN [DOC])~ registers
a custom user command of the named interactor —
~(clal-list-interactor-names)~ lists the valid names (~"ALDO"~,
~"NAVI"~, ~"LAVI"~, ~"INSPECT"~, ~"AUTOLISP"~) —
and ~(clal-define-debugger-command NAMES FN [DOC])~ is its deprecated
ALDO-only equivalent. See /Debugger/ above.

*** ~CLAL-COMMON-LISP~ / ~CLAL-BACK~ -- drop into a live Common Lisp REPL
The developer escape hatch out of AutoLISP and into the Common Lisp
image that is running it. It is *deliberately not available by
default*: the AutoLISP symbol ~clal-common-lisp~ is unbound until you
set the read/write sysvar ~CLAUTOLISPDROP~ (default ~0~) to a non-zero
value, which shadows it with the builtin — saving any binding of your
own, and restoring it when you set the sysvar back to ~0~. An AutoLISP
program therefore cannot fall into a CL REPL by accident.

#+BEGIN_SRC autolisp
_$ (setvar "CLAUTOLISPDROP" 1)
_$ (clal-common-lisp)                  ; no argument: interactive REPL
CL-USER> (lisp-implementation-type)
"SBCL"
CL-USER> (clal-back 42)                ; leave, yielding 42 to AutoLISP
42
_$ (clal-common-lisp "(+ 1 2)")        ; a string: read one form, evaluate it
3
#+END_SRC

With no argument it runs an interactive REPL reading in
~COMMON-LISP-USER~ — leave it with ~(clal-back [VALUE])~, which returns
~VALUE~ (default nil) as the value of the ~clal-common-lisp~ call, or
with end of input. With a string argument it reads *one* CL form from
the string and evaluates it; with any other AutoLISP value it converts
the value structurally into a CL form and evaluates that.

Values cross the boundary by conversion, and the conversion is where the
surprises live: integers, reals and nil pass through; strings unwrap and
re-wrap; AutoLISP symbols are *re-read* with the CL reader under the
current ~*package*~ and ~*readtable*~, so ~'(foo cl:car :kw)~ arrives as
~(CL-USER::FOO CL:CAR :KW)~. Coming back, an integer outside the
AutoLISP range, a circular structure, or an object with no AutoLISP
counterpart is a CL error rather than a silently truncated value.

An unhandled CL error is governed by ~common-lisp-user::*clal-on-error*~:
~:debug~ (the default) enters the native CL debugger at the point of the
error, ~:error~ signals a catchable AutoLISP error that
~vl-catch-all-apply~ can see, ~:ignore~ yields AutoLISP nil, and any
other value is returned as the result. Set it to ~:error~ when the drop
is used from a script that must not stop at a debugger prompt.

*** ~CLAL-OPTIMIZE~ / ~CLAL-OPTIMIZATION~ -- optimization qualities
~(clal-optimization)~ returns the current qualities as
~((DEBUG n) (SPACE n) (SPEED n))~; ~(clal-optimize QUALITIES)~ sets them
and returns the new set. Each element of ~QUALITIES~ is either a bare
quality symbol — which means level 3 — or a ~(SYMBOL LEVEL)~ pair, and
any quality you do not mention keeps its current level.

A function has two forks, and the levels decide which of them exist and
which are compiled. What matters is not each quality on its own but the
levels, and — for the instrumented fork — how ~DEBUG~ and ~SPACE~ compare:

| fork                            | present when       | compiled when |
|---------------------------------+--------------------+---------------|
| the ordinary one                | always             | ~SPEED~ >= 1  |
| the instrumented one (debugging)| ~DEBUG~ >= ~SPACE~ | ~SPEED~ >= 2  |

So ~SPACE~ is not a switch you turn on; it is what you weigh ~DEBUG~
against. ~(DEBUG 3) (SPACE 3)~ says the two matter equally and keeps the
instrumented fork, which is what breakpoints and stepping ride on;
~(DEBUG 0) (SPACE 3)~ says size wins and drops it, and the debugger can
then no longer stop inside your functions.

~SPEED~ has one more step. At 1 and 2 a function is compiled once it has
proved *hot* — called enough times to earn the compilation — so you pay
nothing for functions that a file defines and never calls. At 3 it is
compiled at *definition* instead. That is not just sooner: compiling a
whole file as one unit is what allows optimizations across function
boundaries, which compiling one function at a time cannot do.

The default is ~((DEBUG 3) (SPACE 0) (SPEED 2))~ — debugging matters
most, speed next, size not at all.

#+BEGIN_SRC autolisp
_$ (clal-optimize '((debug 0) (space 3)))   ; run plain, no instrumentation
((DEBUG 0) (SPACE 3) (SPEED 2))
_$ (clal-optimize '((speed 3)))             ; and compile at load time
((DEBUG 0) (SPACE 3) (SPEED 3))
_$ (clal-optimize '((speed 0)))             ; interpret everything
((DEBUG 0) (SPACE 3) (SPEED 0))
#+END_SRC

Before release 2.0.8 ~SPEED~ was pinned at 0 and setting it was silently
ineffective, because there was no compiler for it to reach. If you have
code that reads ~(clal-optimization)~ back and expects a ~SPEED~ of 0,
that expectation no longer holds.

*** ~CLAL-COMPILE-FILE~ / ~CLAL-COMPILE-SYSTEM~ -- compile an application
~(clal-compile-file SOURCE [OUTPUT])~ compiles one AutoLISP source file
into a ~.lap~ compiled application; ~OUTPUT~ defaults to the source name
with type ~.lap~, beside the source.
~(clal-compile-system OUTPUT SOURCES)~ compiles a list of sources into a
single ~.lap~. Both compile; neither loads. Load the result with ~load~
like any other file.

**** What a ~.lap~ is, and what it is not
A ~.lap~ is a *native host FASL, renamed*. It loads into a running
clautolisp alongside other applications, in any order — which is what an
AutoLISP application has to be, and why it is not a saved Lisp image.

Two consequences, both deliberate:

- A ~.lap~ built by an SBCL clautolisp will *not* load in a CCL one, or
  the reverse.
- A ~.lap~ is not promised to load in a different clautolisp version.

A portable format would mean inventing a byte-code FASL, and that trade
is not worth making today. Keep builds for different hosts and versions
in *different directories*, exactly as the binary releases are kept —
the file name carries nothing about which build made it. Loading a
~.lap~ that does not match says so, naming the reason.

**** Why the system form exists
Compiling several sources together puts them through *one* host
compilation, so literals can be shared across the whole application and a
function defined in a later source and called from an earlier one
resolves without a warning at each forward reference. And it ships as one
file rather than one per source.

#+BEGIN_SRC autolisp
_$ (clal-compile-file "geometry.lsp")
T
_$ (load "geometry.lap")

_$ (clal-compile-system "myapp.lap" '("geometry.lsp" "commands.lsp"))
T
#+END_SRC

Functions arriving from a ~.lap~ come already compiled — they never pay
the hotness threshold again — and they keep their source body, so they
stay debuggable.

~vlisp-compile~ is the vendor spelling of the same thing: it writes a
~.lap~ where AutoCAD writes ~.fas~ and BricsCAD writes ~.des~, and
returns ~T~ when the file was written. Its ~mode~ argument is ignored,
as in BricsCAD — an *unknown* mode signals, so a typo in a build script
is not silently absorbed.

*** ~CLAL-COMPILE~ -- build an applicable function object
~(clal-compile NAME LAMBDA-EXPRESSION)~ compiles a
~(lambda LAMBDA-LIST . BODY)~ form into an applicable function object,
weaving the instrumented fork when the current ~DEBUG~ quality is above
0. ~NAME~ is nil for an anonymous function, or a symbol naming it.
Anything that is not a ~lambda~ form is a ~:bad-argument~ error.

*** ~CLAL-MODULE-EXTENSION~ -- the host's packaged-artefact extensions
~(clal-module-extension KIND)~ returns, as a string with a leading dot,
the file extension clautolisp uses for a packaged artefact — so
portability layers can *ask* instead of hard-coding a guess. ~KIND~ is
matched case-insensitively:

- ~"compiled-app"~ :: ~".lap"~ ("Lisp APplication"), the clautolisp
  analogue of AutoCAD's ~.vlx~ and BricsCAD's ~.des~. The name is
  clautolisp's own.
- ~"native-module"~ :: the host operating system's shared-library
  extension — ~".dll"~ on Windows, ~".dylib"~ on macOS, ~".so"~
  elsewhere. This is the ~.arx~ / ~.brx~ slot; a clautolisp native
  module is a shared library loaded by the host Common Lisp, so unlike
  the vendors' fixed extensions this one is OS-dependent.

The full normative entries for these functions live in
~autolisp-spec~ §16 *clautolisp Extensions*; this section is a
quick-reference summary.
