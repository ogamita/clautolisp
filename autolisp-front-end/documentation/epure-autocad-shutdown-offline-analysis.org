#+TITLE: AutoCAD EPURE shutdown: offline exception and heap analysis
#+DATE: 2026-11-03

* Initial termination dump: result and attribution boundary
The available exit dump localizes an access violation to Windows heap
coalescing while MFC destroys its OLE module state. The specific released
member is AFX_MODULE_STATE::m_strUnregisterList, not a Lisp request or a
COM document close operation. This is consistent with damaged heap metadata;
it does not identify the earlier writer, allocator mismatch or double free.
No specific proprietary EPURE component can yet be blamed from this dump.

The independent clean-profile control still establishes the broader trigger:
AutoCAD with an unchanged initial drawing exits zero under its unnamed
profile, but abnormally under its installed EPURE profile, without ALFE.
The dump below comes from a DIFFERENT private diagnostic invocation. Do not
represent it as the dump of that independent control or as qualification
of either MR's final head.

* Why the exit code alone was insufficient
The existing ProcDump log records, in order:
- E06D7363, boost::interprocess::interprocess_exception;
- C0000005, ACCESS_VIOLATION;
- process exit 0x012EBABE.
The earlier C++ exception is not established as the heap corruption cause.
This particular BABE exit accompanies an access violation. That does not
classify every BABE variant, and none is whitelisted by the lifecycle gate.
The receipt's empty WER/default-CrashDumps arrays do not contradict the
separately captured dump in the diagnostic's private crash-data directory.

* Recovering the active exception
The exit minidump has no ExceptionStream. Its final ThreadList context is
in NtTerminateProcess, reached through RtlpWaitOnCriticalSection and CLR's
exception handling path. Raw module-looking stack values are NOT a backtrace.

Reconstructing x64 frames using each matching PE's .pdata/UNWIND_INFO,
including chained unwind records, reaches RtlpExecuteHandlerForException,
RtlDispatchException and KiUserExceptionDispatcher. The dispatcher's stack
points to a still-present original AMD64 CONTEXT (flags 0x10005F) and
EXCEPTION_RECORD. Thus the recovered context belongs to the active dispatch,
not merely to an arbitrary stale address found by scanning.

The record contains C0000005, a read operation, address zero, with exception
address ntdll.dll+0x9750. The saved original R15 is zero. The instruction at
that RVA is mov rax,[r15], exactly matching the recorded null read.

From the original exception context, x64 unwind metadata yields:

6. ucrtbase.dll+0x49C85 / +0x498A7 / +0x4985D: on-exit callback execution.
7. mfc140u.dll+0x2C395D / +0x2C3A7D: CRT DLL detach dispatch.

The recovered nonvolatile RBX in frame 5 points to MFC RVA 0x3D18B0.
Microsoft's private data symbol names it _afxOleModuleState. Its type is
AFX_MODULE_STATE. The destructor releases the CString at object+0x68;
PDB type information names offset 104 m_strUnregisterList. Disassembly
shows the CString reference-count decrement and virtual string-manager free
immediately before return address +0x137E62.

The released CString data pointer and the heap node being coalesced are
outside the dump's captured MemoryList ranges. There is no allocation/free
history. The original corrupting write cannot be recovered from these data.

* EPURE candidates and exclusions
The unloaded-module stream records DOSLib24x64.arx and SNCFOutilsARX64.arx
already unloaded. This excludes a direct instruction fault inside those
modules at the captured point; it does NOT exclude an earlier heap overwrite.
FLSNCFIG.dll addresses occur in raw stack memory but are not frames of the
reconstructed original exception path. Mere presence is not attribution.
The copied FLSNCFIG.dll has no dynamic MFC import and no literal matching
the recorded boost exception type. Neither observation rules it out entirely.
The accessible SCHMS EPURELIB sources show no direct unsafe/DllImport hook
into these components; this is not an audit of unavailable EPURE sources.

The separately proven USERPROFILE stack-buffer failure in SNCFOutilsARX64.arx
is a startup C0000409, not evidence that this later heap failure shares its
cause. ALFE's known-folder environment safeguard remains warranted.

* What is needed to identify the originating component
The existing mini dump lacks the relevant heap blocks and allocation/free
stacks. A full dump at the FIRST access violation would allow inspection of
heap neighbors; allocation instrumentation, or a controlled same-environment
component bisect, is needed to identify an earlier writer/free operation.
Those would be separate native experiments, not conclusions from this file.
No new native experiment was launched here. Keep both MRs unmerged and the
native lifecycle gate blocking until the shutdown defect is resolved.

** Original failure reproduced with full memory
ExceptionStream contains C0000005, read from address zero, at ntdll+9750.
The direct saved R15 is zero, matching mov rax,[r15]. Unwind metadata again
leads through RtlpCoalesceFreeBlocks -> RtlpFreeHeap -> RtlFreeHeap ->
_free_base -> AFX_MODULE_STATE destructor+82, releasing the CString in
_afxOleModuleState.m_strUnregisterList during MFC process detach.

The full memory snapshot now permits inspection of the two adjacent blocks:
- The CString header remains consistent with length zero and allocation
  length 4096 characters. It is being released normally by its MFC manager.
- Immediately before its heap entry is a 0x1F0-byte free block: 16-byte heap
  header plus 480-byte former user allocation. Its free-list Flink points
  to a valid bucket/list structure, but its Blink is zero. Reading that
  null Blink produces the captured access violation.
- Its remaining payload is consistent with _AFX_THREAD_STATE (Microsoft
  PDB type size 480): m_szTempClassName at offset 216 contains an Afx:...
  generated window-class name, matching the type's precise inline layout.
  m_pModuleState is at offset 8 of that former object, exactly overlapping
  Blink after the allocator reuses the object's first two words as links.
- A later write of a null module state through a stale thread-state pointer
  would therefore explain the precise corruption. This is a strong
  use-after-free hypothesis, not a captured write instruction or proof of
  the identity of its caller.

The complete snapshot has one remaining thread. AutoCAD still has a global
reference to this former object; static references found in acad.exe use its
current-message fields. A retained pointer is not proof of a post-free write.
No proprietary EPURE instruction is on the reconstructed failing stack.
The available heap is not recording allocation/free backtraces, so this dump
does not identify which call first invalidated the block or later wrote it.
Do not convert this hypothesis into blame against SNCFOutilsARX64.arx,
FLSNCFIG.dll, EPURELIB, AutoCAD or MFC itself without observing the operation.

** What the first protected exception establishes
The read fault is VCRUNTIME140.dll+0x10B36, memcpy_avx_ermsb_amd+0x126,
not the previous ntdll+9750 heap coalescing fault. The instruction is
movdqu xmm1,[rdx], with R8=16 bytes. Source starts eight bytes before a
protected page; this 16-byte load crosses into that page.

The source lies eight bytes inside an allocation requested as 14 bytes.
Its DPH_BLOCK_INFORMATION allocation stamp is ABCDBBBB (allocated), not
a freed-block stamp. Thus only six requested bytes remain at the source,
followed by two fill bytes and the protected page. This is an allocated
buffer over-read, not the previously hypothesized freed 480-byte thread state.

Matching PE unwind tables reconstruct memcpy -> accore+78E5D ->
accore+9832E -> accore+98017 -> accore+2078BC, followed by further accore
initialization frames, acad+4F765, MFC startup and acad's entry path.
The accore helpers construct a wide std::basic_string using an explicit
count of eight characters, leading to a 16-byte copy from that short source.
The source allocation header is present; its allocation backtrace is not
stored in that header. Autodesk's matching accore PDB request returned 404,
so internal function names are not asserted from nearest exports.
No proprietary EPURE native frame appears in the reconstructed stack.
That does not exclude an application/profile input trigger, and does not
establish a relationship with the earlier MFC shutdown corruption.

A separate open issue records this startup obstacle. Do not relabel this
capture as the writer of the original heap corruption or as a clean exit.

** What follows, and what is not fixed

The immediate fault and preceding free are proven. The component-level
attribution to Traverses is very strongly supported by independent static
and dynamic evidence, with the CLR-sharing limitations above. The lifecycle
violation is freeing MFC thread state while an outer AutoCAD/MFC state guard
still retains its pointer and will restore through it.

The next source-level review should inspect Traverses Attach/Detach ownership
and its On_kUnloadAppMsg order against the AutoCAD2022 SDK and the lifetime
of the last active AFX_MAINTAIN_STATE2. There are no accessible Traverses
sources here. Removing Detach, moving it blindly to DllMain, accepting
C0000005, or patching ALFE to disguise the crash is not a validated remedy.
No source fix, binary patch, new release or merge was performed.

This evidence does not attribute the separate ARX missing-USERPROFILE startup
failure or the global-PageHeap 14-byte startup over-read to Traverses, nor
does it explain an unrelated BricsCAD crash by analogy.
