* Introduction

=alfe(1)= is the unified command-line front-end for AutoLISP. It
drives three backends behind a single command-line shape:

- =clautolisp= — an in-process AutoLISP evaluator that ships with
  alfe. No CAD required. The default backend.
- =bricscad= — BricsCAD V26+, via batch (=-b run.scr=) or COM
  /AppleScript automation. On MS-Windows, =--mode batch= launches
  BricsCAD with its main frame window hidden (the =/Automation=
  startup switch); this is just a hidden-UI batch run and does *not*
  select the COM =--mode automation= backend.
- =autocad= — AutoCAD 2026+, via =accoreconsole= batch or COM
  automation (MS-Windows only).

The same =-x EXPR=, =-l FILE=, =--dialect NAME= and =--host NAME=
options work against every backend. Programs written for alfe run
unchanged whether you point them at the local clautolisp engine
or at a real CAD session.

* Installation

The build target produces two binaries: =alfe-sbcl= (preferred,
faster startup) and =alfe-ccl= (Clozure CL backup, when SBCL is
unavailable). The =install= rule places them under
=$(PREFIX)/bin/= along with a wrapper =alfe= that resolves to one
or the other:

#+begin_src sh
cd autolisp-front-end
make build
sudo make install PREFIX=/opt/local
#+end_src

After install:

#+begin_src sh
alfe --help                    # full option reference
alfe -x "(print (+ 1 2))"      # one-shot eval, prints "3" then exits
alfe -x "(+ 1 2)"              # silent — see "Action output semantics" below
alfe -l script.lsp             # load a file, default backend
alfe                           # interactive REPL, default backend
#+end_src

** The CAD runtime files

The AutoCAD and BricsCAD backends load two AutoLISP files into the CAD:
=autolisp-bootstrap.lsp= and =autolisp-remote-io.lsp=. =make install=
puts them in =$(PREFIX)/share/alfe/runtime/=. A release archive has the
same tree, and can be unpacked under any directory.

alfe finds them from where its own executable is, when it runs. This
works whether the binary is =$(PREFIX)/bin/alfe-sbcl= or sits under
=$(PREFIX)/libexec/= behind the =bin/alfe= launcher, and through a
symbolic link. The current directory plays no part. Neither does the
directory alfe was built in. The search order is:

1. =$ALFE_BOOTSTRAP_LSP= / =$ALFE_RUNTIME_LSP=, when they name an
   existing file;
2. =share/alfe/runtime/= under the installation prefix;
3. the copies in the source tree, for a development build;
4. =/opt/local=, =/usr/local= and =/usr= (=share/alfe/runtime/=).

If either file cannot be found, the CAD is not started. alfe exits
with status 69 (=EX_UNAVAILABLE=) and lists every path it tried (see /Troubleshooting/).

** The installed plug-ins

The =install= rule also places the plug-ins that ship with alfe —
=epure= and =epuree= — under =$(PREFIX)/share/clautolisp/plug-in/= and
compiles them with the alfe it has just installed. =alfe --list-plugins=
shows what alfe finds; see [[#plugins][Plug-ins]].

** Backend flags

The =--clautolisp= / =--bricscad= / =--autocad= flags select a
specific backend; absent a flag, the in-process clautolisp engine
is used (see [[#backend-selection][Backend selection]]).

* Backend selection
:PROPERTIES:
:CUSTOM_ID: backend-selection
:END:

When no backend flag is given, alfe defaults to the =clautolisp=
in-process engine. This is a change from the historical
auto-detection: CAD backends are now NEVER selected automatically
— they require an explicit =--autocad= / =--bricscad= flag (or
an environment override).

** Algorithm

#+begin_example
if --bricscad, --autocad or --clautolisp is explicit:
    use that backend
else if $ALFE_BACKEND_OVERRIDE is set:
    use that backend
else if $AUTOLISP_BACKEND is set:
    use that backend (legacy alias)
else:
    backend = clautolisp     ; default on every system
#+end_example

** One engine, two transports
:PROPERTIES:
:CUSTOM_ID: one-engine-two-transports
:END:

=--clautolisp= runs the clautolisp engine one of two ways:
=--backend direct= (the default) embeds it in alfe, =--backend
subprocess= runs the installed =clautolisp= executable as a child. They
are two transports for the same engine, not two products: choosing the
subprocess for isolation must not change what a program sees. So, for
every option alfe accepts with =--clautolisp=:

- the same features are present. alfe's image carries every part of the
  engine the =clautolisp= program has that a program can observe -- in
  particular the DWG codec, so =--dwg FILE.dwg= opens the drawing in the
  default direct variant as it does in the subprocess one (the native
  LibreDWG library is still loaded only when a DWG is first read or
  written, so an alfe without it starts normally), and the AutoLISP
  compiler, so the default optimization qualities compile as they do in
  =clautolisp=;
- user code sees the same values. The child is handed alfe's own
  =*AUTOLISP-...*= values (with =--front-end-bindings=), so
  =*AUTOLISP-FRONTEND*= is =ALFE=, =*AUTOLISP-VERSION*= is alfe's,
  =*AUTOLISP-ACTIONS*= lists your actions, and =(getvar "PROGRAM")= is
  =alfe= in both. Only =*AUTOLISP-PROCESS*= tells them apart (=DIRECT= /
  =SUBPROCESS=), which is its purpose;
- the diagnostics and the exit status are the same (see /Exit status/): a
  runtime error is reported in the engine's words with its AutoLISP
  backtrace (exit 1), =(exit N)=, =(quit N)= and =autolisp-set-status= give
  exit status =N=, a =-l= file that cannot be opened gives 66
  (=EX_NOINPUT=), a source the reader refuses 65 (=EX_DATAERR=), a drawing
  that cannot be opened is =--dwg: cannot open the drawing ...= with 66
  (missing) or 65 (not a drawing), and =--main FN= runs as =-x "(FN)"= does.

Some of what =clautolisp= offers is not the engine but the =clautolisp=
/program/ built around it: its REPL (interactors, comma commands, the aldo
debugger an error breaks into, the Control-C policy), its recorder
(=--dribble=), its full-screen and GUI DCL renderers, and the cadtui host.
alfe does not carry a second, poorer copy of them. A run that needs one of
them /is/ the program's, so alfe runs it as the child by itself -- the same
command line, the same program, hence the same behaviour whether or not you
wrote =--backend subprocess=:

| The run asks for                                          | Without =--backend=, or =--backend subprocess= | =--backend direct=                |
|-----------------------------------------------------------+------------------------------------------------+-----------------------------------|
| an interactive session: =-i=, or no =-l= / =-x= / =--main= / FILE (a bare =alfe=) | the clautolisp REPL, in the child | usage error (exit 64)|
| =--dribble=, =--dribble=FILE=                              | the child records its REPL (a batch run has no REPL: nothing is recorded, as with =clautolisp=) | usage error (exit 64)|
| =--dcl ncurses=, =--dcl gui=                               | the child, on alfe's terminal                  | usage error (exit 64)             |
| =--host cadtui=                                           | the child                                      | usage error (exit 64)             |

=--dcl tui= and =--dcl auto= (the default) stay in-process: both variants
show a batch run's dialogs with the line renderer (the child's captured
standard output is not a terminal, so its =auto= picks the line form too).
The child reads alfe's standard input in every run, as the in-process
engine does, so =printf '(princ 42)\n' | alfe -i= and a =GETSTRING= in a
batch run see the same input under both variants.

Three more things are the same in both variants. A plug-in with
=:pre-action= / =:post-action= hooks watches the run without changing it:
the child is one process for the whole plan that stops at each action
boundary until alfe has called the hooks (alfe starts it with
=--front-end-action-boundaries DIR=, a directory of small marker files
through which the two wait for each other; see /Plug-ins/), so a variable
set by one =-x= is there for the next, as in-process. =--quit= ends the
plan: =alfe -x A --quit -x B= never runs =B=, and =alfe --quit= runs
nothing (it does not start the child's REPL). =(clal-dribble FILE)= called
from a =-l= / =-x= action records the run into FILE in both, the last,
unterminated line included.

The treatment of every option is written down once, in
=alfe.backend.clautolisp:*clautolisp-option-contract*=, and the test
suite fails when an option alfe accepts is missing from it; a table of
runs is executed under both variants and their output, diagnostics, exit
status and written files compared -- the REPL, dribble and DCL runs
included (=--host cadtui=, =-i=, =--dribble= and =--dcl= are the
=:program= entries of that contract).

** Why not auto-detect?

A host with both BricsCAD and AutoCAD installed got
order-dependent results from the historical auto-detect (whichever
backend's =DETECT= method was probed first won). With the new
rule, =alfe= with no flags always means "talk to the in-process
clautolisp engine" — no probing, no surprises, no dependency on
CAD installation state.

** Pinning a default backend per shell

Users who want a CAD backend selected by default can set
=$ALFE_BACKEND_OVERRIDE= once in their shell init:

#+begin_src sh
# ~/.zshrc or ~/.bashrc
export ALFE_BACKEND_OVERRIDE=bricscad
#+end_src

Explicit flags still win — =alfe --clautolisp -x "(+ 1 2)"= runs
under clautolisp even with the override set.

** Selecting a specific CAD install

=--clautolisp= / =--bricscad= / =--autocad= pick the *latest* install
of a backend. When several versions or localisations are present and
you need a particular one, use =--cad DENOTATION=.

=alfe --list-cad-programs= scans the host and prints every installed
CAD with its canonical denotation:

#+begin_example
acad-2026                /Applications/Autodesk/AutoCAD 2026/…/MacOS/AutoCAD
accoreconsole-2026       /Applications/Autodesk/AutoCAD 2026/…/AcCoreConsole
bricscad-v26             /Applications/BricsCAD V26.app/Contents/MacOS/bricscad
clautolisp               (embedded in alfe)
#+end_example

Denotation grammar:

| Denotation                | Selects                                             |
|---------------------------+-----------------------------------------------------|
| =acad-2026=               | that exact AutoCAD (GUI =acad=)                     |
| =accoreconsole-2022=      | that exact =accoreconsole=                          |
| =dwgtrueview-2024=        | the =accoreconsole= of the DWG TrueView viewer (see below) |
| =bricscad-v25-fr_FR=      | that exact BricsCAD version + locale                |
| =bricscad-v25=            | V25 of any locale (host locale preference breaks ties) |
| =acad= / =bricscad=       | the latest of that kind                             |
| =autocad= / =autocad-2022= | =acad= or =accoreconsole= per =--mode= (batch → accoreconsole, else acad) |
| =clautolisp=              | the embedded engine                                 |

The free DWG TrueView viewer also ships an =accoreconsole.exe=. It is
not AutoCAD — it is read-only, and its configuration file in Program
Files makes it abort on launch for a normal user — so it is listed
under its own name, =dwgtrueview-YYYY=, and =accoreconsole= / =autocad=
never select it, even when it is newer than the installed AutoCAD.
Name it explicitly (=--cad dwgtrueview=) to run it anyway.

*** Which AutoCAD automation actually talks to

Choosing =acad.exe= does not by itself choose the AutoCAD that answers.
=--mode automation= runs a COM bridge (=cscript=), and Windows resolves
the *ProgID* it asks for through the registry — to whatever release that
registration names. The unversioned =AutoCAD.Application= belongs to
whichever AutoCAD registered it last, which need not be the one you
selected, and on a damaged installation it may resolve to a CLSID that
cannot start anything at all.

So an explicitly selected release asks for *its own* ProgID:

| Selection                          | COM server asked for                          |
|------------------------------------+-----------------------------------------------|
| =--cad autocad-2022 --mode automation= | =AutoCAD.Application.24.1= (AutoCAD 2022's)   |
| =--cad autocad= / =--autocad=      | the discovered install's versioned ProgID when it is registered, else =AutoCAD.Application= |
| =$AUTOCAD_PROGID= set              | exactly that, unchanged                       |
| =--mode batch=                     | none: =accoreconsole= needs no COM at all     |

Only =--cad autocad-2022= (or =acad-2022=) *names* a release. =--cad
autocad= asks for the latest one, so the release is alfe's own choice
and never a reason to refuse the run.

alfe confirms the registration before using it (a CLSID *and* a readable
=LocalServer32=). When you named the release and its COM server is not
registered, alfe stops and says so — it will not quietly fall back to the
generic ProgID and drive a different AutoCAD. See /Troubleshooting/.

When alfe cannot read the registry *at all* — no =reg.exe=, a locked-down
host — it says so and uses the named release's own ProgID unverified,
rather than refusing: no answer is not the same as a negative answer.

The same ProgID is used to attach, to create, and to quit at the end of
the run, so alfe never closes an instance of another release.

*** alfe's workdir in AutoCAD's TRUSTEDPATHS

An AutoCAD with =SECURELOAD= set to 2 loads executable files *only* from
the folders listed in =TRUSTEDPATHS=. alfe's first act on the CAD is to
load =run-common.lsp= from its fresh temporary workdir, and every =-x=
form travels through =protocol\alfe-eval.lsp= in the same workdir. Such an
AutoCAD would refuse all of it, and the run would never reach READY.

So, on MS-Windows and for a real launch only (not =--print-command=),
alfe adds one entry, =<workdir>\...=, to =TRUSTEDPATHS= *before*
starting AutoCAD. The trailing =\...= trusts the subfolders too. It
removes that entry again when the run ends. Setting it from AutoLISP would
be too late, because the first load is already the refused one.

- *Where.* In *every* AutoCAD profile of the current user:
  =HKCU\Software\Autodesk\AutoCAD\<release>\<product>\Profiles\<profile>\Variables=,
  value =TRUSTEDPATHS=. Every profile, because "the current profile" is not
  one answer. On the project's runner, the =Profiles= key named one profile
  as the default while =CPROFILE= named another, and AutoCAD and
  accoreconsole choose between them on their own terms.
- *What is removed.* Exactly alfe's entry, from whatever the value is *at
  the end*. Anything you, or another alfe run, added meanwhile stays. The
  value's type (=REG_SZ= or =REG_EXPAND_SZ=) is kept, and so is every
  character: alfe reads and writes through PowerShell's registry API, not
  through =reg.exe='s console codepage. That matters because the workdir
  lives under =%TEMP%=, and so under your user name. alfe runs
  =powershell -NoProfile -NonInteractive -EncodedCommand <base64>=: the
  script travels base64-encoded and strings travel as character codes, so
  no quoting or codepage can alter them. A site whose policy forbids
  PowerShell for the user gets no trust entry: alfe then finds no profile
  (visible with =--debug=) and runs as it did before this existed.
- *When.* After the AutoCAD alfe created has quit. AutoCAD saves its
  profile, =TRUSTEDPATHS= included, when it exits, so an entry removed
  while it still ran would be written back.
- *A killed run* cannot remove its entry. Two records let the next run do
  it for you:
  - =<temp>/alfe-trustedpaths.txt= names each entry with the process id of
    the alfe that added it.
  - Any entry naming an alfe workdir (=alfe-autocad-<pid>-<tag>=) whose
    alfe is no longer running is removed as well.

  A process whose state cannot be determined counts as running. alfe never
  takes away another run's trust on a guess.

Nothing is changed when no AutoCAD profile exists. If a write is refused,
alfe warns that a =SECURELOAD=2= AutoCAD will refuse its runtime, and
carries on. With =SECURELOAD= at 0 or 1, the defaults, the entry is
harmless and unnecessary.

BricsCAD keeps neither =TRUSTEDPATHS= nor =SECURELOAD= in the registry
(both are "not saved" there, and the registry of the project's runner has
neither). alfe's BricsCAD launch script sets =SECURELOAD= to 0 for the
session instead.

*** When alfe is killed before it can quit AutoCAD

alfe quits the AutoCAD it created — but only if it reaches the end of
the run. Killed, or its CI job cancelled, it never gets there, and the
=acad.exe= that COM started belongs to the COM service rather than to
alfe, so killing alfe's process tree does not reach it either.

So each run writes down what it creates, in
=<temp>/alfe-created-cad.txt=: the process id and its creation time, one
line per instance. The file is outside the workdir on purpose — the
workdir goes away with the run, and the run this serves is the one that
cleaned nothing up.

=scripts/sweep-orphaned-cad.ps1= reads that file and ends those
instances, and only those: both the process id *and* the creation time
must still match, because Windows reuses process ids. It never touches
an AutoCAD alfe did not start. On the project's Windows CI it runs
*before* every CAD job, which is the only moment that covers a hard
cancel (nothing runs after one) and the only moment that cannot catch an
AutoCAD the current job is using.

A *process id that still answers is not a running process.* Windows keeps
a process-table entry until the last handle to it is closed, and the COM
service holds one — so a dead =acad.exe= can linger for days: it has no
threads left, =Stop-Process= cannot touch it, and =taskkill= replies
"there is no running instance of the task". The sweep classifies each
recorded id before acting (gone / exited-and-waiting-to-be-reaped /
running) and drops the first two from the file. It *fails the job it
precedes* only when an instance is really *running* and could not be
ended — such an AutoCAD owns the =AutoCAD.Application= COM registration
and answers =RPC_E_CALL_REJECTED= to every call, which would look like an
alfe defect in the log.

Two variables relax that, and they are not interchangeable:

- =CAD_SWEEP_NONBLOCKING=1= — *this job cannot be affected*: it drives BricsCAD
  only, and a wedged AutoCAD owns a registration BricsCAD neither asks for nor
  shares. The sweep still runs and still reports; it simply does not fail the
  job. The project's BricsCAD-only Windows jobs carry it through their CI gate
  (=.gate-windows-bricscad-*=), and ~make check-cad-sweep-gating~ keeps each job
  on the gate its vendor calls for. Note that =accoreconsole= *is* AutoCAD, so
  those jobs stay blocking.
- =CAD_SWEEP_IGNORE_SURVIVORS=1= — *I know, run anyway*: the emergency override
  for a machine nobody can reach at the moment.

The release → version table alfe knows covers AutoCAD 2019–2026 (2022 is
24.1, 2025 is 25.0); the relation is not arithmetic, so a release outside
it is resolved by asking the registry what is installed, and
=$AUTOCAD_PROGID= names one outright.

So =alfe --cad bricscad-v25-fr_FR -l script.lsp= runs a specific
BricsCAD, and =alfe --cad autocad-2022 --mode batch= selects
accoreconsole 2022. =--cad= sets the backend (a conflicting
=--autocad= / =--bricscad= on the same line is an error) and, for a
CAD, points that backend's discovery at the chosen executable. When
several BricsCAD locales of the same version are installed, the host
language preference (macOS =AppleLanguages=; Unix =LANG= / =LC_*=)
picks one.

* Dialect selection

The =--dialect NAME= option (and its =--strict= / =--autocad= /
=--bricscad= / =--clautolisp= shorthands) selects the AutoLISP
dialect descriptor the runtime uses: which reader knobs are on,
which encoding default applies, which special-case syntax is
accepted.

| Option         | Dialect        | Notes                                           |
|----------------+----------------+-------------------------------------------------|
| =--dialect strict= / =--strict= | =strict=       | Default. Portable AutoCAD ∩ BricsCAD subset.    |
| =--dialect autocad-2026= / =--autocad= | =autocad-2026= | AutoCAD 2026 surface. UTF-8 default encoding.   |
| =--dialect bricscad-v26= / =--bricscad= | =bricscad-v26= | BricsCAD V26. Lax reader, hex-float =atof=.     |
| =--dialect clautolisp= / =--clautolisp= | =clautolisp=   | Superset of strict + clautolisp extensions.     |

The dialect is independent of the backend — you can run
=alfe --clautolisp --dialect bricscad-v26 script.lsp= to evaluate
under the BricsCAD reader rules in the in-process engine, which
is useful for testing.

Whatever the dialect selected, all operators remain callable.
Out-of-dialect operators get a diagnostic at use time: under the
=clautolisp= backend, an operator only one vendor provides (BricsCAD's
=vle-*= family, AutoCAD's =acad_*= functions, …) prints one
=[vendor-operator]= notice per session at its first call, unless the
dialect is that vendor's or =lax=. =(setq *AUTOLISP-WARN-OUT-OF-DIALECT* nil)=
silences it. Under =--autocad= and =--bricscad= the CAD itself decides:
an operator it lacks is simply undefined there.

* Host selection

=--host NAME= picks the HAL (host abstraction layer) backend the
clautolisp engine talks to: it decides where the CAD-host effects of a
program land — =(getvar …)=, =(command …)=, =(ssget …)=, the ActiveX
object model. The dialect (see /Dialect selection/) controls the
/language/, the host controls the /target/; the two are independent.

alfe knows three hosts and does not interpret the choice: it passes it on
to clautolisp, which supports all three.

| Option          | Host     | What it is                                            |
|-----------------+----------+-------------------------------------------------------|
| =--host cador=  | =cador=  | Default. The headless CAD core: an in-memory, deterministic CAD application. |
| =--host cadtui= | =cadtui= | The textual UI-tree host, layered on the cador core.  |
| =--host nihil=  | =nihil=  | No host at all: every host operation is refused.      |

Any other name is a usage error (exit status 64, =EX_USAGE=) that lists
these three.

=--host= only matters with the =clautolisp= backend. Under =--bricscad=
and =--autocad= the host is the CAD itself and the option is accepted and
ignored. That is coherent: =--bricscad= and =--autocad= each start a CAD
with its own GUI, and =--clautolisp --host cadtui= starts clautolisp with
a text UI.

** =cador=

The default. It behaves as a small CAD with no window: system
variables have values (=(getvar "CLAYER")= is ="0"=), entities and
selection sets live in memory, and the ActiveX object model
(=vlax-get-acad-object=, =vla-*=) runs against an in-memory object
graph. It has no CAD command engine: =(command …)= does not draw, it
/records/ the command line's tokens, and =(clal-command-log)= returns
what was recorded. That makes it the host for running and testing
programs on a machine with no CAD.

** =nihil=

The trivial host, for programs that must not touch a CAD at all: any
host operation signals =HOST-NOT-SUPPORTED=, for instance

#+begin_example
$ alfe --clautolisp --host nihil -x '(getvar "CLAYER")'
; clautolisp runtime error: HOST-NOT-SUPPORTED: Host backend nihil does not support GETVAR.
#+end_example

Pure computation — lists, strings, arithmetic — is unaffected, so running
a supposedly pure program under =--host nihil= is a way to find out
whether it reaches for a CAD after all.

** =cadtui=

The textual counterpart of a CAD application, built on the cador core.
It presents the CAD — menu bar, drawings, the CAD view with its entities
and grips, alerts, DCL dialogs, consoles — as an inspectable,
keyboard-drivable tree, and mirrors DCL dialogs (=new_dialog= /
=start_dialog=) into that tree, so that programs with dialogs can be
tested headless and scripted. cador is cadtui's degenerate,
application-and-console-only configuration.

alfe does not embed cadtui: the clautolisp executable provides it. So
=alfe --clautolisp --host cadtui …= runs the installed =clautolisp-sbcl=
as a child process — alfe selects =--backend subprocess= by itself — and
gives it the run alfe resolved -- the dialect, =--host cadtui=, the
drawing, the encodings, alfe's =*AUTOLISP-...*= values and one =-l= /
=-x= / =-i= per action of the plan, plus =--quiet= and =--no-init= (alfe
owns the init policy) -- exactly as for any =--backend subprocess= run
(see [[#one-engine-two-transports][One engine, two transports]]). Asking for cadtui together with =--backend direct=, the
in-process engine, is a usage error.

The engine executable, =clautolisp-sbcl= (=clautolisp-sbcl.exe= on
MS-Windows), is looked for in this order, by =--host cadtui= and by
=--backend subprocess= alike, and the first file that exists is run:

1. =$ALFE_CLAUTOLISP_BIN=, when set and not empty;
2. the engine installed with the running alfe: the =clautolisp-sbcl= in
   the same directory as the running =alfe-sbcl= image (in a release both
   live in =PREFIX/libexec/clautolisp/binaries/OS/CPU/=, where the
   =bin/alfe= launcher dispatches to), then, for an alfe installed in
   =PREFIX/bin/=, =PREFIX/libexec/clautolisp/binaries/OS/CPU/clautolisp-sbcl=,
   OS (=linux=, =darwin=, =windows=) and CPU (=x86-64=, =arm64=) named as
   the launcher names them. PREFIX is derived from where the running
   executable is, so an installation works under any prefix, spaces
   included, after being moved, from any current directory, without
   =$PATH= entries for =libexec= and without =$ALFE_CLAUTOLISP_BIN=;
3. the =tools/clautolisp/bin/clautolisp-sbcl= of the checkout alfe was
   built from (=clautolisp-sbcl.exe= on MS-Windows), only when that file still exists;
4. =clautolisp-sbcl= on =$PATH=;
5. =/usr/local/bin/clautolisp-sbcl= (not on MS-Windows).

When it is nowhere alfe exits with status 69 (=EX_UNAVAILABLE=), and the
=NO-SUBPROCESS-BINARY= message lists every place it looked.

#+begin_src sh
alfe --clautolisp --host cadtui -l dialog-test.lsp     # batch: the output comes back when the child ends
alfe --clautolisp --host cadtui -i                     # the cadtui console, on your terminal
#+end_src

In a batch run alfe collects the child's output and prints it when the
child exits. When the plan holds =-i= — or has no action at all, which is an
implicit =-i= — the child is given alfe's own terminal, keyboard and
screen, instead of pipes, so that the cadtui console (or a text UI) talks to
you directly. alfe does nothing else about the terminal while the child
runs: what happens when alfe's terminal settings and a full-screen text UI
disagree is not settled yet, and will be dealt with as it is met. How
cadtui is driven, and what it offers, is documented in the clautolisp user
manual (=clautolisp-user-manual.org=, /Host backend/); alfe does not repeat
it.

** What a program sees

=*AUTOLISP-HOST*= (see the chapter on the =*AUTOLISP-…*= globals) holds
the host that was selected, as a symbol, the same in the in-process engine
and in the child process:

| Selected        | =*AUTOLISP-HOST*= |
|-----------------+-------------------|
| =--host cador=  | =CADOR=           |
| =--host cadtui= | =CADTUI=          |
| =--host nihil=  | =NIHIL=           |

With no =--host= the host is cador.

** =--list-hosts=

=alfe --list-hosts= prints the three backends with a one-line summary each
and exits, like =--list-dialects= and =--list-encodings=:

#+begin_example
$ alfe --list-hosts
Available --host backends:
  cador    Headless CAD core: the /application/console tree (default).
  cadtui   Full textual UI-tree host on the cador core: menus, drawings,
            CAD view, and DCL dialogs mirrored into an inspectable tree.
  nihil    Trivial backend: no CAD host at all.
#+end_example

clautolisp's own =--list-hosts= adds a line about =mock=, =null= and
=none=; alfe does not, because it refuses those spellings (see the table
above). Up to alfe 2.2.106 the option was accepted and did nothing, so
=alfe --list-hosts= with no other action opened the REPL instead of
answering.

** One clautolisp option alfe does not have

=--mock-input PATH= (a file of answers for the cador host's =getstring= /

* CAD engine control

Four options govern *how* a CAD engine is obtained and how much of the
bootstrap it runs. They apply to the CAD backends (=--bricscad=,
=--autocad=); the clautolisp backend ignores them, since it needs
neither a launch nor a workdir handshake.

| Option                        | Effect                                          |
|-------------------------------+-------------------------------------------------|
| =--backend attach\vert{}launch=      | Attach to an already-running CAD, or launch a fresh one. |
| =--workdir DIR=               | Override the exchange directory (default: =$AUTOLISP_WORKDIR=). |
| =--bootstrap-phase PHASE=     | Truncate the bootstrap at =marker=, =core=, =log= or =full=. |
| =--cad-log FILE=              | After the run, copy the CAD's own command-history log to FILE, in UTF-8 (see [[#cad-log][The CAD's log: =--cad-log=]]). |
| =--epure=                     | Run BricsCAD or AutoCAD under the EPURE profile (MS-Windows only). Defined by the =epure= plug-in, not by alfe itself: see [[#plugin-epure][The EPURE plug-in]]. |

=--workdir= names the directory through which alfe and the CAD engine
exchange files — the file-IPC channel the CAD backends run on. Point it
somewhere you can read when you want to inspect that traffic; combine it
with =--keep-workdir= (or =$AUTOLISP_KEEP_WORKDIR=), which stops alfe
deleting the directory at the end of the run, since by default there is
nothing left to look at.

The process alfe launches for a CAD backend (=accoreconsole=, =bricscad=,
or the =cscript= / =osascript= launcher) writes its own console — the
command echoes, prompts and messages the CAD prints, not your program's
output, which comes back through the protocol — to two files in that
directory, =engine-console-stdout.txt= and =engine-console-stderr.txt=.
alfe reads them only when the launch fails, to quote them in its
message; with =--keep-workdir= they stay for inspection. They used to be
pipes that nothing read while the CAD ran, so a long, chatty
=--autocad --mode batch= run (=accoreconsole= echoes its whole command line,
two bytes a character) filled the pipe and hung until =--timeout=. A file
never fills, however long the run.

=--bootstrap-phase= truncates the engine-side bootstrap, which is how
you diagnose a CAD that never reaches =READY= — work *up* from =marker=
and the phase that stops working is the one at fault:

| Phase     | Behaviour                                                       |
|-----------+-----------------------------------------------------------------|
| =marker=  | Writes a startup marker and a status, nothing else. *Your actions are not executed* — this only proves the engine started and can write to the workdir. |
| =core=    | Executes actions with basic file I/O, but does *not* capture =print= / =princ= / =prompt= output. |
| =log=     | =core= plus the CAD-log setup (=LOGFILEMODE=, =LOGFILEPATH=, =LOGFILENAME=). |
| =full=    | The default: CAD log, capture of Lisp output, batch REPL under =-i=, and the remote protocol. |

Two consequences worth knowing before you use a truncated phase: under
=marker= a run that "succeeds" has not run your script at all, and under
=core= a script that prints its results looks silent because the capture
is not installed. =--interactive= requires =full= — combined with any
other phase, alfe exits with code =2=.

** The CAD's log: =--cad-log=
:PROPERTIES:
:CUSTOM_ID: cad-log
:END:

In the =log= and =full= phases the engine-side bootstrap points the CAD's
=LOGFILEPATH= at the workdir's =logs/= directory and sets =LOGFILEMODE= to
1, so AutoCAD and BricsCAD write their command-history log there (alfe's
own =debug.log= sits beside it). That log carries what the CAD prints to
its command line — command prompts, and on AutoCAD a native =princ= — which
alfe's captured output does not.

=--cad-log FILE= makes alfe read that log once the engine has shut down,
and write it to =FILE= (replaced if it exists) in UTF-8 with LF line ends.
When the CAD wrote several log files (one per drawing), each is preceded by
a ~==> NAME <==~ line. The CAD writes the log in its own encoding, which
alfe decodes as follows:

- with =-Elog ENC= (or =--log-encoding ENC=): as =ENC= — =utf-8=,
  =utf-16le=, =iso-8859-1=, =windows-1252= or =us-ascii=; any other name is
  warned about and the log is auto-detected. A bare =-E= does *not* reach
  the log: the CAD does not change its encoding for it;
- otherwise, as measured: a byte-order mark names the encoding (UTF-8,
  UTF-16LE); without one, =windows-1252= on MS-Windows, which is what both
  Windows CADs write (measured: AutoCAD 2022, and BricsCAD V25 — no BOM,
  an e-acute is the single byte =E9=) and auto-detection elsewhere.

No log, no file: alfe warns instead — BricsCAD on macOS writes none in
batch mode (measured), and =--bootstrap-phase marker= / =core= do not turn
logging on. =--cad-log= concerns the CAD backends only; under
=--clautolisp= it is warned about and ignored (clautolisp writes its own
=LOGFILEMODE= log where =LOGFILEPATH= points, and =-Elog= sets its
encoding — see the clautolisp user manual).

=--epure= is not one of alfe's own options: the =epure= plug-in, which
ships with alfe, defines it ([[#plugin-epure][The EPURE plug-in]]). Before the plug-in system
alfe accepted =--epure= and did nothing with it. It now launches
BricsCAD or AutoCAD under the =Epure= profile and runs EPURE's control
script before alfe's run-time is loaded. It works on MS-Windows only;
elsewhere, and under =--clautolisp=, it is silently ignored. Its
companions =--epure-profile= and =--epure-script= are described with the
plug-in.

The environment variables =$AUTOLISP_WORKDIR=, =$AUTOLISP_BOOTSTRAP_PHASE=
and, for the plug-in option =--epure=, =$AUTOLISP_EPURE= supply the
defaults; an explicit option always wins.

* The debugger (aldo)

alfe takes the debugger options of the =clautolisp= program, spelled,
parsed and meant exactly as there (the option specs are shared; the
=clautolisp= user manual describes the debugger itself). Under
=--clautolisp= they apply to both engine variants:

- =--backend direct= (the in-process engine) resolves them and starts the
  aldo session, its user interface and the aldb listener with the
  =clautolisp= program's own functions;
- =--backend subprocess= forwards the ones you gave to the =clautolisp=
  child, which applies them -- and its own defaults to the others. When
  they start a debugger (=--on-error debug=, =--debugger-ui=, an aldb
  transport, an explicit =--on-quit debug= / =--on-interrupt debug=) the
  child runs on alfe's own terminal, as for =-i=, so its prompts reach you.

| Option                      | Under =--clautolisp=                                                                                         | Under =--autocad= / =--bricscad=                       |
|-----------------------------+--------------------------------------------------------------------------------------------------------------+--------------------------------------------------------|
| =--on-error POLICY=         | Uncaught AutoLISP error: =quit= reports it and exits 1 (batch default), =debug= stops in aldo at the error (default of an interactive REPL), =ignore= uses no debugger (the AutoLISP =*error*= handler runs). | Accepted: governs alfe's own reporting only (below). |
| =--on-interrupt POLICY=     | Control-C: =debug= (break into aldo, the default), =ignore= (resume), =quit= (exit 130). A second Control-C while one is handled exits at once. | Usage error (EX_USAGE, 64).                            |
| =--on-quit POLICY=          | =(quit)= / =(exit)=: =quit= (default) or =debug= (aldo before the stack unwinds).                            | Usage error (EX_USAGE, 64).                            |
| =--debugger-ui UI=          | =dumb= (aliases =terminal=, =tui=), =ncurses=, =aldb= (alias =emacs=); selecting one debugs the run.        | Usage error (EX_USAGE, 64).                            |
| =--aldb-listen [HOST:]PORT= | The aldb (Emacs) listener's address (HOST defaults to 127.0.0.1, PORT 0 = a free port); implies =aldb=.     | Usage error (EX_USAGE, 64).                            |
| =--aldb-stdio=              | aldb over stdin/stdout; implies =aldb=; excludes =--interactive= and =--aldb-listen= (usage error).          | Usage error (EX_USAGE, 64).                            |

The CAD backends run AutoLISP inside the CAD, which has no aldo: alfe
refuses the options it could not honour rather than ignoring them,
=--dry-run= included.

=--on-error= also keeps its older meaning, under every backend: =debug=
and =ignore= make alfe dump the Common-Lisp backtrace of an unexpected
condition in alfe ITSELF (captured before the stack unwinds), after the
terse =alfe: <error>= line; =quit=, or no =--on-error=, prints that line
only. That reporting concerns a fault of alfe, never the user's AutoLISP.

Control-C: under =--backend direct= the =--on-interrupt= policy applies to
alfe's process for the run, then Control-C is alfe's again. Under
=--backend subprocess= alfe leaves Control-C to the child, which applies the
forwarded policy: alfe passes the signal on when the terminal did not deliver
it to the child itself (a batch child runs in its own process group).

#+begin_src sh
alfe --clautolisp --on-error debug -l buggy.lsp          # stop in aldo at the error
alfe --clautolisp --backend subprocess --on-error debug -l buggy.lsp   # same, in the child
alfe --clautolisp --aldb-listen 0 -l buggy.lsp           # debug from Emacs (M-x aldb-connect)
alfe --clautolisp --on-interrupt quit -l long-run.lsp    # Control-C exits 130
#+end_src

* Actions

alfe accepts an ordered queue of actions on the command line. The
queue runs in order then the engine terminates (or enters the
REPL with =-i=).

| Option              | Action                                          |
|---------------------+-------------------------------------------------|
| =-x EXPR= / =--eval EXPR= | Evaluate EXPR. Value is NOT auto-printed — wrap with =(print …)= if you want it back on stdout. See "Action output semantics" below. |
| =-l FILE= / =--load FILE= | Load and evaluate FILE. A relative FILE is resolved from alfe's invocation directory before it is sent to a CAD process. |
| =FILE.lsp= (positional)  | Equivalent to =-l FILE.lsp=.                    |
| =-i= / =--interactive=   | Enter REPL after the queue (same context). Auto-printing is enabled in the REPL only.      |
| =--quit=               | Force engine shutdown after the queue.          |
| =--dry-run=            | Print the resolved plan; don't run anything.    |
| =--print-command=      | Stage the workdir for real, print the CAD command line that would be launched, launch nothing. CAD backends only. |
| =--on-error POLICY=    | What an uncaught AutoLISP error does under =--clautolisp= (=quit=, =debug=, =ignore=), and how alfe reports its own unexpected conditions. See "The debugger (aldo)" below. |

Examples:

#+begin_src sh
alfe -x "(print (+ 1 2))"                # → 3
alfe -x "(+ 1 2)"                        # silent — value discarded
alfe -l prelude.lsp -x "(my-main)"       # load then call
alfe -l script.lsp -i                    # load then drop to REPL
alfe --bricscad -l ../scripts/draw.lsp   # run under BricsCAD
alfe --dry-run -l foo.lsp                # show the plan only
#+end_src

A relative =-l= pathname always denotes a file relative to the directory
from which =alfe= was invoked.  This is true for every backend.  In
particular, AutoCAD and BricsCAD receive an absolute pathname: their batch
processes run inside alfe's temporary workdir, which is not the caller's
current directory.

** Action output semantics

=-x EXPR=, =-l FILE= and =--main FN= are *batch* evaluations, not
REPL steps. The value an action produces is *not* echoed to alfe's
stdout — use an explicit printing primitive in the expression
(=(print …)=, =(princ …)=, =(prin1 …)=) when you want the value
to come back. This is uniform across the =--clautolisp=,
=--bricscad= and =--autocad= backends.

The interactive REPL (=-i= / =--interactive=) is the only context
where values are auto-printed: there, each top-level form's value
is read, evaluated and printed (read-eval-print loop). =-x= and
=-l= actions issued alongside =-i= remain silent-by-default; only
forms typed AT the REPL prompt print their values.

*The printing primitives frame their output the same way on every
backend.* =(princ X)= writes X and nothing else -- it does NOT end the
line, so =(princ "a") (princ "b")= gives =ab= -- =(prin1 X)= writes the
readable form, =(print X)= writes a newline, the readable form and a
trailing space, and =(princ)= alone writes a bare newline. With a file
descriptor from =(open path "w")= the text goes to that file instead of
alfe's stdout. This is uniform across =--clautolisp=, =--bricscad= and
=--autocad=; up to alfe 2.2.91 the AutoCAD backend added a newline
after every =princ= and =print=.

*An action that signals ends the run.* When an expression fails --
an undefined function, a wrong argument type, an error the code
raises itself -- the action is a failure: alfe prints the engine's
own message on =stderr= and exits non-zero, whether the form came
from =-x=, =-l= or =--main=, and whatever backend ran it. On the CAD
backends the message is prefixed with the request that produced it:

#+begin_example
$ alfe --bricscad -x '(no-such-function 1)' ; echo "exit $?"
ERROR protocol request 1: Undefined AutoLISP function NO-SUCH-FUNCTION.
exit 1
#+end_example

A batch script can therefore test alfe's exit status and trust it.
(Up to alfe 2.2.90 a =-x= form that signalled on a CAD backend was
reported as a success -- exit 0, no diagnostic, and the expression's
output missing, which looked exactly like a form that printed
nothing. If you have a script that took that silence for success,
re-run it.)

If you want a one-line shorthand for "evaluate and print", define a
helper in your init file:

#+begin_src lisp
(defun ep (form) (print (eval form)))
;; … then …
alfe -l ~/.autolisp -x "(ep (quote (list 1 2 3)))"
#+end_src

** How a form reaches a CAD

On the =--bricscad= and =--autocad= backends alfe does not hand an =-l=
file to the CAD's own =LOAD=: its CAD-side loader reads the file one
top-level form at a time, so that errors are reported with their file,
line and enclosing =defun=, and passes each form to the CAD's native
=LOAD= through a temporary file (=protocol/alfe-eval.lsp= in the
workdir). =-x= expressions and the forms typed at the REPL take the same
route.

What that file holds is the form's own *text*, exactly as it was written:
the CAD reads =(setq a 1.5707963267948966)= with its own reader, and
=a= gets every digit. Only a form alfe has to rewrite is printed back from
its value -- on AutoCAD, whose =defun= has no =&rest=, a call such as
=(princ x)= is padded to =(princ x nil)= -- and then every real is printed
with as many digits as it takes to read back to the same number
(=1.5707963267948966E+00=), checked by the CAD's own reader.

/Changed in alfe 2.3.12./ Every form used to be printed back with =princ=,
which keeps 6 significant digits of a real on AutoCAD (=1.5708=) and 14 on
BricsCAD (=1.5707963267949=), so real literals of a loaded file, of =-x=
and of the REPL arrived rounded. Values the CAD computes, and digits held
in a string, were never affected. =--clautolisp= was never affected.

What a program *prints* is unchanged: =(print 1.5707963267948966)= on
AutoCAD still shows =1.5708=, as AutoCAD's own =print= does.

The loader knows both AutoLISP comments: a semicolon comments out the rest
of its line, and =;|= opens a block comment that runs, across lines if
need be, to the next =|;= -- the form of the documentation blocks
(=;| @Global ... |;=) many projects put before each =defun=. Nothing inside
a block comment is read, whatever parentheses, quotes or semicolons it
holds; =;|= inside a string is text; forms before, after and between
comments on one line each run once. A block comment still open at the end
of the file is an error (/unexpected end of file in a ;| block comment/).

/Changed in alfe 2.3.13./ The loader used to know only the line comment,
so the lines of a block comment after its first were read as code, and a
parenthesis in the prose was called as a function (/no function
definition: SYMBOLE/). =--clautolisp= was never affected.

** Interactive REPL on CAD backends

=alfe --interactive --bricscad= (and =--autocad=) drops into a live
REPL backed by the same file-IPC protocol the batch =-x= / =-l=
actions use. Practical points:

- The prompt is =alfe>= (or =    >= for continuation lines when the
  form isn't balanced yet). Multi-line forms are accepted — the
  reader waits for a balanced parenthesis count before forwarding.
- Each form is sent through =protocol/stdin.txt=; output is drained
  live to your terminal as the CAD prints (no end-of-plan buffering).
- Errors do not exit the REPL: a failed eval surfaces its message on
  =stderr=, the prompt comes back, the runtime stays in its read-eval
  loop.

On MS-Windows, the CAD backends discover installed engines by
default from the standard =Program Files= roots. =--bricscad=
searches =%ProgramW6432%=, =%ProgramFiles%= and
=%ProgramFiles(x86)%= for =Bricsys/*/bricscad.exe=; =--autocad=
searches the same roots for =Autodesk/AutoCAD */acad.exe=,
=AutoCAD LT */acadlt.exe= and =accoreconsole.exe=. If
=BRICSCAD_EXE=, =AUTOCAD_EXE= or =AUTOCAD_ACCORECONSOLE= is set,
that explicit path wins.

For =alfe --autocad --mode batch=, the drawing/template selection is:
=--dwg FILE= first, then =AUTOLISP_DWG=, then a shipped
=Template/acadiso.dwt= or =Template/acad.dwt= next to the discovered
AutoCAD install. Only if all three miss does batch mode stop with a
=NO-DWG= bootstrap error. Under =--clautolisp=, =--dwg FILE= (or
=AUTOLISP_DWG=) is the drawing the engine starts on, in place of its
untitled =Drawing1.dwg=, as =clautolisp --dwg FILE= does.
- Exit with any of: Ctrl-D (EOF), an empty line that equals =:quit=,
  =:q=, =:exit=, =(quit)=, =(exit)=, or by queuing a =--quit= action.

You can mix =-l= / =-x= with =--interactive= in one invocation: the
batch actions run first, then control hands off to the REPL with the
same shared evaluation context.

* Encoding

Encoding is set per /situation/ — one option per boundary where
bytes cross. Each situation =S= has a long form =--S-encoding ENC=
and a short form =-ES ENC=; bidirectional situations also accept a
=-in= / =-out= suffix (=--S-in-encoding=, =-ES-in=). A bare
=--encoding ENC= / =-E ENC= sets every situation at once.

| Situation  | Option                | Effect                                              |
|------------+-----------------------+-----------------------------------------------------|
| source     | =-Esource ENC=        | Source-file encoding for the whole session.         |
| terminal   | =-Eterminal ENC=      | alfe's own REPL I/O encoding; surfaced to AutoLISP. |
| file       | =-Efile ENC=          | =(open …)= file I/O default.                         |
| console    | =-Econsole ENC=       | CAD GUI console device I/O.                          |
| cadstdio   | =-Ecadstdio ENC=      | CAD subprocess stdin/stdout pipes.                  |
| log        | =-Elog ENC=           | The CAD's command-history log (=LOGFILEMODE=).       |
| (all)      | =-E ENC=              | Every situation at once.                            |

Accepted ENC values: =utf-8=, =iso-8859-1= (= =latin-1=),
=windows-1252= (= =cp1252=), =us-ascii=. Suffixes select a
line-ending variant: =-mac= / =-cr= for CR, =-dos= / =-crlf= for
CRLF, =-unix= / =-lf= for LF. So =-Esource utf-8-crlf= reads a UTF-8
file with CRLF terminators.

Without =-Esource=, the dialect's default applies (=iso-8859-1= for
=strict=, =utf-8= for =autocad-2026= / =bricscad-v26= /
=clautolisp=). When neither dialect nor option specifies one, the
process locale (=$LC_ALL=, then =$LANG=, then =$LC_CTYPE=)
supplies the fallback.

=--list-encodings= prints every accepted ENC name and exits;
=--list-situations= prints the situations and their directions.

** What each situation actually does

Not every situation is settable on every target — some are fixed by the
CAD product. alfe *accepts* the option in all cases, but when the value is
fixed it warns that it is ignored and keeps the product value (so a typo is
still an error, but a fixed boundary is never silently wrong).

- =terminal= — applied to alfe's OWN =*standard-output*= / =*standard-input*=
  / =*error-output*=. =-Eterminal-in= drives stdin, =-Eterminal-out= drives
  stdout+stderr; the bare form both. Settable everywhere (it is alfe's own
  stream). On MS-Windows a redirected stream (a pipe, a file) is re-made in
  the encoding; a console already receives alfe's text as Unicode, so
  there the option sets the console's code page (=SetConsoleOutputCP= /
  =SetConsoleCP=: UTF-8 65001, WINDOWS-1252 1252, ISO-8859-1 28591,
  US-ASCII 20127, CP850, CP437), which is what other programs writing to
  it are read in. An encoding without a code page is warned and ignored.
- =source= — an explicit =-Esource= is forwarded into the CAD's native
  =(load)= so a =.lsp= with non-ASCII literals decodes correctly (BricsCAD
  =,ccs=…=, AutoCAD the =open= 3rd-arg at =LISPSYS= 1/2). Without it the CAD
  keeps its own default decode. A =-l= file in a code page (=-Esource cp1252=)
  is handed to AutoCAD as a cp1252 copy without a BOM -- read right at every
  =LISPSYS= -- and to BricsCAD as UTF-8 with a BOM.
- =file= — the default encoding of files the AutoLISP program itself opens:
  =-Efile ENC= for both directions, =-Efile-read ENC= / =-Efile-write ENC=
  for one. On clautolisp it sets =*AUTOLISP-FILE-READ-ENCODING*= /
  =*AUTOLISP-FILE-WRITE-ENCODING*=, which =open= uses when the program names
  no encoding; =alfe --clautolisp= forwards them to the engine (in
  subprocess mode too, with =-Eterminal-in= / =-Eterminal-out= / =-Elog=).
  On the CADs the variables are transmitted too, but the CAD's own =open=
  takes an encoding in one case only, measured with the =open-encoding=
  probe (writing =A=, e-acute, =B=):

  | CAD                       | =(open f "w")= | an encoding requested                               | read           |
  |---------------------------+----------------+-----------------------------------------------------+----------------|
  | AutoCAD 2022, =LISPSYS= 0 | cp1252         | any 3rd argument is an error; ~,ccs=~ ignored       | decodes cp1252 |
  | BricsCAD V25 / Windows    | cp1252         | 3rd argument ignored; ~w,ccs=UTF-8~ and ~w,ccs=UTF-16LE~ honoured, with a BOM | raw octets |
  | BricsCAD V26 / macOS      | UTF-8, no BOM  | ignored (always UTF-8)                              | raw octets     |

  At =LISPSYS= 1 or 2, AutoCAD 2022's =open= does take a third argument
  (measured, the =LISPSYS= probe): =(open f "w" "utf8")= writes UTF-8
  without a BOM, ="utf8-bom"= with one, and a plain ="w"= still writes
  cp1252; a plain read decodes UTF-8, falling back to cp1252. An append
  =(open f "a" "utf8")= adds UTF-8, and ="utf8-bom"= on a file that already
  has its BOM adds no second one.

  So alfe forwards the WRITE direction in two cases, on every action -- the
  file given to =-l=, =-x= forms, =--main=, REPL input, and code loaded with
  =alfe-load= -- when =-Efile-write= (or =-Efile=, or the bare =-E=) asks for:
  - BricsCAD/Windows, =UTF-8= or =UTF-16LE=: a plain =(open f "w")= /
    =(open f "a")= becomes ~(open f "w,ccs=UTF-8")~ (or =UTF-16LE=), so the
    file is written in that encoding *with a byte-order mark*; an append
    adds no second one (measured, BricsCAD V25), whereas a plain ="a"=
    would append cp1252 bytes to the UTF-8 file; if BricsCAD refuses the
    mode, the plain one is used;
  - AutoCAD, =UTF-8=: a plain =(open f "w")= / =(open f "a")= becomes
    =(open f "w" "utf8")= / =(open f "a" "utf8")= (UTF-8, no BOM) — but
    only when the running AutoCAD's =LISPSYS= is 1 or 2, which alfe checks
    in the CAD at the call, since =LISPSYS= is set when AutoCAD starts. At
    =LISPSYS= 0 the plain mode is used and a warning says why, once per run.
  A call that already names an encoding (a ~,ccs=~ of its own, a third
  argument) or a read mode is left alone. alfe rewrites each =open= call
  written in the code it is given into the bootstrap's =alfe-open*=, in the
  source text (the rest of the text reaches the CAD as written); so an =open=
  that only appears at run time -- =(apply 'open ...)=, a quoted
  =(open ...)= evaluated later, a file read by a native =load= nested inside
  an expression -- is not forwarded, while a top-level =(load ...)= in an
  =-l= file or =-x= form, and =alfe-load= anywhere, are. Without
  =-Efile-write= nothing is rewritten. =cp1252= /
  =windows-1252= is both Windows CADs' default and needs nothing. Every
  other request is warned about, once per run, with the measured reason,
  and not forwarded: any other write encoding on BricsCAD/Windows or on
  AutoCAD, any write encoding on BricsCAD/macOS except UTF-8, and any read
  encoding (the CADs' =open= reads in its own default whatever it is asked:
  cp1252 on AutoCAD at =LISPSYS= 0, UTF-8 then cp1252 at 1/2, octets on
  BricsCAD).
- =console= / =cadstdio= — how alfe DECODES the CAD's console/pipe output.
  accoreconsole is UTF-16LE, *fixed by the product* — =-Econsole= is warned
  and ignored under =--autocad=; =-Ecadstdio= forces the codec alfe decodes
  with. A bare =-E= reaches neither, under =--autocad= or =--bricscad=.
  Under =--bricscad=, =-Econsole[-out]= selects the decode codec, and
  =-Econsole-in= is warned about and ignored: the console device is
  product-fixed and alfe's input does not go through it (forms travel over
  the file protocol). For other targets the default is an auto-detect
  cascade (UTF-16LE / UTF-8 / lenient) unless you name a codec. In front of
  clautolisp the console IS the terminal: =-Econsole[-in|-out]= applies to
  the terminal unless =-Eterminal[-in|-out]= is given.
- =log= — the command-history log file (=LOGFILEMODE=). On clautolisp,
  =-Elog= is the encoding clautolisp writes it in. On AutoCAD and BricsCAD
  the CAD writes it in its own encoding, and =-Elog= is how alfe *decodes*
  it when =--cad-log FILE= asks for a copy (see [[#cad-log][The CAD's log:
  =--cad-log=]]); a bare =-E= does not reach it.

** Per-target defaults (measured 2026-07)

These are the encodings each target exhibits with NO override — the reason
some situations warn-and-ignore. Full provenance (settable / product-fixed /
LISPSYS-selected) is tracked in the project's encoding issues.

| Target                    | source / file           | console                       |
|---------------------------+-------------------------+-------------------------------|
| clautolisp (Linux)        | UTF-8 (settable, LC_*)  | UTF-8                         |
| BricsCAD V26 / macOS      | UTF-8 under a UTF-8 locale (settable via =LC_ALL=); read needs a BOM | full Unicode (GUI) |
| BricsCAD V25 / Windows    | ANSI_1252; per-open =,ccs=UTF-8/UTF-16LE= honoured on write (with a BOM; =-Efile-write= forwards it), read returns octets | cp1252 (GUI) |
| AutoCAD 2022 / accoreconsole | ANSI_1252 / MBCS; =LISPSYS= 1/2 → UTF-8 (restart); =ccs=~ ignored; =open= takes no 3rd argument at =LISPSYS= 0 | UTF-16LE, fixed |

* The =alfe-*= operators (for test and REPL code)

Code that alfe *controls* — =autolisp-test= suites, =outils-autolisp=
regression scenarios, REPL snippets, anything you feed through
=alfe -l FILE= or =-x EXPR= — should call the fixed-arity =alfe-*=
operators instead of the native =load= / =princ= / =print= / =prin1= when
it needs alfe's behaviour to be *identical on AutoCAD and on BricsCAD*.
The native operators still work, but they run in the CAD, not in alfe: on
AutoCAD =accoreconsole= a native =(load)= of a file that contains a
non-ASCII byte fails outright, and native =(princ …)= output does not
reach alfe's captured stream. The =alfe-*= operators are the portable
interface; they are defined by the alfe runtime, so they exist on every
backend (AutoCAD, BricsCAD, and the =clautolisp= host).

Why not just redefine =load= / =princ=? Because AutoCAD's AutoLISP has no
variable-arity user functions and re-routing the builtins re-enters alfe's
protocol loop. So alfe does *not* shadow the builtins; it offers parallel
=alfe-*= operators and rewrites the code it loads to use them (see below).

** The operators

| You write             | Use instead                | Notes                                              |
|-----------------------+----------------------------+----------------------------------------------------|
| =(load "f.lsp")=      | =(alfe-load "f.lsp")=      | Byte-safe deported load; honours =-Esource=.       |
| =(load p onfailure)=  | =(alfe-load-onfailure p x)=| Returns =x= on a resolve failure instead of erroring. |
| =(princ obj [file])=  | =(alfe-princ obj)=         | 1-arg convenience; output reaches alfe's stream.   |
| =(print obj [file])=  | =(alfe-print obj)=         |                                                    |
| =(prin1 obj [file])=  | =(alfe-prin1 obj)=         |                                                    |

For a call whose arity is not exactly one argument, use the *star* form,
which takes the argument list, so any arity maps to a fixed-arity call
(this is what lets it work on AutoCAD):

: (alfe-princ* (list obj file))     ; = (princ obj file)
: (alfe-princ* (list))              ; = (princ)  -> newline
: (alfe-load*  (list "f.lsp"))      ; = (load "f.lsp")

=alfe-print*=, =alfe-prin1*= and =alfe-load*= follow the same shape.

** =alfe-load= rewrites the file it loads

You do *not* have to convert a whole source tree by hand. =alfe-load=
reads the file honouring its encoding (so a high byte survives even on
=accoreconsole=), then *rewrites* every native =(load …)= / =(princ …)=
/ =(print …)= / =(prin1 …)= call in the loaded forms into its =alfe-*=
equivalent, and evaluates them directly. So a file loaded with =alfe-load=
gets the full alfe behaviour throughout — a nested =(load "other.lsp")=
inside it deports too — while the same file loaded with the native
=(load)= keeps native behaviour. Quoted data (=(quote …)=, =#'…=) is left
untouched.

Practical rule for =autolisp-test= / =outils-autolisp=: make the *entry
point* alfe loads use =alfe-load= for any file that may contain non-ASCII
literals, and use =alfe-print= / =alfe-princ= for output the harness must
capture. Everything transitively loaded through =alfe-load= is rewritten
automatically, so the scenario files themselves need no per-call change.

** Portability summary

| Backend                      | native =(load)= high-byte | =(alfe-load)= high-byte |
|------------------------------+---------------------------+-------------------------|
| clautolisp (Linux)           | ok                        | ok                      |
| BricsCAD (macOS / Windows)   | ok                        | ok                      |
| AutoCAD 2022 / accoreconsole | FAILS                     | ok                      |

=alfe-load= is the safe default in cross-backend test code: it is verified on
clautolisp, BricsCAD (macOS + Windows), and AutoCAD =accoreconsole= (the
encoding probe reads =(setq ENCSRC "A<e-acute>Z")= back as code points
=65 233 90= on all three). Native =(load)= of a high byte still FAILS on
accoreconsole, which is why alfe-owned code must call =alfe-load=.

** Names reserved to alfe on a CAD

On =--autocad= and =--bricscad=, alfe evaluates every form you give it —
the =-l= file, each =-x=, =--main=, REPL input, a file loaded with
=alfe-load= — *inside* alfe's own AutoLISP functions running in the CAD.
AutoLISP binds a function's parameters and locals dynamically, so a name
those functions bound would capture your =setq=: before alfe 2.3.15 a
=(setq f 1)= (or =text=, =r=, =path=, =form=, =source=, =result=, ...) set
alfe's local and was gone when the request returned.

Every variable alfe's CAD-side runtime binds is now named =alfe--NAME=, so
any other name is yours, globally, exactly as in the CAD itself. In return:

- names starting with =alfe--= are *reserved* to alfe — do not =setq= or
  bind them;
- the functions alfe defines in the CAD (=alfe-*=, =autolisp-*=, the
  =princ= / =print= / =prin1= / =prompt= / =terpri= shadows, =quit=, =exit=,
  =clear-input=, =clear-output=, =get_new_guid=) and its globals
  (=*AUTOLISP…*=, =*ALFE…*=) must not be redefined or assigned.

The =clautolisp= backend evaluates your code in-process and has no such
functions on the stack, so this concerns the CAD backends only.

* Init files

On startup (unless =--no-init= / =-norc= is given), alfe loads
the first init file it finds in this order:

1. =~/.alfe= or =~/.alferc=
2. =~/.autolisp= or =~/.autolisprc=
3. =~/.config/alfe/init=
4. =~/.config/autolisp/init=

The init file runs under the selected dialect and backend; it's a
natural place to put =alref-set-root= calls, custom helpers, REPL
preferences, etc.

*The engine's own init files do not run.* When alfe drives clautolisp as
a subprocess it passes =--no-init= (and =--quiet=) to it, so your
=~/.autolisp=, =~/.clautolisp= and the XDG init files are *not* loaded
by the engine. This is deliberate: the front end owns bootstrap policy,
and loading the spawned engine's rc files would make a subprocess run
behave differently from the in-process =:direct= one and let a personal
init file leak into test results. What you want in an alfe session
belongs in *alfe's* init file above, which does run.

The CAD backends are a different matter: AutoCAD and BricsCAD load
their own startup files, and alfe does not suppress them wholesale — but
it is not neutral either. A BricsCAD profile named with
=$AUTOLISP_BRICSCAD_PROFILE= changes what the engine auto-loads, and a
*clean* profile is precisely how you keep a vertical application out of
a pure-CAD run. See /Environment variables/ above.

* Plug-ins
:PROPERTIES:
:CUSTOM_ID: plugins
:END:

Behaviour that belongs to one site, one CAD product or one user —
starting EPURE, loading a package before your script — does not belong
in alfe's backends. A /plug-in/ is a Common Lisp file that alfe loads at
start-up and that

1. defines command-line options, possibly taking arguments;
2. intervenes, through named /hooks/, at any stage of a run: it can read
   and change the parsed options, veto a backend, rewrite the action
   plan, add lines to the scripts alfe generates for the CAD, change the
   command line and working directory the CAD is launched with, and
   observe every action, the shutdown, the exit code and every error.

Two plug-ins ship with alfe: =epure= runs BricsCAD or AutoCAD under the
EPURE profile ([[#plugin-epure][The EPURE plug-in]]), and =epuree= loads the EPUREE emulation
of the EPURE API before your script ([[#plugin-epuree][The EPUREE plug-in]]). Writing your
own is described in [[#plugin-writing][Writing a plug-in]].

What you can rely on:

- *Load all, activate by flag.* Every installed plug-in is loaded at
  start-up, so that its options exist when the command line is parsed.
  Only an /active/ plug-in has its hooks called.
- *Zero active plug-ins, zero behaviour change.* Every hook call site
  returns its input unchanged when no active plug-in registered that
  hook.
- *No silent shadowing.* A plug-in cannot redefine an alfe option or an
  option of another plug-in. That is a registration error and the
  plug-in is skipped.
- *A plug-in that fails to load is a warning.* =--help=, =--version= and
  every run that does not need the plug-in keep working.
- *A plug-in is trusted.* It runs inside alfe's image with alfe's
  privileges; there is no sandbox. Install one as you would install a
  program.

** Where plug-ins are installed

A /plug-in root/ is a directory holding one sub-directory per plug-in,
named for it. The plug-in =NAME= is one or both of

| File                            | Form                                                                   |
|---------------------------------+------------------------------------------------------------------------|
| =NAME/NAME.lisp=                | source                                                                 |
| =NAME/NAME.VERSION-IMPL.plugin= | compiled, for alfe version VERSION and Common Lisp implementation IMPL |

IMPL is =sbcl= or =ccl=. NAME matches =[a-z][a-z0-9-]*= and is the name
the plug-in registers under.

alfe searches the roots in this order, and *the first plug-in of a given
name wins*, so a local install shadows a system one:

1. every =--plugin-path DIR=, in command-line order;
2. every entry of =$ALFE_PLUGIN_PATH=, a PATH-style list (separated by
   =:=, or by =;= on MS-Windows);
3. =$XDG_DATA_HOME/clautolisp/plug-in= (=~/.local/share/clautolisp/plug-in=
   when the variable is unset; =%APPDATA%\clautolisp\plug-in= on
   MS-Windows);
4. =clautolisp/plug-in= under every entry of =$XDG_DATA_DIRS=
   (=/usr/local/share:/usr/share= when unset; none on MS-Windows unless the
   variable is set);
5. =PREFIX/share/clautolisp/plug-in=, PREFIX being the installation prefix
   the running executable belongs to — derived the same way as for the
   CAD runtime files (see /The CAD runtime files/);
6. the =plugins/= directory of alfe's source tree, when alfe runs from a
   checkout. It is what makes =epure= and =epuree= work before anything is
   installed; it comes last, so an installed plug-in shadows it.

=make install= puts the plug-ins that ship with alfe in
=$(PREFIX)/share/clautolisp/plug-in/= and compiles them with the alfe it
has just installed. Your own belong in the user-level root (item 3), or
in any directory you name with =--plugin-path=.

*Which form is loaded.* When the compiled file for this alfe version and
this Common Lisp implementation exists and is at least as new as the
source — or there is no source — it is loaded; otherwise the source is.
Editing a source therefore retires an older compiled file by itself. A
compiled file that fails to load falls back to the source, with a
warning. A compiled file whose VERSION or IMPL is not the running alfe's
is ignored (=--verbose= logs it).

** Compiling a plug-in

=alfe --compile-plugin FILE.lisp= compiles the plug-in source =FILE.lisp=
for the running alfe version and implementation into
=NAME.VERSION-IMPL.plugin= next to the source, prints its path and exits
0 (1 on a compile error, or when FILE is not there). NAME is the name of
FILE. Compiling is optional: a plug-in works from its source alone.

alfe is built for two implementations (=alfe-sbcl= and =alfe-ccl=, see
/Installation/), and a compiled file is valid for one of them and one
alfe version only. Compile once for each implementation you run, and
again after upgrading alfe.

#+begin_src sh
alfe --compile-plugin ~/.local/share/clautolisp/plug-in/hello/hello.lisp
#+end_src

** Listing plug-ins

=alfe --list-plugins= prints the plug-ins alfe found (name, version, the
form loaded — source or compiled —, path and description), those that
failed to load with the reason, and the search path, then exits 0.

** Activating a plug-in

An installed plug-in does nothing until it is /active/. It is active
when

- you gave its own activating option (=--epure= for =epure=, =--epuree=
  for =epuree=); or
- the environment variable that supplies the default of that option is
  set to a true value (=1=, =y=, =yes=, =true= or =on=), for instance
  =$AUTOLISP_EPURE=1=; or
- you gave =--plugin NAME=, which may be repeated; or
- =$ALFE_PLUGINS=, a comma-separated list of plug-in names, lists it.

=--plugin NAME= — or a name in =$ALFE_PLUGINS= — that is not installed is a usage error that
lists the installed plug-ins.

An active plug-in's other options take their value from the command
line, else from their environment variable, else from their default.
Giving an option of a plug-in that is *not* active is a usage error (exit
status 64) that names the option activating the plug-in: =alfe
--epure-profile Epure …= fails and points at =--epure=.

A plug-in declares the backends it takes part in. Under another backend
it is still loaded and its options still parse, but its hooks are not
called.

=alfe --help= ends with a generated /Plug-in options/ section listing
every option of every installed plug-in, active or not.

#+begin_src sh
alfe --bricscad --epure -x '(princ "ok")'          # the plug-in's own option
alfe --bricscad --plugin epure -x '(princ "ok")'   # the same, by name
export ALFE_PLUGINS=epure                          # every run, from your shell init
#+end_src

** Choosing the plug-in roots

=--plugin-path DIR= adds DIR to the search path; repeat it for several
roots. The directories given this way are searched first, in
command-line order, then the entries of =$ALFE_PLUGIN_PATH=, then the
standard places listed above. DIR is a plug-in /root/: it holds
=NAME/NAME.lisp=, not =NAME.lisp= itself.

#+begin_src sh
alfe --plugin-path ./my-plugins --plugin hello -x '(+ 1 2)'
export ALFE_PLUGIN_PATH=$HOME/plugins:/srv/site/plugins
#+end_src

** Loading no plug-in

=--no-plugins=, or =$ALFE_NO_PLUGINS= set to a true value, makes alfe
load no plug-in at all. It is the way to rule a plug-in out when you
suspect it.

Plug-ins are loaded before the command line is parsed, since their
options must exist for the parser. Two options decide what is loaded,
=--plugin-path= and =--no-plugins=, so alfe finds them in a first pass
over the raw command line; the parser still accepts them.

** When a plug-in fails to load

Each plug-in file is loaded with the package set to =CL-USER=, and the
compiler and loader chatter is captured (shown with =--debug=). A
plug-in that signals an error while loading — a read or compile error, a
registration error — is reported on standard error as

#+begin_example
alfe: warning: plug-in NAME (PATH): MESSAGE
#+end_example

and skipped; alfe carries on, and =--list-plugins= shows the failure and
its reason. Registration fails when NAME does not match the file the
plug-in was loaded from, when one of its options breaks the naming rules
(see [[#plugin-writing][Writing a plug-in]]), or when it names a hook this alfe does not
have — a plug-in written for another alfe version finds that out when it
is loaded, not in the middle of a run.

** The EPURE plug-in
:PROPERTIES:
:CUSTOM_ID: plugin-epure
:END:

EPURE is the SNCF Réseau vertical application (menus, profile, SCHMS+)
that the site's CAD sessions run under. The =epure= plug-in launches
BricsCAD or AutoCAD the way the site's =scripts/bricscad-epure= and
=scripts/autocad-epure= do: with the =Epure= user profile, from the CAD's
=UserDataCache= directory, running EPURE's control script; and it
arranges for that script to run before alfe's own runtime is loaded. It
replaces the legacy =autolisp --epure=. (Before the plug-in system,
alfe accepted =--epure= and did nothing with it.)

It applies to =--bricscad= and =--autocad= and is *MS-Windows only*. On
another OS, and under =--clautolisp=, =--epure= is ignored with a warning
suggesting =--epuree=, the EPUREE emulation, which does run there; the run
itself goes on, so a script shared between machines still works.

| Option / variable                                 | Meaning                                                   |
|---------------------------------------------------+-----------------------------------------------------------|
| =--epure=, =$AUTOLISP_EPURE=                      | Activate the plug-in (the variable: set to a true value). |
| =--epure-profile NAME=, =$AUTOLISP_EPURE_PROFILE= | The CAD user profile to run under (default =Epure=).      |
| =--epure-script FILE=, =$AUTOLISP_EPURE_SCRIPT=   | EPURE's control script (default below).                   |

An explicit option wins over its variable. =--epure-profile= and
=--epure-script= are usage errors unless the plug-in is active (see
[[#plugins][Plug-ins]], /Activating a plug-in/).

The default control script is

- =%APPDATA%\sncf\epure\epure 2022_b\control_path_epure_2022.scr= for
  BricsCAD;
- =%APPDATA%\sncf\epure\epure 2022\control_path_epure_2022.scr= for
  AutoCAD.

When the script does not exist the run stops with a
=backend-bootstrap-error= naming the path (exit status 69,
=EX_UNAVAILABLE=) — unless it is a =--dry-run=.

*** How the control script is run

Despite its =.scr= name, EPURE's control script is *AutoLISP source*: it
reads =VENDORNAME= and loads EPURE's =.des= (BricsCAD) or =.vlx=
(AutoCAD) accordingly. So alfe =LOAD=s it, and =run.scr= reads

#+begin_example
(load "C:/Users/.../AppData/Roaming/sncf/epure/epure 2022_b/control_path_epure_2022.scr")
(load "C:/.../run-common.lsp")
#+end_example

=LOAD= returns, so the line after it — alfe's own runtime — runs. The
earlier spelling nested a =._SCRIPT= inside =run.scr= instead, inherited
from the legacy wrapper on the assumption that control comes back from
one. On BricsCAD V25 it does not: =run.scr= began and stopped there,
BricsCAD sitting at =BOOTING= until the timeout, while the same script
without EPURE ran to completion. AutoCAD's COM bridge still sends
=._SCRIPT= through =SendCommand=, where it works.

*** EPURE is slow to load, and alfe waits for it

Loading EPURE's =.des= / =.vlx= and the vertical application's menus
takes minutes: 174 s to READY on the project's Windows runner (BricsCAD
V25, 2026-09-25), against a 30 s backend default. So when =--epure= is
active and you named no =--timeout=, alfe waits *420 s* instead, and
says so under =--verbose=. An explicit =--timeout= is yours and is left
alone.

The path is checked before anything is launched. It is stable for a
given EPURE version, so a missing file means EPURE is not installed —
or that its version moved and the directory (=epure 2022_b=) is no
longer the right one. Either way alfe stops and says which path it
looked for; =--epure-script FILE= names another.

*** What has been verified, and where

On the project's Windows runner (=verify:epure:windows=, 2026-09-25),
with EPURE 2022_b installed:

- =alfe --autocad --epure= runs the action and exits with its status
  (AutoCAD 2022, COM automation).
- =alfe --bricscad --epure= (BricsCAD V25 fr_FR, =/b= batch script) is
  what exposed the nested-=._SCRIPT= problem above. With =LOAD= in its
  place it reaches READY in about 30 s and runs the action.
- *EPURE's own functions answer inside the session, on both CADs.* By
  hand on the runner (alfe 2.2.134, 2026-09-28), with no other CAD
  running, both of

  #+begin_src sh
    alfe -norc --autocad --epure -x '(print (com_way "\\foo"))'
    alfe -norc --bricscad --epure -x '(print (com_way "\\foo"))'
  #+end_src

  work; and =verify:epure-api:windows= (alfe 2.2.141) found =com_way=
  and =com_tl_continu= (EPURE's =COM/lisp/SNCF_Com.lsp=) on AutoCAD and
  on BricsCAD, with the same nine of 24 catalogued EPURE names present
  on both. Functions of a module EPURE loads on demand — the
  save-parameters dialog's =Sauvprm.lsp=: =toutes_options=,
  =f_DateHeure_UTC= — are *not* there in a fresh session, on either CAD.
- Run one CAD at a time: an AutoCAD started while the previous run's CAD
  was still exiting failed before READY (exit 4 then; 69 since alfe
  2.2.159).
- =--mode automation= is *not* the answer for BricsCAD, and is not
  wanted in any case: =--epure= exists for GUI work. On the runner the
  COM bridge hung at attach/create even *without* EPURE, so BricsCAD COM
  automation is a separate matter from this plug-in.

Two assumptions inherited from the legacy wrapper remain to be confirmed
separately: that a =._SCRIPT= nested in a =/b= script gives control back
to the outer script, and that COM =SendCommand= preserves the order of
two sends. AutoCAD's result above is consistent with the second.

*Why the mode matters.* EPURE is a full-GUI application: it needs the
CAD's profile, menus and CUIX. accoreconsole (AutoCAD's batch mode) has
neither a GUI nor profiles. So:

| Backend, mode                           | What =--epure= does                                                                                                                                                                                                             |
|-----------------------------------------+---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| BricsCAD, =batch= (the default)         | Starts =bricscad.exe [template] /p PROFILE /b run.scr= from =UserDataCache=. The =/Automation= switch, which hides the main window, is *dropped*. =run.scr= =LOAD=s the control script, then loads =run-common.lsp=. |
| BricsCAD, =--mode automation= (COM)     | The bridge tries to activate the profile through =Preferences.Profiles= (a failure is written to the errors file and the run carries on with the current profile), and sends =._SCRIPT= before the load.                        |
| AutoCAD, =automation= (COM)             | The default under =--epure=. The bridge activates the profile and sends =._SCRIPT= before the load.                                                                                                                             |
| AutoCAD, =--mode batch= (accoreconsole) | Refused: usage error (exit status 64), "EPURE requires the full AutoCAD GUI; accoreconsole (--mode batch) has no profile support. Use --mode automation."                                                                                                              |

Under COM the run-time is loaded into the GUI session, and its server
loop keeps the CAD's UI thread busy for as long as alfe drives it: the
GUI is blocked for the duration of the run. That is acceptable for a
scripted run, not for an interactive one.

#+begin_src sh
alfe --bricscad --epure -x '(princ "ok")'
alfe --autocad --epure --epure-profile Epure -l check.lsp
alfe --bricscad --epure --epure-script 'D:\epure\control_path.scr' -l check.lsp
#+end_src

*Not validated on real CADs.* The plug-in was written and tested against
the mock CAD, =--print-command= and an OS override, not against EPURE
itself. Two assumptions come from the legacy wrapper and have not been
re-checked on a real installation: that a =._SCRIPT= nested in a =/b=
script returns control to the outer script (so the =(load …)= after it
runs), and that two consecutive COM =SendCommand= calls run in order. If
the first does not hold, =--mode automation= (COM) is the fallback under
BricsCAD too. Also unchecked: that dropping =/Automation= is right, that
the default control-script paths — which name EPURE 2022 — match your
installation (use =--epure-script= when they do not), and that the GUI
stays usable after the run-time is loaded. The validation on real CADs
is tracked as =alfe-plugin-epure-windows-validation=.

** The EPUREE plug-in
:PROPERTIES:
:CUSTOM_ID: plugin-epuree
:END:

EPUREE is an AutoLISP emulation of the public EPURE API, for BricsCAD on
macOS and Linux, where EPURE itself does not exist, and for tests. It is
packaged as the ALPM (AutoLISP package manager) system =epuree=:
=epuree.alpm= at the root of the EPUREE repository. The =epuree= plug-in
loads it into the engine before anything else the plan does. It applies
to every backend and every OS.

| Option / variable                   | Meaning                                                                                                                         |
|-------------------------------------+---------------------------------------------------------------------------------------------------------------------------------|
| =--epuree=, =$AUTOLISP_EPUREE=      | Activate the plug-in (the variable: set to a true value).                                                                       |
| =--epuree-path DIR=, =$EPUREE_PATH= | A directory, searched recursively, that ALPM is told holds =epuree.alpm=. May be repeated; =$EPUREE_PATH= is a PATH-style list. |
| =--epuree-alpm FILE=, =$ALPM_LSP=   | The =alpm.lsp= to load (default below).                                                                                         |

An explicit option wins over its variable. =--epuree-path= and
=--epuree-alpm= are usage errors unless the plug-in is active.

Without =--epuree-alpm=, =alpm.lsp= is looked for in =$ALPM_LSP=,
=PREFIX/share/autolisp/= (PREFIX being the installation prefix of the
running executable), =/opt/local/share/autolisp/=,
=/usr/local/share/autolisp/= and =~/.local/share/autolisp/=. When it is
nowhere, the run stops with a usage error listing the places tried.

The plug-in puts =eval= actions in front of the action plan — so in front of
your init files and actions — and they show in =--dry-run=:

1. for each installed EPUREE, =PREFIX/share/epuree/= (PREFIX being the
   installation prefix of the running executable, =/opt/local=,
   =/usr/local= or =~/.local=) that exists, append =PREFIX/share/epuree/...=
   (=\...= on MS-Windows: the directory and its subdirectories) to
   =TRUSTEDPATHS=, unless it is already there, so that SECURELOAD lets EPUREE's
   files load. Where =TRUSTEDPATHS= is read-only (BricsCAD V26), the refusal
   is ignored and the run goes on;
2. load =alpm.lsp=;
3. one =(alpm-register-directory DIR T)= for each =--epuree-path=
   directory;
4. =(alpm-load-system "epuree" nil)=;
5. =(epuree-initialize)=.

Loading the system only defines; =(epuree-initialize)= is what does the rest
of what =(load "load_epuree")= does: it installs the path-separator and
Windows-environment shims and anchors the bundle root. Steps 4 and 5 together
are equivalent to =(load "load_epuree")=.

Because these are ordinary plan actions, the engine evaluates them
itself, identically under clautolisp, BricsCAD and AutoCAD, and a failure
fails the run before your script starts.

#+begin_src sh
alfe --epuree --epuree-path ~/src/epuree -l check.lsp
alfe --epuree --epuree-path ~/src/epuree --dry-run -x '(princ 1)'   # see the actions
alfe --bricscad --epuree --epuree-alpm /opt/alpm/alpm.lsp -l check.lsp
#+end_src

** Writing a plug-in
:PROPERTIES:
:CUSTOM_ID: plugin-writing
:END:

A plug-in is one Common Lisp file. It defines its own package, registers
itself with =define-plugin= and adds hooks with =define-plugin-hook=. The
API is the set of exported symbols of the package =ALFE.PLUGIN=. The two
plug-ins that ship with alfe (=plugins/epure/epure.lisp= and
=plugins/epuree/epuree.lisp= in the alfe source tree) are written with
it.

*** A first plug-in

This plug-in defines a flag and an option with an argument, and greets
before the action plan runs. The option names ~--hello~ and
~--hello-name~ exist only in this example.

#+begin_src lisp
(defpackage #:alfe.plugin.hello (:use #:cl #:alfe.plugin))
(in-package #:alfe.plugin.hello)

(define-plugin "hello"
  :version "1.0.0"
  :description "Greet before the plan runs."
  :options ((:flag  "--hello"      :activates t :doc "Enable the greeting.")
            (:value "--hello-name" :key :name :arg "NAME" :default "world"
                                   :doc "Whom to greet.")))

(define-plugin-hook "hello" :plan (ctx plan &key backend)
  (declare (ignore backend))
  (cons (alfe.backend:action-eval
         (format nil "(princ ~A)"
                 (autolisp-string-literal
                  (format nil "Hello, ~A!~%" (plugin-option :name)))))
        plan))
#+end_src

Save it as ~$HOME/.local/share/clautolisp/plug-in/hello/hello.lisp~ — the
directory and the file are named for the plug-in, and registration fails
when the name in =define-plugin= is not the name of the file. Then:

#+begin_src sh
alfe --list-plugins                            # hello is listed
alfe --hello --hello-name Ada -x '(+ 1 2)'     # prints "Hello, Ada!" first
alfe --compile-plugin ~/.local/share/clautolisp/plug-in/hello/hello.lisp
#+end_src

In the example, ~--hello~ has =:activates t=, so giving it activates the
plug-in; ~--hello-name~ stores its value under the key =:name=, which
=(plugin-option :name)= reads back. Giving ~--hello-name~ without ~--hello~
(or =--plugin hello=) is a usage error naming ~--hello~. The =:plan= hook
is a /filter/: it receives the action plan and returns a new one, here
with one =eval= action added in front. What =--dry-run= prints is that
plan.

*** Registering: =define-plugin=

#+begin_src lisp
(define-plugin NAME
  :version     "1.0.0"                 ; string, shown by --list-plugins
  :description "one line"
  :applies-to  (:bricscad :autocad)    ; or :all (the default)
  :priority    0                       ; lower runs first; ties: load order
  :options     (OPTION-SPEC ...))
#+end_src

NAME is a string (a symbol or keyword is downcased). Registering a name
already registered replaces the earlier registration, which is how tests
reload a plug-in; two /files/ of the same name are never both loaded.
=:applies-to= lists the backends (=:clautolisp=, =:bricscad=, =:autocad=)
whose runs the plug-in's hooks are called for; the plug-in is still
loaded, and its options still parse, under any backend.

*** Options a plug-in defines

An =OPTION-SPEC= is =(KIND "--long" . PLIST)=. The values in the plist
are evaluated, so quote list literals.

| Kind      | Meaning                                                          |
|-----------+------------------------------------------------------------------|
| =:flag=   | takes no argument; its value is =t=                              |
| =:value=  | takes one argument (~--opt V~ or ~--opt=V~)                      |
| =:repeat= | like =:value=, may be given several times; its value is the list |

| Key          | Meaning                                                                                                                         |
|--------------+---------------------------------------------------------------------------------------------------------------------------------|
| =:key=       | keyword under which the value is stored (default: the option name without the ~--NAME-~ prefix, =:enabled= for ~--NAME~ itself) |
| =:activates= | true: giving this option, or its environment default, activates the plug-in                                                     |
| =:arg=       | metavariable shown by =--help=                                                                                                  |
| =:doc=       | one-line description shown by =--help= and =--list-plugins=                                                                     |
| =:env=       | environment variable supplying a default                                                                                        |
| =:default=   | value used when neither the command line nor the environment gave one                                                           |
| =:parser=    | function from string to value; signals =cli-usage-error= on a bad value                                                         |
| =:choices=   | list of accepted strings, checked before =:parser=                                                                              |

*Naming rules.* A plug-in ~NAME~ may define only the long options ~--NAME~
and ~--NAME-…~, and no short option: single-dash options are reserved to
alfe. A name that collides with an alfe option, or with an option of a
plug-in registered earlier, is a registration error naming both.

*Resolution and activation* are as described in /Activating a plug-in/:
right after the command line is parsed, for each active plug-in, the
command line wins, then the environment variable, then the default.
=(plugin-option KEY)= returns the resolved value stored under =:key= KEY.

*** Hooks

A hook point has a name, a /kind/, a primary /value/ and keyword
/details/. A handler is =(lambda (ctx value &key … &allow-other-keys) …)=,
defined with =define-plugin-hook=, which adds =&allow-other-keys= itself:
name only the keywords you use. The kind says what a handler's result
means.

| Kind      | Handler's result                                                      |
|-----------+-----------------------------------------------------------------------|
| /event/   | ignored; the handler acts by side effect, or by signalling            |
| /filter/  | the new value, passed to the next handler; the last one is the result |
| /collect/ | a list; the lists of all handlers are concatenated                    |

Handlers run in =:priority= order (ties: registration order), and only
for plug-ins that are active and whose =:applies-to= holds the run's
backend. A handler may call =(deactivate-plugin ctx)=: the remaining
handlers of that plug-in are then skipped. The hooks, in the order a run
meets them:

| Hook                   | Kind    | Called                                                                                          | Value received; what a handler can change                     |
|------------------------+---------+-------------------------------------------------------------------------------------------------+---------------------------------------------------------------|
| =:cli-parsed=          | event   | after parsing and =--cad= selection, before the backend is resolved                             | the parsed options: mutate them, or signal =cli-usage-error=  |
| =:backend-selected=    | event   | after the backend is resolved (and detected, unless a dry run)                                  | the backend object: veto it by signalling                     |
| =:plan=                | filter  | on the effective plan: init files, user actions, terminator; it is also what =--dry-run= prints | the list of actions: return another one                       |
| =:dry-run-report=      | collect | after the plan, under =--dry-run=                                                               | NIL: return strings to print                                  |
| =:workdir-prepared=    | event   | once the workdir exists                                                                         | the workdir                                                   |
| =:run-common-prelude=  | collect | CAD backends: in =run-common.lsp=, after the injected globals, before the bootstrap is loaded   | NIL: return AutoLISP source to insert                         |
| =:run-common-epilogue= | collect | CAD backends: after the runtime is loaded, before its server loop                               | NIL: return AutoLISP source to insert                         |
| =:launcher-lines=      | collect | CAD backends: once per launcher-script slot (below)                                             | the slot: return lines for it                                 |
| =:launcher-script=     | filter  | CAD backends: the whole launcher script, just before it is written                              | the script text: return another one                           |
| =:launch-argv=         | filter  | CAD backends: the command line, just before the process is spawned                              | the argument list: return another one                         |
| =:launch-options=      | filter  | CAD backends: just before the spawn                                                             | the plist =(:directory D :environment E)=: return another one |
| =:engine-started=      | event   | the engine reached READY                                                                        | the session                                                   |
| =:pre-action=          | event   | before each action                                                                              | the action                                                    |
| =:post-action=         | event   | after each action                                                                               | the action; its result is in the details                      |
| =:pre-shutdown=        | event   | before the engine is shut down                                                                  | the session; the reason is in the details                     |
| =:post-shutdown=       | event   | after the shutdown, before the workdir is removed                                               | the session; the workdir is in the details                    |
| =:exit-code=           | filter  | for a run that reached the end of its plan                                                      | the exit code, an integer: return another one                 |
| =:error=               | event   | an error is about to be reported and turned into an exit code                                   | the condition; the phase is in the details                    |

In the =:launch-options= plist, =:directory= is the working directory
the CAD is spawned in (a pathname, or NIL) and =:environment= the changes
to its environment, as =(NAME . VALUE)= pairs, VALUE NIL to unset.

The keyword details each hook receives (=:backend=, =:variant=, =:index=,
=:result=, …) are listed in the specification, chapter /Plug-ins/.

=:pre-action= and =:post-action= are called around each action, but only
when an active plug-in registered one of them; otherwise the whole plan
goes to the backend in one call. A CAD backend then evaluates the plan one
action at a time and stops at the first failed action. The clautolisp
backend runs the plan as the same single run it makes without the hooks --
in-process, and in one clautolisp child that stops at each action boundary
under =--backend subprocess= -- so AutoLISP state carries from one action
to the next and the run ends where it would end anyway (a runtime error,
=(exit N)=), whichever transport runs it. =:launcher-lines=, =:launcher-script=,
=:launch-argv= and =:launch-options= are called by the CAD backends only:
the clautolisp backend has no launch step.

*** The run context

A handler receives the /context/ of the run as its first argument. The
special variable =*CONTEXT*= holds it for the whole run (NIL outside a
run, which makes every hook call site a no-op).

| Accessor                  | Meaning                                                     |
|---------------------------+-------------------------------------------------------------|
| =(context-options ctx)=   | the parsed options                                          |
| =(context-backend ctx)=   | the backend keyword (=:clautolisp= when none was requested) |
| =(context-version ctx)=   | alfe's version string                                       |
| =(plugin-option KEY)=     | the calling plug-in's resolved value for =:key= KEY         |
| =(plugin-state ctx KEY)=  | a =setf=-able per-run scratch value of the calling plug-in  |
| =(deactivate-plugin ctx)= | the calling plug-in takes no further part in this run       |

*** Launcher script slots

The engine-side launcher is a script alfe writes in the workdir and
hands to the CAD. =:launcher-lines= is called once per slot, with the
slot as its value and the kind of script (=:scr= or =:vbs=) as the =:kind=
detail; return its lines when the slot is one you care about.

| Kind   | File                                              | Slot           | Position                                                                                      |
|--------+---------------------------------------------------+----------------+-----------------------------------------------------------------------------------------------|
| =:scr= | =run.scr= (BricsCAD batch), the accoreconsole SCR | =:before-load= | immediately before the =(load run-common.lsp)= line                                           |
|        |                                                   | =:after-load=  | after it, before the final =_QUIT= (the load only returns when the session ends)              |
| =:vbs= | =bridge-bricscad.vbs=, =bridge-autocad.vbs=       | =:after-app=   | once the COM application object exists, before waiting for it and before the document is used |
|        |                                                   | =:before-load= | once the document is active, immediately before the =(load run-common.lsp)= is sent           |

SCR lines are script lines: a command, its answers, or an AutoLISP form.
VBS lines are VBScript statements: ASCII only (=cscript= reads the file
as ANSI), variables declared with =Dim=, strings quoted with the helper
=vbs-escape=.

*** Errors raised by a hook

A =cli-error= (=cli-usage-error= is one) or a =backend-error= signalled by
a handler passes through unchanged, with its usual exit status; a
=cli-error= may carry its own (=:status clautolisp.sysexits:+ex-noinput+=
for a file an option names that is not there). Any other Lisp error
becomes an =alfe.error:plugin-error=, reported as =plug-in NAME, hook
:HOOK: …= with exit status 70 (=EX_SOFTWARE=).

* The *AUTOLISP-…* globals

User AutoLISP code can read these globals to branch on session
state:

| Variable                       | Meaning                                                |
|--------------------------------+--------------------------------------------------------|
| =*AUTOLISP-FRONTEND*=          | =ALFE= when alfe is the entry point, =CLAUTOLISP= when clautolisp is invoked directly. |
| =*AUTOLISP-BACKEND*=           | The engine running user code: =CLAUTOLISP= / =BRICSCAD= / =AUTOCAD=. |
| =*AUTOLISP-HELP*=              | The --help banner of the front-end as a string.        |
| =*AUTOLISP-DIALECT*=           | =:strict= / =:autocad-2026= / =:bricscad-v26= / =:clautolisp=. |

| =*AUTOLISP-FILE-ENCODING*=     | Active source-file encoding (always a string). Empty string =""= means "no preference; fall through to the dialect default" — the documented degenerate case when neither =-Esource= nor any =LC_*= env var resolves an encoding. |
| =*AUTOLISP-TERMINAL-ENCODING*= | Active terminal encoding (always a string, never empty — falls back to =US-ASCII= in the degenerate case). |

The specifications document the full set and their lifetimes.

* Recording a session: =--dribble=

=--dribble= keeps a transcript of a session. A CAD session is the hard kind to
reproduce — a particular drawing, a particular install, a modal dialog nobody
saw — so a record of what was sent and what came back is often the only evidence
there will be.

#+begin_example
alfe --bricscad --dribble -x '(princ (getvar "DWGNAME"))'
alfe --autocad --dribble=/tmp/session.log -l script.lsp
#+end_example

Bare, the file is
=$XDG_STATE_HOME/alfe/dribbles/<backend>/<timestamp>.log= (=~/.local/state/…=
when that variable is unset). The per-backend directory is alfe's own: one
machine drives several engines, and a listing that mixed an AutoCAD session with
a BricsCAD one would hide the difference the transcript is kept for. With
=--dribble=FILE= the file is FILE, *appended to* when it already exists, so a
day's sessions accumulate instead of overwriting each other.

** The format

The same format clautolisp writes, so the two can be read — and diffed — side by
side:

#+begin_example
;; H: alfe 2.2.124 bricscad bricscad-v25
(princ (getvar "DWGNAME"))
;; O: Drawing1.dwg
;; E: a warning the engine printed
;; C: DIVISION-BY-ZERO: Division by zero in /.
#+end_example

- the *header* names *both* versions — alfe's and the engine's — where
  clautolisp's names one. A CAD transcript is only interpretable with both. The
  CAD version is what alfe knows when recording *starts*: the release it
  selected or detected, or =unknown=. It is deliberately not withheld until the
  engine answers, because a CAD start takes tens of seconds and can fail, and a
  transcript that appeared only after a successful start would be missing
  exactly the sessions worth reading;
- *input* — the form alfe sent — is raw and unprefixed;
- =;; O:= is engine output, =;; E:= its error output, =;; C:= a condition
  report, one line each. A line never carries two tags' text: when output and
  error output interleave, the open line is closed first.

** Which backend records, and why it differs

- Under =--autocad= / =--bricscad=, *alfe* records: those engines have no
  dribble of their own, so the transcript is what alfe sees of the conversation.
- Under =--clautolisp=, the request is *forwarded to the engine program*,
  which records its own REPL. That transcript is richer than anything alfe
  could reconstruct from outside -- it has the prompts, the interactor stack
  and the values -- and forwarding means one file per session rather than two
  partial ones. The recorder is the =clautolisp= program's, so a =--dribble=
  run is the program's: alfe runs it as the child even without =--backend
  subprocess= (and =--backend direct --dribble= is a usage error). As with
  =clautolisp=, the recording starts with the REPL: a batch run (=-x= /
  =-l= only) records nothing.

** =--dribble-interactors=

Selects which interactors are recorded: =t= for all, or a comma-separated list
of names (=--dribble-interactors=AUTOLISP,ALDO=). Interactors are a clautolisp
notion — the REPL, the ALDO debugger, the navigator — so the option is forwarded
to =--clautolisp= and *ignored* under the CAD backends, which have no interactor
stack and record the whole session.

* Seeing the CAD command line: =--print-command=

=--print-command= answers "what exactly does alfe launch?". It runs
the whole preparation phase for real — creates the workdir, stages the
runtime and bootstrap LSP, writes =run-common.lsp= and the launcher
(=run.scr=, or the VBScript/AppleScript bridge under
=--mode automation=) — and then, instead of spawning the CAD, prints
the command line it would have spawned:

#+begin_src sh
$ alfe --bricscad --print-command -x "(princ)"
/opt/bricsys/bricscad/bricscad -B /tmp/alfe-bricscad-31337-a1b2c3/run.scr

$ alfe --autocad --mode batch --print-command -l draw.lsp
'C:/Program Files/Autodesk/AutoCAD 2026/accoreconsole.exe' /i C:/T/tpl.dwt /s C:/T/alfe-autocad-2244-f0e9d1/run.scr
#+end_src

Exactly one line goes to stdout — the command, with every argument
quoted for the host shell — so it can be captured directly:

#+begin_src sh
cmd=$(alfe --bricscad --print-command --keep-workdir -x "(princ)")
#+end_src

When a plug-in makes the CAD start in a particular directory (the =epure=
plug-in does: the CAD's =UserDataCache=), the line begins with
=cd DIR &&=, since the command means nothing run from elsewhere.

Everything else (backend, workdir, the raw argv list) is logged at
=--verbose= / =--debug=.

Two things to know:

- *The workdir is deleted on the way out* unless you pass
  =--keep-workdir=. Without it the printed command names a directory
  that no longer exists — fine for reading the argv, useless for
  running it. Combine with =--keep-workdir= (and optionally
  =--write-workdir-path FILE=) when you intend to run the command by
  hand.
- *Running that command yourself is not a full alfe run.* It starts
  the CAD against the staged workdir, and the engine will boot, load
  =run-common.lsp= and reach =READY= — then wait, because nothing is
  driving alfe's side of the file-IPC protocol (no request is ever
  written to =protocol/=, no output is drained). It is a debugging
  aid: it shows the exact switches, binary and script path, and lets
  you reproduce a launch-time failure (licensing, profile, a modal
  dialog) without alfe in the loop.

=--print-command= requires a CAD backend. Under =--clautolisp= there
is no external command line — the engine runs in-process — so alfe
exits 64 (=EX_USAGE=) rather than printing nothing.

It is distinct from =--dry-run=, which resolves nothing, touches no
disk and just prints the action plan.

* Exit status

alfe's exit status says how the run ended, and is the same whichever
transport runs the =clautolisp= engine (=--backend direct= or
=subprocess=). Apart from 1, /N/ and 130, the statuses are the
semi-standard codes of =<sysexits.h>= (see =sysexits.h(3head)=), with the
same values on *every* system, MS-Windows included -- a script that tests
for 66 works everywhere.

| Status | Name             | When                                                                                                    |
|--------+------------------+---------------------------------------------------------------------------------------------------------|
|    =0= | =EX_OK=          | Success.                                                                                                |
|    =1= |                  | The AutoLISP program failed: a runtime error escaped it, on any backend (a CAD request that answered =FAIL=). |
|    /N/ |                  | Under =--clautolisp=: the program's own =(exit N)=, =(quit N)= or =autolisp-set-status N=, unchanged.    |
|   =64= | =EX_USAGE=       | The command line is wrong: an unknown option, a missing argument, an invalid value, conflicting options, a plug-in option without its plug-in, =--host cadtui --backend direct=, =--print-command= without a CAD backend, =--dwg= on a host without drawings, =--autocad --mode batch= without a drawing or with =--epure=, an aldo option (=--on-interrupt=, =--on-quit=, =--debugger-ui=, =--aldb-listen=, =--aldb-stdio=) under a CAD backend, =--aldb-stdio= with =--interactive= or =--aldb-listen=. |
|   =65= | =EX_DATAERR=     | An input is not well formed: a =-l= file or =-x= expression the reader refuses (unbalanced parenthesis, unterminated string, bytes not valid in the source encoding); a =--dwg= file that is not a drawing; a =--compile-plugin= source that does not compile. |
|   =66= | =EX_NOINPUT=     | An input file does not exist or is not readable: the =-l= file, the =--dwg= drawing, the =--epuree-alpm= file, the =--compile-plugin= source. |
|   =69= | =EX_UNAVAILABLE= | The backend, or something it needs, is not there or would not start: the CAD is not installed or not supported on this system, no clautolisp executable for =--backend subprocess=, no accoreconsole, EPURE or alpm.lsp not installed, the DWG native library missing, the CAD launcher died before READY. |
|   =70= | =EX_SOFTWARE=    | An internal error: a defect of alfe, of the engine, or of a plug-in (an error raised by a plug-in hook).  |
|   =71= | =EX_OSERR=       | The clautolisp child process (=--backend subprocess=) could not be started.                            |
|   =73= | =EX_CANTCREAT=   | An output cannot be created: the workdir, the =--dribble= transcript.                                    |
|   =74= | =EX_IOERR=       | An input/output error while reading or writing.                                                         |
|   =75= | =EX_TEMPFAIL=    | The CAD did not answer in time -- READY within =--timeout=, a request, the shutdown -- or a protocol slot stayed busy. Retrying may succeed. |
|   =76= | =EX_PROTOCOL=    | The CAD runtime answered something the file protocol does not allow.                                    |
|  =130= |                  | Interrupted: Control-C under the =quit= interrupt policy (128 + SIGINT).                                 |

The other =<sysexits.h>= codes are not used: alfe looks up no user (67
=EX_NOUSER=) or host name (68 =EX_NOHOST=), needs no system file (72
=EX_OSFILE=), reports an unreadable input file as =EX_NOINPUT= the way
=<sysexits.h>= says rather than as 77 =EX_NOPERM=, and has no
configuration file whose error stops a run (78 =EX_CONFIG=).

Why 1 for a failing program, and not a =<sysexits.h>= code: those codes
say what kept a program from running properly -- a bad command line, a
missing input, an engine that is not there. When everything was in place
and the AutoLISP program itself signalled an error, the /program/
failed, and 1 is what a failing program conventionally returns. Keeping
it at 1 also keeps the meaning of 1 that scripts and CI jobs already test
for.

#+begin_example
$ alfe -l no-such-file.lsp ; echo "exit $?"
clautolisp: The file #P"/home/me/no-such-file.lsp" does not exist: No such file or directory
exit 66
$ alfe -x '(princ' ; echo "exit $?"
clautolisp: <-x>:1:7: read error: Unexpected end of input inside list. [UNEXPECTED-EOF]
exit 65
#+end_example

*Changed in alfe 2.2.159.* The codes were 1 (a failing program, or any
unexpected error), 2 (a usage error, or a =-l= file the =clautolisp=
engine could not open), 3 (backend not available) and 4 (bootstrap,
protocol or plug-in error). A script that tested for 2, 3 or 4 must be
adapted: 2 is now 64 (usage) or 66 (missing file), 3 is 69, and 4 is 69,
75, 76 or 70 depending on the failure.

* Environment variables

Every variable alfe reads is listed here. This does *not* include the
variables of the engines alfe drives: for alfe, clautolisp is a CAD like
AutoCAD and BricsCAD, and each engine's own environment belongs to that
engine's documentation. What does belong here is anything alfe itself
consults, including what it *passes on* to an engine.

** Engine location and launch
- =$ALFE_CLAUTOLISP_BIN= :: the =clautolisp= executable the clautolisp
  backend runs as a subprocess. Set it to test a build that is not the
  installed one. Unset, an installed alfe runs the =clautolisp-sbcl=
  installed in the same prefix; the whole search order is under
  /cadtui/ in the hosts chapter.
- =$ALFE_BOOTSTRAP_LSP=, =$ALFE_RUNTIME_LSP= :: the two CAD runtime
  files, =autolisp-bootstrap.lsp= and =autolisp-remote-io.lsp=, in
  place of the installed ones. A value naming no file is ignored. See
  /The CAD runtime files/ above.
- =$AUTOCAD_EXE=, =$AUTOCAD_ACCORECONSOLE=, =$BRICSCAD_EXE= :: explicit
  engine binaries, bypassing detection.
- =$AUTOCAD_COM_MODE=, =$BRICSCAD_COM_MODE= :: =auto= (default) or
  =off=. =off= is the batch path, without COM.
- =$AUTOCAD_PROGID= :: the COM ProgID =--mode automation= asks for, used
  verbatim and without a registry check — the way to name a release alfe
  does not know, or to pin one on a host with several. Unset, alfe
  resolves the selected release's own ProgID. See /Which AutoCAD
  automation actually talks to/.
- =$AUTOLISP_BRICSCAD_PROFILE=, =$BRICSCAD_PROFILE= :: the BricsCAD
  profile to launch under; the first takes precedence. Unset means the
  engine's own default profile.
- =$ALFE_BRICSCAD_STARTUP_DELAY= :: overrides the =STARTUPWAIT= given to
  BricsCAD — the grace period before alfe expects the engine to answer.
- =$ALFE_ENABLE_MACOS_AUTOMATION= :: opts into BricsCAD =--mode
  automation= on macOS. Off by default: macOS refuses that mode
  immediately (=:no-automation=), since =--mode batch= is the
  well-tested, documented macOS path. Any non-empty value other than
  ="0"= enables it (Windows is unaffected either way — =--mode
  automation= has always worked there). On macOS, automation mode drives
  BricsCAD by typing into its command-line console with synthetic
  keystrokes (AppleScript / System Events), which needs an interactive
  GUI session *and* Accessibility (TCC) permission granted to the
  process running =alfe= — it cannot work headless or in an ordinary CI
  job without that grant.
- =$ALFE_NO_CUI_REPAIR= :: when set and non-empty, do *not* quarantine a
  corrupt per-user =default.cui=. alfe normally renames one aside (never
  deletes) so BricsCAD regenerates it, because the alternative is a
  startup dialog that stalls a batch launch with nobody to dismiss it.

** Plug-in loading
See [[#plugins][Plug-ins]].

- =$ALFE_PLUGIN_PATH= :: extra plug-in roots, a PATH-style list
  (separated by =:=, or by =;= on MS-Windows), searched after the
  directories given with =--plugin-path=.
- =$ALFE_PLUGINS= :: comma-separated names of the plug-ins to activate in
  every run, like =--plugin= given once per name.
- =$ALFE_NO_PLUGINS= :: set to a true value (=1=, =yes=, …), loads no
  plug-in, like =--no-plugins=.

** Encoding
- =$ALFE_AUTOCAD_CONSOLE_ENCODING= :: the AutoCAD console encoding used
  when =-Ecadstdio= is not given, before falling back to the robust
  =ISO-8859-1= default. See /Encoding/ above.

** Conformance corpus
Both gate scenarios that a plain =make test= must never run, so the unit
lane stays green on a machine with no CAD at all.

- =$ALFE_VENDOR_CONFORMANCE= :: set to a non-empty value to actually
  drive the vendor CAD through the corpus. Without it the
  =:bricscad-only= and =:autocad-only= scenarios are skipped rather than
  attempted.
- =$AUTOLISP_LEGACY= :: a *path* to a legacy engine the runner can
  spawn — not a flag. The =:parity= scenarios run only when it names a
  file that exists.

** Consulted, not configured
=$HOME=, =$PATH=, =$TMPDIR=, =$TEMP=, =$TMP= and =$APPDATA= are read for
the usual platform locations, =$XDG_DATA_HOME= and =$XDG_DATA_DIRS= for
the plug-in roots ([[#plugins][Plug-ins]]), and =$NO_COLOR= disables ANSI colour.

* Troubleshooting

** "AutoCAD 2022 was requested, but no COM server for it is registered"

=--mode automation= needs that release's COM registration, and it is
either absent or unusable (a CLSID whose =LocalServer32= cannot be
read). The message lists every ProgID tried and why each was rejected.
alfe stops rather than fall back to the generic =AutoCAD.Application=,
which may belong to another release.

Repair the AutoCAD installation's COM registration (a repair install, or
=acad.exe /regserver= from an elevated prompt), or name the server
yourself with =$AUTOCAD_PROGID=AutoCAD.Application.24.1=. =--mode batch=
uses =accoreconsole= and needs no COM registration at all.

** "AutoCAD COM bridge (cscript) exited before READY"

The COM bridge failed to attach to or create an AutoCAD. The message
carries the stage (=getobject= / =createobject=), the ProgID asked for,
and the COM error in decimal and hexadecimal with its description —
=429 (0x1AD) ActiveX component can't create object= is a registration
that resolves to no runnable server; try the versioned ProgID as above.
What exited is =cscript=, the bridge: whether =acad.exe= itself started
is what the =ATTACHED= / =CREATED= flags report.

** "did not reach READY within N s ... the engine never moved past BOOTING"

The CAD was launched and published *nothing*: =BOOTING= is what alfe itself
writes to =status.txt= before the launch, so seeing it still there means the
engine never got as far as loading =run-common.lsp=.

On *Windows* that is almost always a *startup dialog waiting for input*.
BricsCAD asks which drawing and which profile to use when given neither, and
under a hidden main frame (=/Automation=) the dialog is invisible as well as
unanswerable — the CAD sits there for ever and the job's only symptom is the
timeout. Give it a drawing (=--dwg=) and a profile
(=$AUTOLISP_BRICSCAD_PROFILE=, e.g. the clean =<<Profil sans nom>>=). On
*macOS* the same shape comes from the Accessibility prompt that blocks the
first keystroke an un-permitted =osascript= sends: grant the terminal
Accessibility permission once, in front of the machine.

The wording matters, so it is worth reading exactly: =launcher still running=
alone means the engine *did* start and stalled later, which is a different
problem — look at the request, not the launch. If the phrase instead names an
exit code, the launcher itself died and its output is quoted with it.

A cold start can legitimately take minutes (174 s to READY on the project's
Windows runner), so raise =--timeout= before concluding anything; this
diagnosis is about a CAD that produced *no* transition at all.

** =alfe= prints "Backend ... is not registered"

You selected an explicit backend that isn't compiled into this
build. Usually means a CAD backend is referenced on a host build
that doesn't ship it. Pick =--clautolisp= or omit the flag for
the default.

** =alfe --bricscad= fails on Linux

BricsCAD ships for Linux but the wrapper integration is currently
macOS- and Windows-only. Track =alfe-bricscad-linux.issue=.

** =alfe --autocad= fails on macOS or Linux

AutoCAD is not distributed for those platforms. =alfe= exits with
code 3 and a clear message. Use =--bricscad= (where supported) or
=--clautolisp= instead.

** "alfe with no flags is suddenly different"

Yes — see the [[#backend-selection][Backend selection]] section.
Auto-detection of installed CADs has been removed. Set
=$ALFE_BACKEND_OVERRIDE= in your shell init if you want a CAD
backend by default.

** "not launched: required CAD runtime file not found"
alfe could not find =autolisp-bootstrap.lsp= or =autolisp-remote-io.lsp=,
so it did not start the CAD. Without these files the CAD would boot
and never answer. The message lists each missing file and every path
tried, starting with =share/alfe/runtime/= under the prefix alfe
derived from its own location, and it names the running executable.
Either install the files there, or point =$ALFE_BOOTSTRAP_LSP= /
=$ALFE_RUNTIME_LSP= at them.

** A long =(eval …)= on a CAD backend is aborted after ~30 s

By default the per-request timeout is *RUNNING-aware*: it bounds only
the time until the engine acknowledges the request (=RUNNING N=). Once
that acknowledgement is seen and the CAD process is alive, alfe keeps
waiting — a legitimately long computation is not killed on wall-clock,
and a dead engine still aborts promptly. If you still want a firm upper
bound (or need to raise a slow-launch handshake window), pass
=--timeout N= or set =$AUTOLISP_WAIT_SECS=N=; an explicit value is a
*hard cap* — =--timeout 1= aborts a long eval, =--timeout 600= grants it
ten minutes. (Before alfe 1.7.3 =--timeout= was parsed but ignored on
the CAD backends, so a long eval was aborted at the fixed 30 s default.)

** A plug-in option is refused: it requires its plug-in

=--epure-profile=, =--epure-script=, =--epuree-path=, =--epuree-alpm=
and every other option a plug-in defines are usage errors (exit status
64) while their plug-in is not active. The message names the option that
activates it — for =--epure-profile=, that is =--epure=. Add that
option, or activate the plug-in by name: =--plugin epure=, or
=$ALFE_PLUGINS=epure= in your shell init. See /Activating a plug-in/.

** =--list-plugins= shows nothing, or reports a plug-in as failed

/Nothing./ alfe found no plug-in in any root. Read the search path that
=--list-plugins= prints, and check that the plug-in sits in a directory
named for it (=NAME/NAME.lisp=, not =NAME.lisp= directly under the root),
that =$ALFE_NO_PLUGINS= is not set to a true value, and, for the two
plug-ins that ship with alfe, that alfe was installed with =make install=
(they go under =$(PREFIX)/share/clautolisp/plug-in/=). A root that is not
on the standard path can be added with =--plugin-path= or
=$ALFE_PLUGIN_PATH=.

/Failed./ The listing gives the reason, and every run repeats it on
standard error as =alfe: warning: plug-in NAME (PATH): MESSAGE=. The
usual causes are a read or compile error in the file, a name that
differs from the file's, an option that breaks the naming rules
(=--NAME= or =--NAME-…= only, no short option) or collides with another
option, and a hook name this alfe does not know — typically a plug-in
written for another alfe version. Run with =--debug= to see the compiler
and loader output alfe captured. A compiled file made for another alfe
version or the other implementation is ignored without a word unless you
give =--verbose=; recompile it with =--compile-plugin=.

** =--epure= is given and nothing happens

The =epure= plug-in acts only on MS-Windows and only with =--bricscad=
or =--autocad=. On any other system, and under =--clautolisp= — the
default when nothing names a backend — alfe ignores =--epure= silently.
Run with =--verbose= to see the message saying so, and name the backend.

** A run under EPURE or EPUREE stops before the script starts

- EPURE control script not found (exit status 69): the message names the
  path looked at. Install EPURE, or point =--epure-script= (or
  =$AUTOLISP_EPURE_SCRIPT=) at the script. A =--dry-run= does not check.
- =--autocad --mode batch --epure= is refused (exit status 64):
  accoreconsole has no profile support. Drop =--mode batch=; AutoCAD
  then runs under COM automation.
- =alpm.lsp= not found under =--epuree=: exit status 66 when the file
  named by =--epuree-alpm= is not there, 69 when none is installed in the
  places tried (the message lists them). Give =--epuree-alpm FILE=, or set
  =$ALPM_LSP=.
- =plug-in NAME, hook :HOOK: …= (exit status 70): a plug-in's hook raised
  an error that is not a usage or backend error. It is a defect of that
  plug-in.
