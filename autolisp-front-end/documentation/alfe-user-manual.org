* Introduction

=alfe(1)= is the unified command-line front-end for AutoLISP. It
drives three backends behind a single command-line shape:

- =clautolisp= — an in-process AutoLISP evaluator that ships with
  alfe. No CAD required. The default backend.
- =bricscad= — BricsCAD V26+, via batch (=-b run.scr=) or COM
  /AppleScript automation. On MS-Windows, =--mode batch= launches
  BricsCAD with its main frame window hidden (the =/Automation=
  startup switch); this is just a hidden-UI batch run and does *not*
  select the COM =--mode automation= backend.
- =autocad= — AutoCAD 2026+, via =accoreconsole= batch or COM
  automation (MS-Windows only).

The same =-x EXPR=, =-l FILE=, =--dialect NAME= and =--host NAME=
options work against every backend. Programs written for alfe run
unchanged whether you point them at the local clautolisp engine
or at a real CAD session.

* Installation

The build target produces two binaries: =alfe-sbcl= (preferred,
faster startup) and =alfe-ccl= (Clozure CL backup, when SBCL is
unavailable). The =install= rule places them under
=$(PREFIX)/bin/= along with a wrapper =alfe= that resolves to one
or the other:

#+begin_src sh
cd autolisp-front-end
make build
sudo make install PREFIX=/opt/local
#+end_src

After install:

#+begin_src sh
alfe --help                    # full option reference
alfe -x "(print (+ 1 2))"      # one-shot eval, prints "3" then exits
alfe -x "(+ 1 2)"              # silent — see "Action output semantics" below
alfe -l script.lsp             # load a file, default backend
alfe                           # interactive REPL, default backend
#+end_src

** The CAD runtime files

The AutoCAD and BricsCAD backends load two AutoLISP files into the CAD:
=autolisp-bootstrap.lsp= and =autolisp-remote-io.lsp=. =make install=
puts them in =$(PREFIX)/share/alfe/runtime/=. A release archive has the
same tree, and can be unpacked under any directory.

alfe finds them from where its own executable is, when it runs. This
works whether the binary is =$(PREFIX)/bin/alfe-sbcl= or sits under
=$(PREFIX)/libexec/= behind the =bin/alfe= launcher, and through a
symbolic link. The current directory plays no part. Neither does the
directory alfe was built in. The search order is:

1. =$ALFE_BOOTSTRAP_LSP= / =$ALFE_RUNTIME_LSP=, when they name an
   existing file;
2. =share/alfe/runtime/= under the installation prefix;
3. the copies in the source tree, for a development build;
4. =/opt/local=, =/usr/local= and =/usr= (=share/alfe/runtime/=).

If either file cannot be found, the CAD is not started. alfe exits
with status 4 and lists every path it tried (see /Troubleshooting/).

** The installed plug-ins

The =install= rule also places the plug-ins that ship with alfe —
=epure= and =epuree= — under =$(PREFIX)/share/clautolisp/plug-in/= and
compiles them with the alfe it has just installed. =alfe --list-plugins=
shows what alfe finds; see [[#plugins][Plug-ins]].

** Backend flags

The =--clautolisp= / =--bricscad= / =--autocad= flags select a
specific backend; absent a flag, the in-process clautolisp engine
is used (see [[#backend-selection][Backend selection]]).

* Backend selection
:PROPERTIES:
:CUSTOM_ID: backend-selection
:END:

When no backend flag is given, alfe defaults to the =clautolisp=
in-process engine. This is a change from the historical
auto-detection: CAD backends are now NEVER selected automatically
— they require an explicit =--autocad= / =--bricscad= flag (or
an environment override).

** Algorithm

#+begin_example
if --bricscad, --autocad or --clautolisp is explicit:
    use that backend
else if $ALFE_BACKEND_OVERRIDE is set:
    use that backend
else if $AUTOLISP_BACKEND is set:
    use that backend (legacy alias)
else:
    backend = clautolisp     ; default on every system
#+end_example

** Why not auto-detect?

A host with both BricsCAD and AutoCAD installed got
order-dependent results from the historical auto-detect (whichever
backend's =DETECT= method was probed first won). With the new
rule, =alfe= with no flags always means "talk to the in-process
clautolisp engine" — no probing, no surprises, no dependency on
CAD installation state.

** Pinning a default backend per shell

Users who want a CAD backend selected by default can set
=$ALFE_BACKEND_OVERRIDE= once in their shell init:

#+begin_src sh
# ~/.zshrc or ~/.bashrc
export ALFE_BACKEND_OVERRIDE=bricscad
#+end_src

Explicit flags still win — =alfe --clautolisp -x "(+ 1 2)"= runs
under clautolisp even with the override set.

** Selecting a specific CAD install

=--clautolisp= / =--bricscad= / =--autocad= pick the *latest* install
of a backend. When several versions or localisations are present and
you need a particular one, use =--cad DENOTATION=.

=alfe --list-cad-programs= scans the host and prints every installed
CAD with its canonical denotation:

#+begin_example
acad-2026                /Applications/Autodesk/AutoCAD 2026/…/MacOS/AutoCAD
accoreconsole-2026       /Applications/Autodesk/AutoCAD 2026/…/AcCoreConsole
bricscad-v26             /Applications/BricsCAD V26.app/Contents/MacOS/bricscad
clautolisp               (embedded in alfe)
#+end_example

Denotation grammar:

| Denotation                | Selects                                             |
|---------------------------+-----------------------------------------------------|
| =acad-2026=               | that exact AutoCAD (GUI =acad=)                     |
| =accoreconsole-2022=      | that exact =accoreconsole=                          |
| =bricscad-v25-fr_FR=      | that exact BricsCAD version + locale                |
| =bricscad-v25=            | V25 of any locale (host locale preference breaks ties) |
| =acad= / =bricscad=       | the latest of that kind                             |
| =autocad= / =autocad-2022= | =acad= or =accoreconsole= per =--mode= (batch → accoreconsole, else acad) |
| =clautolisp=              | the embedded engine                                 |

So =alfe --cad bricscad-v25-fr_FR -l script.lsp= runs a specific
BricsCAD, and =alfe --cad autocad-2022 --mode batch= selects
accoreconsole 2022. =--cad= sets the backend (a conflicting
=--autocad= / =--bricscad= on the same line is an error) and, for a
CAD, points that backend's discovery at the chosen executable. When
several BricsCAD locales of the same version are installed, the host
language preference (macOS =AppleLanguages=; Unix =LANG= / =LC_*=)
picks one.

* Dialect selection

The =--dialect NAME= option (and its =--strict= / =--autocad= /
=--bricscad= / =--clautolisp= shorthands) selects the AutoLISP
dialect descriptor the runtime uses: which reader knobs are on,
which encoding default applies, which special-case syntax is
accepted.

| Option         | Dialect        | Notes                                           |
|----------------+----------------+-------------------------------------------------|
| =--dialect strict= / =--strict= | =strict=       | Default. Portable AutoCAD ∩ BricsCAD subset.    |
| =--dialect autocad-2026= / =--autocad= | =autocad-2026= | AutoCAD 2026 surface. UTF-8 default encoding.   |
| =--dialect bricscad-v26= / =--bricscad= | =bricscad-v26= | BricsCAD V26. Lax reader, hex-float =atof=.     |
| =--dialect clautolisp= / =--clautolisp= | =clautolisp=   | Superset of strict + clautolisp extensions.     |

The dialect is independent of the backend — you can run
=alfe --clautolisp --dialect bricscad-v26 script.lsp= to evaluate
under the BricsCAD reader rules in the in-process engine, which
is useful for testing.

Whatever the dialect selected, all operators remain callable.
Out-of-dialect operators are eligible for a diagnostic warning at
use time (the warning machinery itself is tracked separately —
see =deferred-clautolisp-out-of-dialect-warnings.issue= in the project
issue tracker).

* Host selection

=--host NAME= picks the HAL (host abstraction layer) backend the
clautolisp engine talks to: it decides where the CAD-host effects of a
program land — =(getvar …)=, =(command …)=, =(ssget …)=, the ActiveX
object model. The dialect (see /Dialect selection/) controls the
/language/, the host controls the /target/; the two are independent.

alfe knows three hosts and does not interpret the choice: it passes it on
to clautolisp, which supports all three.

| Option          | Host     | What it is                                            |
|-----------------+----------+-------------------------------------------------------|
| =--host cador=  | =cador=  | Default. The headless CAD core: an in-memory, deterministic CAD application. |
| =--host cadtui= | =cadtui= | The textual UI-tree host, layered on the cador core.  |
| =--host nihil=  | =nihil=  | No host at all: every host operation is refused.      |

Any other name is a usage error (exit status 2) that lists these three.

=--host= only matters with the =clautolisp= backend. Under =--bricscad=
and =--autocad= the host is the CAD itself and the option is accepted and
ignored. That is coherent: =--bricscad= and =--autocad= each start a CAD
with its own GUI, and =--clautolisp --host cadtui= starts clautolisp with
a text UI.

** =cador=

The default. It behaves as a small CAD with no window: system
variables have values (=(getvar "CLAYER")= is ="0"=), entities and
selection sets live in memory, and the ActiveX object model
(=vlax-get-acad-object=, =vla-*=) runs against an in-memory object
graph. It has no CAD command engine: =(command …)= does not draw, it
/records/ the command line's tokens, and =(clal-command-log)= returns
what was recorded. That makes it the host for running and testing
programs on a machine with no CAD.

** =nihil=

The trivial host, for programs that must not touch a CAD at all: any
host operation signals =HOST-NOT-SUPPORTED=, for instance

#+begin_example
$ alfe --clautolisp --host nihil -x '(getvar "CLAYER")'
; clautolisp runtime error: HOST-NOT-SUPPORTED: Host backend nihil does not support GETVAR.
#+end_example

Pure computation — lists, strings, arithmetic — is unaffected, so running
a supposedly pure program under =--host nihil= is a way to find out
whether it reaches for a CAD after all.

** =cadtui=

The textual counterpart of a CAD application, built on the cador core.
It presents the CAD — menu bar, drawings, the CAD view with its entities
and grips, alerts, DCL dialogs, consoles — as an inspectable,
keyboard-drivable tree, and mirrors DCL dialogs (=new_dialog= /
=start_dialog=) into that tree, so that programs with dialogs can be
tested headless and scripted. cador is cadtui's degenerate,
application-and-console-only configuration.

alfe does not embed cadtui: the clautolisp executable provides it. So
=alfe --clautolisp --host cadtui …= runs the installed =clautolisp-sbcl=
as a child process — alfe selects =--backend subprocess= by itself — and
gives it the dialect, =--host cadtui=, the source encoding (=-Esource=)
and one =-l= / =-x= / =-i= per action of the plan, plus =--quiet= and
=--no-init= (alfe owns the init policy). Other alfe options are not passed
on. The executable is looked for in =$ALFE_CLAUTOLISP_BIN=, in the
=tools/clautolisp/bin/= of the checkout alfe was built from, on =$PATH=,
and in =/usr/local/bin=, in that order; when it is nowhere alfe exits with
status 3. Asking for cadtui together with =--backend direct=, the
in-process engine, is a usage error.

#+begin_src sh
alfe --clautolisp --host cadtui -l dialog-test.lsp     # batch: the output comes back when the child ends
alfe --clautolisp --host cadtui -i                     # the cadtui console, on your terminal
#+end_src

In a batch run alfe collects the child's output and prints it when the
child exits. When the plan holds =-i= — or has no action at all, which is an
implicit =-i= — the child is given alfe's own terminal, keyboard and
screen, instead of pipes, so that the cadtui console (or a text UI) talks to
you directly. alfe does nothing else about the terminal while the child
runs: what happens when alfe's terminal settings and a full-screen text UI
disagree is not settled yet, and will be dealt with as it is met. How
cadtui is driven, and what it offers, is documented in the clautolisp user
manual (=clautolisp-user-manual.org=, /Host backend/); alfe does not repeat
it.

** What a program sees

=*AUTOLISP-HOST*= (see the chapter on the =*AUTOLISP-…*= globals) holds
the host that was selected, as a symbol, the same in the in-process engine
and in the child process:

| Selected        | =*AUTOLISP-HOST*= |
|-----------------+-------------------|
| =--host cador=  | =CADOR=           |
| =--host cadtui= | =CADTUI=          |
| =--host nihil=  | =NIHIL=           |

With no =--host= the host is cador.

** Two clautolisp options alfe does not have

=--list-hosts= (print the available hosts with a one-line summary each)
and =--mock-input PATH= (a file of answers for the cador host's
=getstring= / =getpoint= prompts) belong to clautolisp. alfe rejects
=--mock-input= as an unknown option and accepts =--list-hosts= without
doing anything with it; use =clautolisp --list-hosts= to see the list.

* CAD engine control

Four options govern *how* a CAD engine is obtained and how much of the
bootstrap it runs. They apply to the CAD backends (=--bricscad=,
=--autocad=); the clautolisp backend ignores them, since it needs
neither a launch nor a workdir handshake.

| Option                        | Effect                                          |
|-------------------------------+-------------------------------------------------|
| =--backend attach\vert{}launch=      | Attach to an already-running CAD, or launch a fresh one. |
| =--workdir DIR=               | Override the exchange directory (default: =$AUTOLISP_WORKDIR=). |
| =--bootstrap-phase PHASE=     | Truncate the bootstrap at =marker=, =core=, =log= or =full=. |
| =--epure=                     | Run BricsCAD or AutoCAD under the EPURE profile (MS-Windows only). Defined by the =epure= plug-in, not by alfe itself: see [[#plugin-epure][The EPURE plug-in]]. |

=--workdir= names the directory through which alfe and the CAD engine
exchange files — the file-IPC channel the CAD backends run on. Point it
somewhere you can read when you want to inspect that traffic; combine it
with =--keep-workdir= (or =$AUTOLISP_KEEP_WORKDIR=), which stops alfe
deleting the directory at the end of the run, since by default there is
nothing left to look at.

=--bootstrap-phase= truncates the engine-side bootstrap, which is how
you diagnose a CAD that never reaches =READY= — work *up* from =marker=
and the phase that stops working is the one at fault:

| Phase     | Behaviour                                                       |
|-----------+-----------------------------------------------------------------|
| =marker=  | Writes a startup marker and a status, nothing else. *Your actions are not executed* — this only proves the engine started and can write to the workdir. |
| =core=    | Executes actions with basic file I/O, but does *not* capture =print= / =princ= / =prompt= output. |
| =log=     | =core= plus the CAD-log setup (=LOGFILEMODE=, =LOGFILEPATH=, =LOGFILENAME=). |
| =full=    | The default: CAD log, capture of Lisp output, batch REPL under =-i=, and the remote protocol. |

Two consequences worth knowing before you use a truncated phase: under
=marker= a run that "succeeds" has not run your script at all, and under
=core= a script that prints its results looks silent because the capture
is not installed. =--interactive= requires =full= — combined with any
other phase, alfe exits with code =2=.

=--epure= is not one of alfe's own options: the =epure= plug-in, which
ships with alfe, defines it ([[#plugin-epure][The EPURE plug-in]]). Before the plug-in system
alfe accepted =--epure= and did nothing with it. It now launches
BricsCAD or AutoCAD under the =Epure= profile and runs EPURE's control
script before alfe's run-time is loaded. It works on MS-Windows only;
elsewhere, and under =--clautolisp=, it is silently ignored. Its
companions =--epure-profile= and =--epure-script= are described with the
plug-in.

The environment variables =$AUTOLISP_WORKDIR=, =$AUTOLISP_BOOTSTRAP_PHASE=
and, for the plug-in option =--epure=, =$AUTOLISP_EPURE= supply the
defaults; an explicit option always wins.

* Actions

alfe accepts an ordered queue of actions on the command line. The
queue runs in order then the engine terminates (or enters the
REPL with =-i=).

| Option              | Action                                          |
|---------------------+-------------------------------------------------|
| =-x EXPR= / =--eval EXPR= | Evaluate EXPR. Value is NOT auto-printed — wrap with =(print …)= if you want it back on stdout. See "Action output semantics" below. |
| =-l FILE= / =--load FILE= | Load and evaluate FILE.                         |
| =FILE.lsp= (positional)  | Equivalent to =-l FILE.lsp=.                    |
| =-i= / =--interactive=   | Enter REPL after the queue (same context). Auto-printing is enabled in the REPL only.      |
| =--quit=               | Force engine shutdown after the queue.          |
| =--dry-run=            | Print the resolved plan; don't run anything.    |
| =--print-command=      | Stage the workdir for real, print the CAD command line that would be launched, launch nothing. CAD backends only. |
| =--on-error POLICY=    | How an unexpected Lisp condition escaping alfe itself is reported: =quit= (default — the terse =alfe: <error>= line, then exit) or =debug= / =ignore=, which additionally dump the Common-Lisp backtrace (captured before the stack unwinds). alfe has no debugger of its own, so =debug= and =ignore= behave the same. |

Examples:

#+begin_src sh
alfe -x "(print (+ 1 2))"                # → 3
alfe -x "(+ 1 2)"                        # silent — value discarded
alfe -l prelude.lsp -x "(my-main)"       # load then call
alfe -l script.lsp -i                    # load then drop to REPL
alfe --bricscad -l ../scripts/draw.lsp   # run under BricsCAD
alfe --dry-run -l foo.lsp                # show the plan only
#+end_src

** Action output semantics

=-x EXPR=, =-l FILE= and =--main FN= are *batch* evaluations, not
REPL steps. The value an action produces is *not* echoed to alfe's
stdout — use an explicit printing primitive in the expression
(=(print …)=, =(princ …)=, =(prin1 …)=) when you want the value
to come back. This is uniform across the =--clautolisp=,
=--bricscad= and =--autocad= backends.

The interactive REPL (=-i= / =--interactive=) is the only context
where values are auto-printed: there, each top-level form's value
is read, evaluated and printed (read-eval-print loop). =-x= and
=-l= actions issued alongside =-i= remain silent-by-default; only
forms typed AT the REPL prompt print their values.

If you want a one-line shorthand for "evaluate and print", define a
helper in your init file:

#+begin_src lisp
(defun ep (form) (print (eval form)))
;; … then …
alfe -l ~/.autolisp -x "(ep (quote (list 1 2 3)))"
#+end_src

** Interactive REPL on CAD backends

=alfe --interactive --bricscad= (and =--autocad=) drops into a live
REPL backed by the same file-IPC protocol the batch =-x= / =-l=
actions use. Practical points:

- The prompt is =alfe>= (or =    >= for continuation lines when the
  form isn't balanced yet). Multi-line forms are accepted — the
  reader waits for a balanced parenthesis count before forwarding.
- Each form is sent through =protocol/stdin.txt=; output is drained
  live to your terminal as the CAD prints (no end-of-plan buffering).
- Errors do not exit the REPL: a failed eval surfaces its message on
  =stderr=, the prompt comes back, the runtime stays in its read-eval
  loop.

On MS-Windows, the CAD backends discover installed engines by
default from the standard =Program Files= roots. =--bricscad=
searches =%ProgramW6432%=, =%ProgramFiles%= and
=%ProgramFiles(x86)%= for =Bricsys/*/bricscad.exe=; =--autocad=
searches the same roots for =Autodesk/AutoCAD */acad.exe=,
=AutoCAD LT */acadlt.exe= and =accoreconsole.exe=. If
=BRICSCAD_EXE=, =AUTOCAD_EXE= or =AUTOCAD_ACCORECONSOLE= is set,
that explicit path wins.

For =alfe --autocad --mode batch=, the drawing/template selection is:
=--dwg FILE= first, then =AUTOLISP_DWG=, then a shipped
=Template/acadiso.dwt= or =Template/acad.dwt= next to the discovered
AutoCAD install. Only if all three miss does batch mode stop with a
=NO-DWG= bootstrap error.
- Exit with any of: Ctrl-D (EOF), an empty line that equals =:quit=,
  =:q=, =:exit=, =(quit)=, =(exit)=, or by queuing a =--quit= action.

You can mix =-l= / =-x= with =--interactive= in one invocation: the
batch actions run first, then control hands off to the REPL with the
same shared evaluation context.

* Encoding

Encoding is set per /situation/ — one option per boundary where
bytes cross. Each situation =S= has a long form =--S-encoding ENC=
and a short form =-ES ENC=; bidirectional situations also accept a
=-in= / =-out= suffix (=--S-in-encoding=, =-ES-in=). A bare
=--encoding ENC= / =-E ENC= sets every situation at once.

| Situation  | Option                | Effect                                              |
|------------+-----------------------+-----------------------------------------------------|
| source     | =-Esource ENC=        | Source-file encoding for the whole session.         |
| terminal   | =-Eterminal ENC=      | alfe's own REPL I/O encoding; surfaced to AutoLISP. |
| file       | =-Efile ENC=          | =(open …)= file I/O default.                         |
| console    | =-Econsole ENC=       | CAD GUI console device I/O.                          |
| cadstdio   | =-Ecadstdio ENC=      | CAD subprocess stdin/stdout pipes.                  |
| log        | =-Elog ENC=           | alfe's log/diagnostic stream.                        |
| (all)      | =-E ENC=              | Every situation at once.                            |

Accepted ENC values: =utf-8=, =iso-8859-1= (= =latin-1=),
=windows-1252= (= =cp1252=), =us-ascii=. Suffixes select a
line-ending variant: =-mac= / =-cr= for CR, =-dos= / =-crlf= for
CRLF, =-unix= / =-lf= for LF. So =-Esource utf-8-crlf= reads a UTF-8
file with CRLF terminators.

Without =-Esource=, the dialect's default applies (=iso-8859-1= for
=strict=, =utf-8= for =autocad-2026= / =bricscad-v26= /
=clautolisp=). When neither dialect nor option specifies one, the
process locale (=$LC_ALL=, then =$LANG=, then =$LC_CTYPE=)
supplies the fallback.

=--list-encodings= prints every accepted ENC name and exits;
=--list-situations= prints the situations and their directions.

** What each situation actually does

Not every situation is settable on every target — some are fixed by the
CAD product. alfe *accepts* the option in all cases, but when the value is
fixed it warns that it is ignored and keeps the product value (so a typo is
still an error, but a fixed boundary is never silently wrong).

- =terminal= — applied to alfe's OWN =*standard-output*= / =*standard-input*=
  / =*error-output*=. =-Eterminal-in= drives stdin, =-Eterminal-out= drives
  stdout+stderr; the bare form both. Settable everywhere (it is alfe's own
  stream).
- =source= — an explicit =-Esource= is forwarded into the CAD's native
  =(load)= so a =.lsp= with non-ASCII literals decodes correctly (BricsCAD
  =,ccs=…=, AutoCAD the =open= 3rd-arg at =LISPSYS= 1/2). Without it the CAD
  keeps its own default decode.
- =file= — the default encoding of files the AutoLISP program itself opens.
  On clautolisp it also drives =*AUTOLISP-FILE-ENCODING*=.
- =console= / =cadstdio= — how alfe DECODES the CAD's console/pipe output.
  accoreconsole is UTF-16LE, *fixed by the product* — a conflicting
  =-Econsole= is warned and ignored. For other targets the default is an
  auto-detect cascade (UTF-16LE / UTF-8 / lenient) unless you name a codec.
- =log= — alfe's own diagnostic stream.

** Per-target defaults (measured 2026-07)

These are the encodings each target exhibits with NO override — the reason
some situations warn-and-ignore. Full provenance (settable / product-fixed /
LISPSYS-selected) is tracked in the project's encoding issues.

| Target                    | source / file           | console                       |
|---------------------------+-------------------------+-------------------------------|
| clautolisp (Linux)        | UTF-8 (settable, LC_*)  | UTF-8                         |
| BricsCAD V26 / macOS      | UTF-8 under a UTF-8 locale (settable via =LC_ALL=); read needs a BOM | full Unicode (GUI) |
| BricsCAD V25 / Windows    | ANSI_1252; per-open =,ccs=UTF-8/UTF-16LE= honoured | cp1252 (GUI) |
| AutoCAD 2022 / accoreconsole | ANSI_1252 / MBCS; =LISPSYS= 1/2 → UTF-8 (restart); =ccs=~ ignored | UTF-16LE, fixed |

* Init files

On startup (unless =--no-init= / =-norc= is given), alfe loads
the first init file it finds in this order:

1. =~/.alfe= or =~/.alferc=
2. =~/.autolisp= or =~/.autolisprc=
3. =~/.config/alfe/init=
4. =~/.config/autolisp/init=

The init file runs under the selected dialect and backend; it's a
natural place to put =alref-set-root= calls, custom helpers, REPL
preferences, etc.

*The engine's own init files do not run.* When alfe drives clautolisp as
a subprocess it passes =--no-init= (and =--quiet=) to it, so your
=~/.autolisp=, =~/.clautolisp= and the XDG init files are *not* loaded
by the engine. This is deliberate: the front end owns bootstrap policy,
and loading the spawned engine's rc files would make a subprocess run
behave differently from the in-process =:direct= one and let a personal
init file leak into test results. What you want in an alfe session
belongs in *alfe's* init file above, which does run.

The CAD backends are a different matter: AutoCAD and BricsCAD load
their own startup files, and alfe does not suppress them wholesale — but
it is not neutral either. A BricsCAD profile named with
=$AUTOLISP_BRICSCAD_PROFILE= changes what the engine auto-loads, and a
*clean* profile is precisely how you keep a vertical application out of
a pure-CAD run. See /Environment variables/ above.

* Plug-ins
:PROPERTIES:
:CUSTOM_ID: plugins
:END:

Behaviour that belongs to one site, one CAD product or one user —
starting EPURE, loading a package before your script — does not belong
in alfe's backends. A /plug-in/ is a Common Lisp file that alfe loads at
start-up and that

1. defines command-line options, possibly taking arguments;
2. intervenes, through named /hooks/, at any stage of a run: it can read
   and change the parsed options, veto a backend, rewrite the action
   plan, add lines to the scripts alfe generates for the CAD, change the
   command line and working directory the CAD is launched with, and
   observe every action, the shutdown, the exit code and every error.

Two plug-ins ship with alfe: =epure= runs BricsCAD or AutoCAD under the
EPURE profile ([[#plugin-epure][The EPURE plug-in]]), and =epuree= loads the EPUREE emulation
of the EPURE API before your script ([[#plugin-epuree][The EPUREE plug-in]]). Writing your
own is described in [[#plugin-writing][Writing a plug-in]].

What you can rely on:

- *Load all, activate by flag.* Every installed plug-in is loaded at
  start-up, so that its options exist when the command line is parsed.
  Only an /active/ plug-in has its hooks called.
- *Zero active plug-ins, zero behaviour change.* Every hook call site
  returns its input unchanged when no active plug-in registered that
  hook.
- *No silent shadowing.* A plug-in cannot redefine an alfe option or an
  option of another plug-in. That is a registration error and the
  plug-in is skipped.
- *A plug-in that fails to load is a warning.* =--help=, =--version= and
  every run that does not need the plug-in keep working.
- *A plug-in is trusted.* It runs inside alfe's image with alfe's
  privileges; there is no sandbox. Install one as you would install a
  program.

** Where plug-ins are installed

A /plug-in root/ is a directory holding one sub-directory per plug-in,
named for it. The plug-in =NAME= is one or both of

| File                            | Form                                                                   |
|---------------------------------+------------------------------------------------------------------------|
| =NAME/NAME.lisp=                | source                                                                 |
| =NAME/NAME.VERSION-IMPL.plugin= | compiled, for alfe version VERSION and Common Lisp implementation IMPL |

IMPL is =sbcl= or =ccl=. NAME matches =[a-z][a-z0-9-]*= and is the name
the plug-in registers under.

alfe searches the roots in this order, and *the first plug-in of a given
name wins*, so a local install shadows a system one:

1. every =--plugin-path DIR=, in command-line order;
2. every entry of =$ALFE_PLUGIN_PATH=, a PATH-style list (separated by
   =:=, or by =;= on MS-Windows);
3. =$XDG_DATA_HOME/clautolisp/plug-in= (=~/.local/share/clautolisp/plug-in=
   when the variable is unset; =%APPDATA%\clautolisp\plug-in= on
   MS-Windows);
4. =clautolisp/plug-in= under every entry of =$XDG_DATA_DIRS=
   (=/usr/local/share:/usr/share= when unset; none on MS-Windows unless the
   variable is set);
5. =PREFIX/share/clautolisp/plug-in=, PREFIX being the installation prefix
   the running executable belongs to — derived the same way as for the
   CAD runtime files (see /The CAD runtime files/);
6. the =plugins/= directory of alfe's source tree, when alfe runs from a
   checkout. It is what makes =epure= and =epuree= work before anything is
   installed; it comes last, so an installed plug-in shadows it.

=make install= puts the plug-ins that ship with alfe in
=$(PREFIX)/share/clautolisp/plug-in/= and compiles them with the alfe it
has just installed. Your own belong in the user-level root (item 3), or
in any directory you name with =--plugin-path=.

*Which form is loaded.* When the compiled file for this alfe version and
this Common Lisp implementation exists and is at least as new as the
source — or there is no source — it is loaded; otherwise the source is.
Editing a source therefore retires an older compiled file by itself. A
compiled file that fails to load falls back to the source, with a
warning. A compiled file whose VERSION or IMPL is not the running alfe's
is ignored (=--verbose= logs it).

** Compiling a plug-in

=alfe --compile-plugin FILE.lisp= compiles the plug-in source =FILE.lisp=
for the running alfe version and implementation into
=NAME.VERSION-IMPL.plugin= next to the source, prints its path and exits
0 (1 on a compile error, or when FILE is not there). NAME is the name of
FILE. Compiling is optional: a plug-in works from its source alone.

alfe is built for two implementations (=alfe-sbcl= and =alfe-ccl=, see
/Installation/), and a compiled file is valid for one of them and one
alfe version only. Compile once for each implementation you run, and
again after upgrading alfe.

#+begin_src sh
alfe --compile-plugin ~/.local/share/clautolisp/plug-in/hello/hello.lisp
#+end_src

** Listing plug-ins

=alfe --list-plugins= prints the plug-ins alfe found (name, version, the
form loaded — source or compiled —, path and description), those that
failed to load with the reason, and the search path, then exits 0.

** Activating a plug-in

An installed plug-in does nothing until it is /active/. It is active
when

- you gave its own activating option (=--epure= for =epure=, =--epuree=
  for =epuree=); or
- the environment variable that supplies the default of that option is
  set to a true value (=1=, =y=, =yes=, =true= or =on=), for instance
  =$AUTOLISP_EPURE=1=; or
- you gave =--plugin NAME=, which may be repeated; or
- =$ALFE_PLUGINS=, a comma-separated list of plug-in names, lists it.

=--plugin NAME= — or a name in =$ALFE_PLUGINS= — that is not installed is a usage error that
lists the installed plug-ins.

An active plug-in's other options take their value from the command
line, else from their environment variable, else from their default.
Giving an option of a plug-in that is *not* active is a usage error (exit
status 2) that names the option activating the plug-in: =alfe
--epure-profile Epure …= fails and points at =--epure=.

A plug-in declares the backends it takes part in. Under another backend
it is still loaded and its options still parse, but its hooks are not
called.

=alfe --help= ends with a generated /Plug-in options/ section listing
every option of every installed plug-in, active or not.

#+begin_src sh
alfe --bricscad --epure -x '(princ "ok")'          # the plug-in's own option
alfe --bricscad --plugin epure -x '(princ "ok")'   # the same, by name
export ALFE_PLUGINS=epure                          # every run, from your shell init
#+end_src

** Choosing the plug-in roots

=--plugin-path DIR= adds DIR to the search path; repeat it for several
roots. The directories given this way are searched first, in
command-line order, then the entries of =$ALFE_PLUGIN_PATH=, then the
standard places listed above. DIR is a plug-in /root/: it holds
=NAME/NAME.lisp=, not =NAME.lisp= itself.

#+begin_src sh
alfe --plugin-path ./my-plugins --plugin hello -x '(+ 1 2)'
export ALFE_PLUGIN_PATH=$HOME/plugins:/srv/site/plugins
#+end_src

** Loading no plug-in

=--no-plugins=, or =$ALFE_NO_PLUGINS= set to a true value, makes alfe
load no plug-in at all. It is the way to rule a plug-in out when you
suspect it.

Plug-ins are loaded before the command line is parsed, since their
options must exist for the parser. Two options decide what is loaded,
=--plugin-path= and =--no-plugins=, so alfe finds them in a first pass
over the raw command line; the parser still accepts them.

** When a plug-in fails to load

Each plug-in file is loaded with the package set to =CL-USER=, and the
compiler and loader chatter is captured (shown with =--debug=). A
plug-in that signals an error while loading — a read or compile error, a
registration error — is reported on standard error as

#+begin_example
alfe: warning: plug-in NAME (PATH): MESSAGE
#+end_example

and skipped; alfe carries on, and =--list-plugins= shows the failure and
its reason. Registration fails when NAME does not match the file the
plug-in was loaded from, when one of its options breaks the naming rules
(see [[#plugin-writing][Writing a plug-in]]), or when it names a hook this alfe does not
have — a plug-in written for another alfe version finds that out when it
is loaded, not in the middle of a run.

** The EPURE plug-in
:PROPERTIES:
:CUSTOM_ID: plugin-epure
:END:

EPURE is the SNCF Réseau vertical application (menus, profile, SCHMS+)
that the site's CAD sessions run under. The =epure= plug-in launches
BricsCAD or AutoCAD the way the site's =scripts/bricscad-epure= and
=scripts/autocad-epure= do: with the =Epure= user profile, from the CAD's
=UserDataCache= directory, running EPURE's control script; and it
arranges for that script to run before alfe's own runtime is loaded. It
replaces the legacy =autolisp --epure=. (Before the plug-in system,
alfe accepted =--epure= and did nothing with it.)

It applies to =--bricscad= and =--autocad= and is *MS-Windows only*. On
another OS, and under =--clautolisp=, =--epure= is silently ignored (a
=--verbose= message says so), so the option stays harmless in scripts
shared between machines.

| Option / variable                                 | Meaning                                                   |
|---------------------------------------------------+-----------------------------------------------------------|
| =--epure=, =$AUTOLISP_EPURE=                      | Activate the plug-in (the variable: set to a true value). |
| =--epure-profile NAME=, =$AUTOLISP_EPURE_PROFILE= | The CAD user profile to run under (default =Epure=).      |
| =--epure-script FILE=, =$AUTOLISP_EPURE_SCRIPT=   | EPURE's control script (default below).                   |

An explicit option wins over its variable. =--epure-profile= and
=--epure-script= are usage errors unless the plug-in is active (see
[[#plugins][Plug-ins]], /Activating a plug-in/).

The default control script is

- =%APPDATA%\sncf\epure\epure 2022_b\control_path_epure_2022.scr= for
  BricsCAD;
- =%APPDATA%\sncf\epure\epure 2022\control_path_epure_2022.scr= for
  AutoCAD.

When the script does not exist the run stops with a
=backend-bootstrap-error= naming the path (exit status 4) — unless it is
a =--dry-run=.

*Why the mode matters.* EPURE is a full-GUI application: it needs the
CAD's profile, menus and CUIX. accoreconsole (AutoCAD's batch mode) has
neither a GUI nor profiles. So:

| Backend, mode                           | What =--epure= does                                                                                                                                                                                                             |
|-----------------------------------------+---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| BricsCAD, =batch= (the default)         | Starts =bricscad.exe [template] /p PROFILE /b run.scr= from =UserDataCache=. The =/Automation= switch, which hides the main window, is *dropped*. =run.scr= runs =._SCRIPT= on the control script, then loads =run-common.lsp=. |
| BricsCAD, =--mode automation= (COM)     | The bridge tries to activate the profile through =Preferences.Profiles= (a failure is written to the errors file and the run carries on with the current profile), and sends =._SCRIPT= before the load.                        |
| AutoCAD, =automation= (COM)             | The default under =--epure=. The bridge activates the profile and sends =._SCRIPT= before the load.                                                                                                                             |
| AutoCAD, =--mode batch= (accoreconsole) | Refused: usage error (exit status 2), "EPURE requires the full AutoCAD GUI; accoreconsole (--mode batch) has no profile support. Use --mode automation."                                                                                                              |

Under COM the run-time is loaded into the GUI session, and its server
loop keeps the CAD's UI thread busy for as long as alfe drives it: the
GUI is blocked for the duration of the run. That is acceptable for a
scripted run, not for an interactive one.

#+begin_src sh
alfe --bricscad --epure -x '(princ "ok")'
alfe --autocad --epure --epure-profile Epure -l check.lsp
alfe --bricscad --epure --epure-script 'D:\epure\control_path.scr' -l check.lsp
#+end_src

*Not validated on real CADs.* The plug-in was written and tested against
the mock CAD, =--print-command= and an OS override, not against EPURE
itself. Two assumptions come from the legacy wrapper and have not been
re-checked on a real installation: that a =._SCRIPT= nested in a =/b=
script returns control to the outer script (so the =(load …)= after it
runs), and that two consecutive COM =SendCommand= calls run in order. If
the first does not hold, =--mode automation= (COM) is the fallback under
BricsCAD too. Also unchecked: that dropping =/Automation= is right, that
the default control-script paths — which name EPURE 2022 — match your
installation (use =--epure-script= when they do not), and that the GUI
stays usable after the run-time is loaded. The validation on real CADs
is tracked as =alfe-plugin-epure-windows-validation=.

** The EPUREE plug-in
:PROPERTIES:
:CUSTOM_ID: plugin-epuree
:END:

EPUREE is an AutoLISP emulation of the public EPURE API, for BricsCAD on
macOS and Linux, where EPURE itself does not exist, and for tests. It is
packaged as the ALPM (AutoLISP package manager) system =epuree=:
=epuree.alpm= at the root of the EPUREE repository. The =epuree= plug-in
loads it into the engine before anything else the plan does. It applies
to every backend and every OS.

| Option / variable                   | Meaning                                                                                                                         |
|-------------------------------------+---------------------------------------------------------------------------------------------------------------------------------|
| =--epuree=, =$AUTOLISP_EPUREE=      | Activate the plug-in (the variable: set to a true value).                                                                       |
| =--epuree-path DIR=, =$EPUREE_PATH= | A directory, searched recursively, that ALPM is told holds =epuree.alpm=. May be repeated; =$EPUREE_PATH= is a PATH-style list. |
| =--epuree-alpm FILE=, =$ALPM_LSP=   | The =alpm.lsp= to load (default below).                                                                                         |

An explicit option wins over its variable. =--epuree-path= and
=--epuree-alpm= are usage errors unless the plug-in is active.

Without =--epuree-alpm=, =alpm.lsp= is looked for in =$ALPM_LSP=,
=PREFIX/share/autolisp/= (PREFIX being the installation prefix of the
running executable), =/opt/local/share/autolisp/=,
=/usr/local/share/autolisp/= and =~/.local/share/autolisp/=. When it is
nowhere, the run stops with a usage error listing the places tried.

The plug-in puts =eval= actions in front of the action plan — so in front of
your init files and actions — and they show in =--dry-run=:

1. load =alpm.lsp=;
2. one =(alpm-register-directory DIR T)= for each =--epuree-path=
   directory;
3. =(alpm-load-system "epuree" nil)=;
4. =(epuree-initialize)=.

Loading the system only defines; =(epuree-initialize)= is what does the rest
of what =(load "load_epuree")= does: it installs the path-separator and
Windows-environment shims and anchors the bundle root. Steps 3 and 4 together
are equivalent to =(load "load_epuree")=.

Because these are ordinary plan actions, the engine evaluates them
itself, identically under clautolisp, BricsCAD and AutoCAD, and a failure
fails the run before your script starts.

#+begin_src sh
alfe --epuree --epuree-path ~/src/epuree -l check.lsp
alfe --epuree --epuree-path ~/src/epuree --dry-run -x '(princ 1)'   # see the actions
alfe --bricscad --epuree --epuree-alpm /opt/alpm/alpm.lsp -l check.lsp
#+end_src

** Writing a plug-in
:PROPERTIES:
:CUSTOM_ID: plugin-writing
:END:

A plug-in is one Common Lisp file. It defines its own package, registers
itself with =define-plugin= and adds hooks with =define-plugin-hook=. The
API is the set of exported symbols of the package =ALFE.PLUGIN=. The two
plug-ins that ship with alfe (=plugins/epure/epure.lisp= and
=plugins/epuree/epuree.lisp= in the alfe source tree) are written with
it.

*** A first plug-in

This plug-in defines a flag and an option with an argument, and greets
before the action plan runs. The option names ~--hello~ and
~--hello-name~ exist only in this example.

#+begin_src lisp
(defpackage #:alfe.plugin.hello (:use #:cl #:alfe.plugin))
(in-package #:alfe.plugin.hello)

(define-plugin "hello"
  :version "1.0.0"
  :description "Greet before the plan runs."
  :options ((:flag  "--hello"      :activates t :doc "Enable the greeting.")
            (:value "--hello-name" :key :name :arg "NAME" :default "world"
                                   :doc "Whom to greet.")))

(define-plugin-hook "hello" :plan (ctx plan &key backend)
  (declare (ignore backend))
  (cons (alfe.backend:action-eval
         (format nil "(princ ~A)"
                 (autolisp-string-literal
                  (format nil "Hello, ~A!~%" (plugin-option :name)))))
        plan))
#+end_src

Save it as ~$HOME/.local/share/clautolisp/plug-in/hello/hello.lisp~ — the
directory and the file are named for the plug-in, and registration fails
when the name in =define-plugin= is not the name of the file. Then:

#+begin_src sh
alfe --list-plugins                            # hello is listed
alfe --hello --hello-name Ada -x '(+ 1 2)'     # prints "Hello, Ada!" first
alfe --compile-plugin ~/.local/share/clautolisp/plug-in/hello/hello.lisp
#+end_src

In the example, ~--hello~ has =:activates t=, so giving it activates the
plug-in; ~--hello-name~ stores its value under the key =:name=, which
=(plugin-option :name)= reads back. Giving ~--hello-name~ without ~--hello~
(or =--plugin hello=) is a usage error naming ~--hello~. The =:plan= hook
is a /filter/: it receives the action plan and returns a new one, here
with one =eval= action added in front. What =--dry-run= prints is that
plan.

*** Registering: =define-plugin=

#+begin_src lisp
(define-plugin NAME
  :version     "1.0.0"                 ; string, shown by --list-plugins
  :description "one line"
  :applies-to  (:bricscad :autocad)    ; or :all (the default)
  :priority    0                       ; lower runs first; ties: load order
  :options     (OPTION-SPEC ...))
#+end_src

NAME is a string (a symbol or keyword is downcased). Registering a name
already registered replaces the earlier registration, which is how tests
reload a plug-in; two /files/ of the same name are never both loaded.
=:applies-to= lists the backends (=:clautolisp=, =:bricscad=, =:autocad=)
whose runs the plug-in's hooks are called for; the plug-in is still
loaded, and its options still parse, under any backend.

*** Options a plug-in defines

An =OPTION-SPEC= is =(KIND "--long" . PLIST)=. The values in the plist
are evaluated, so quote list literals.

| Kind      | Meaning                                                          |
|-----------+------------------------------------------------------------------|
| =:flag=   | takes no argument; its value is =t=                              |
| =:value=  | takes one argument (~--opt V~ or ~--opt=V~)                      |
| =:repeat= | like =:value=, may be given several times; its value is the list |

| Key          | Meaning                                                                                                                         |
|--------------+---------------------------------------------------------------------------------------------------------------------------------|
| =:key=       | keyword under which the value is stored (default: the option name without the ~--NAME-~ prefix, =:enabled= for ~--NAME~ itself) |
| =:activates= | true: giving this option, or its environment default, activates the plug-in                                                     |
| =:arg=       | metavariable shown by =--help=                                                                                                  |
| =:doc=       | one-line description shown by =--help= and =--list-plugins=                                                                     |
| =:env=       | environment variable supplying a default                                                                                        |
| =:default=   | value used when neither the command line nor the environment gave one                                                           |
| =:parser=    | function from string to value; signals =cli-usage-error= on a bad value                                                         |
| =:choices=   | list of accepted strings, checked before =:parser=                                                                              |

*Naming rules.* A plug-in ~NAME~ may define only the long options ~--NAME~
and ~--NAME-…~, and no short option: single-dash options are reserved to
alfe. A name that collides with an alfe option, or with an option of a
plug-in registered earlier, is a registration error naming both.

*Resolution and activation* are as described in /Activating a plug-in/:
right after the command line is parsed, for each active plug-in, the
command line wins, then the environment variable, then the default.
=(plugin-option KEY)= returns the resolved value stored under =:key= KEY.

*** Hooks

A hook point has a name, a /kind/, a primary /value/ and keyword
/details/. A handler is =(lambda (ctx value &key … &allow-other-keys) …)=,
defined with =define-plugin-hook=, which adds =&allow-other-keys= itself:
name only the keywords you use. The kind says what a handler's result
means.

| Kind      | Handler's result                                                      |
|-----------+-----------------------------------------------------------------------|
| /event/   | ignored; the handler acts by side effect, or by signalling            |
| /filter/  | the new value, passed to the next handler; the last one is the result |
| /collect/ | a list; the lists of all handlers are concatenated                    |

Handlers run in =:priority= order (ties: registration order), and only
for plug-ins that are active and whose =:applies-to= holds the run's
backend. A handler may call =(deactivate-plugin ctx)=: the remaining
handlers of that plug-in are then skipped. The hooks, in the order a run
meets them:

| Hook                   | Kind    | Called                                                                                          | Value received; what a handler can change                     |
|------------------------+---------+-------------------------------------------------------------------------------------------------+---------------------------------------------------------------|
| =:cli-parsed=          | event   | after parsing and =--cad= selection, before the backend is resolved                             | the parsed options: mutate them, or signal =cli-usage-error=  |
| =:backend-selected=    | event   | after the backend is resolved (and detected, unless a dry run)                                  | the backend object: veto it by signalling                     |
| =:plan=                | filter  | on the effective plan: init files, user actions, terminator; it is also what =--dry-run= prints | the list of actions: return another one                       |
| =:dry-run-report=      | collect | after the plan, under =--dry-run=                                                               | NIL: return strings to print                                  |
| =:workdir-prepared=    | event   | once the workdir exists                                                                         | the workdir                                                   |
| =:run-common-prelude=  | collect | CAD backends: in =run-common.lsp=, after the injected globals, before the bootstrap is loaded   | NIL: return AutoLISP source to insert                         |
| =:run-common-epilogue= | collect | CAD backends: after the runtime is loaded, before its server loop                               | NIL: return AutoLISP source to insert                         |
| =:launcher-lines=      | collect | CAD backends: once per launcher-script slot (below)                                             | the slot: return lines for it                                 |
| =:launcher-script=     | filter  | CAD backends: the whole launcher script, just before it is written                              | the script text: return another one                           |
| =:launch-argv=         | filter  | CAD backends: the command line, just before the process is spawned                              | the argument list: return another one                         |
| =:launch-options=      | filter  | CAD backends: just before the spawn                                                             | the plist =(:directory D :environment E)=: return another one |
| =:engine-started=      | event   | the engine reached READY                                                                        | the session                                                   |
| =:pre-action=          | event   | before each action                                                                              | the action                                                    |
| =:post-action=         | event   | after each action                                                                               | the action; its result is in the details                      |
| =:pre-shutdown=        | event   | before the engine is shut down                                                                  | the session; the reason is in the details                     |
| =:post-shutdown=       | event   | after the shutdown, before the workdir is removed                                               | the session; the workdir is in the details                    |
| =:exit-code=           | filter  | for a run that reached the end of its plan                                                      | the exit code, an integer: return another one                 |
| =:error=               | event   | an error is about to be reported and turned into an exit code                                   | the condition; the phase is in the details                    |

In the =:launch-options= plist, =:directory= is the working directory
the CAD is spawned in (a pathname, or NIL) and =:environment= the changes
to its environment, as =(NAME . VALUE)= pairs, VALUE NIL to unset.

The keyword details each hook receives (=:backend=, =:variant=, =:index=,
=:result=, …) are listed in the specification, chapter /Plug-ins/.

=:pre-action= and =:post-action= make alfe evaluate the plan one action
at a time and stop at the first failed action — but only when an active
plug-in registered one of them. Otherwise the whole plan goes to the
backend in one call. =:launcher-lines=, =:launcher-script=,
=:launch-argv= and =:launch-options= are called by the CAD backends only:
the clautolisp backend has no launch step.

*** The run context

A handler receives the /context/ of the run as its first argument. The
special variable =*CONTEXT*= holds it for the whole run (NIL outside a
run, which makes every hook call site a no-op).

| Accessor                  | Meaning                                                     |
|---------------------------+-------------------------------------------------------------|
| =(context-options ctx)=   | the parsed options                                          |
| =(context-backend ctx)=   | the backend keyword (=:clautolisp= when none was requested) |
| =(context-version ctx)=   | alfe's version string                                       |
| =(plugin-option KEY)=     | the calling plug-in's resolved value for =:key= KEY         |
| =(plugin-state ctx KEY)=  | a =setf=-able per-run scratch value of the calling plug-in  |
| =(deactivate-plugin ctx)= | the calling plug-in takes no further part in this run       |

*** Launcher script slots

The engine-side launcher is a script alfe writes in the workdir and
hands to the CAD. =:launcher-lines= is called once per slot, with the
slot as its value and the kind of script (=:scr= or =:vbs=) as the =:kind=
detail; return its lines when the slot is one you care about.

| Kind   | File                                              | Slot           | Position                                                                                      |
|--------+---------------------------------------------------+----------------+-----------------------------------------------------------------------------------------------|
| =:scr= | =run.scr= (BricsCAD batch), the accoreconsole SCR | =:before-load= | immediately before the =(load run-common.lsp)= line                                           |
|        |                                                   | =:after-load=  | after it, before the final =_QUIT= (the load only returns when the session ends)              |
| =:vbs= | =bridge-bricscad.vbs=, =bridge-autocad.vbs=       | =:after-app=   | once the COM application object exists, before waiting for it and before the document is used |
|        |                                                   | =:before-load= | once the document is active, immediately before the =(load run-common.lsp)= is sent           |

SCR lines are script lines: a command, its answers, or an AutoLISP form.
VBS lines are VBScript statements: ASCII only (=cscript= reads the file
as ANSI), variables declared with =Dim=, strings quoted with the helper
=vbs-escape=.

*** Errors raised by a hook

A =cli-usage-error= or a =backend-error= signalled by a handler passes
through unchanged, with its usual exit status. Any other Lisp error
becomes an =alfe.error:plugin-error=, reported as =plug-in NAME, hook
:HOOK: …= with exit status 4.

* Seeing the CAD command line: =--print-command=

=--print-command= answers "what exactly does alfe launch?". It runs
the whole preparation phase for real — creates the workdir, stages the
runtime and bootstrap LSP, writes =run-common.lsp= and the launcher
(=run.scr=, or the VBScript/AppleScript bridge under
=--mode automation=) — and then, instead of spawning the CAD, prints
the command line it would have spawned:

#+begin_src sh
$ alfe --bricscad --print-command -x "(princ)"
/opt/bricsys/bricscad/bricscad -B /tmp/alfe-bricscad-31337-a1b2c3/run.scr

$ alfe --autocad --mode batch --print-command -l draw.lsp
'C:/Program Files/Autodesk/AutoCAD 2026/accoreconsole.exe' /i C:/T/tpl.dwt /s C:/T/alfe-autocad-2244-f0e9d1/run.scr
#+end_src

Exactly one line goes to stdout — the command, with every argument
quoted for the host shell — so it can be captured directly:

#+begin_src sh
cmd=$(alfe --bricscad --print-command --keep-workdir -x "(princ)")
#+end_src

When a plug-in makes the CAD start in a particular directory (the =epure=
plug-in does: the CAD's =UserDataCache=), the line begins with
=cd DIR &&=, since the command means nothing run from elsewhere.

Everything else (backend, workdir, the raw argv list) is logged at
=--verbose= / =--debug=.

Two things to know:

- *The workdir is deleted on the way out* unless you pass
  =--keep-workdir=. Without it the printed command names a directory
  that no longer exists — fine for reading the argv, useless for
  running it. Combine with =--keep-workdir= (and optionally
  =--write-workdir-path FILE=) when you intend to run the command by
  hand.
- *Running that command yourself is not a full alfe run.* It starts
  the CAD against the staged workdir, and the engine will boot, load
  =run-common.lsp= and reach =READY= — then wait, because nothing is
  driving alfe's side of the file-IPC protocol (no request is ever
  written to =protocol/=, no output is drained). It is a debugging
  aid: it shows the exact switches, binary and script path, and lets
  you reproduce a launch-time failure (licensing, profile, a modal
  dialog) without alfe in the loop.

=--print-command= requires a CAD backend. Under =--clautolisp= there
is no external command line — the engine runs in-process — so alfe
exits 2 with a usage error rather than printing nothing.

It is distinct from =--dry-run=, which resolves nothing, touches no
disk and just prints the action plan.

** Engine location and launch
- =$ALFE_CLAUTOLISP_BIN= :: the =clautolisp= executable the clautolisp
  backend runs as a subprocess. Set it to test a build that is not the
  installed one.
- =$ALFE_BOOTSTRAP_LSP=, =$ALFE_RUNTIME_LSP= :: the two CAD runtime
  files, =autolisp-bootstrap.lsp= and =autolisp-remote-io.lsp=, in
  place of the installed ones. A value naming no file is ignored. See
  /The CAD runtime files/ above.
- =$AUTOCAD_EXE=, =$AUTOCAD_ACCORECONSOLE=, =$BRICSCAD_EXE= :: explicit
  engine binaries, bypassing detection.
- =$AUTOCAD_COM_MODE=, =$BRICSCAD_COM_MODE= :: =auto= (default) or
  =off=. =off= is the batch path, without COM.
- =$AUTOLISP_BRICSCAD_PROFILE=, =$BRICSCAD_PROFILE= :: the BricsCAD
  profile to launch under; the first takes precedence. Unset means the
  engine's own default profile.
- =$ALFE_BRICSCAD_STARTUP_DELAY= :: overrides the =STARTUPWAIT= given to
  BricsCAD — the grace period before alfe expects the engine to answer.
- =$ALFE_ENABLE_MACOS_AUTOMATION= :: opts into BricsCAD =--mode
  automation= on macOS. Off by default: macOS refuses that mode
  immediately (=:no-automation=), since =--mode batch= is the
  well-tested, documented macOS path. Any non-empty value other than
  ="0"= enables it (Windows is unaffected either way — =--mode
  automation= has always worked there). On macOS, automation mode drives
  BricsCAD by typing into its command-line console with synthetic
  keystrokes (AppleScript / System Events), which needs an interactive
  GUI session *and* Accessibility (TCC) permission granted to the
  process running =alfe= — it cannot work headless or in an ordinary CI
  job without that grant.
- =$ALFE_NO_CUI_REPAIR= :: when set and non-empty, do *not* quarantine a
  corrupt per-user =default.cui=. alfe normally renames one aside (never
  deletes) so BricsCAD regenerates it, because the alternative is a
  startup dialog that stalls a batch launch with nobody to dismiss it.

** Plug-in loading
See [[#plugins][Plug-ins]].

- =$ALFE_PLUGIN_PATH= :: extra plug-in roots, a PATH-style list
  (separated by =:=, or by =;= on MS-Windows), searched after the
  directories given with =--plugin-path=.
- =$ALFE_PLUGINS= :: comma-separated names of the plug-ins to activate in
  every run, like =--plugin= given once per name.
- =$ALFE_NO_PLUGINS= :: set to a true value (=1=, =yes=, …), loads no
  plug-in, like =--no-plugins=.

** Encoding
- =$ALFE_AUTOCAD_CONSOLE_ENCODING= :: the AutoCAD console encoding used
  when =-Ecadstdio= is not given, before falling back to the robust
  =ISO-8859-1= default. See /Encoding/ above.

** Conformance corpus
Both gate scenarios that a plain =make test= must never run, so the unit
lane stays green on a machine with no CAD at all.

- =$ALFE_VENDOR_CONFORMANCE= :: set to a non-empty value to actually
  drive the vendor CAD through the corpus. Without it the
  =:bricscad-only= and =:autocad-only= scenarios are skipped rather than
  attempted.
- =$AUTOLISP_LEGACY= :: a *path* to a legacy engine the runner can
  spawn — not a flag. The =:parity= scenarios run only when it names a
  file that exists.

** Consulted, not configured
=$HOME=, =$PATH=, =$TMPDIR=, =$TEMP=, =$TMP= and =$APPDATA= are read for
the usual platform locations, =$XDG_DATA_HOME= and =$XDG_DATA_DIRS= for
the plug-in roots ([[#plugins][Plug-ins]]), and =$NO_COLOR= disables ANSI colour.

* Troubleshooting

** =alfe= prints "Backend ... is not registered"

You selected an explicit backend that isn't compiled into this
build. Usually means a CAD backend is referenced on a host build
that doesn't ship it. Pick =--clautolisp= or omit the flag for
the default.

** =alfe --bricscad= fails on Linux

BricsCAD ships for Linux but the wrapper integration is currently
macOS- and Windows-only. Track =alfe-bricscad-linux.issue=.

** =alfe --autocad= fails on macOS or Linux

AutoCAD is not distributed for those platforms. =alfe= exits with
code 3 and a clear message. Use =--bricscad= (where supported) or
=--clautolisp= instead.

** "alfe with no flags is suddenly different"

Yes — see the [[#backend-selection][Backend selection]] section.
Auto-detection of installed CADs has been removed. Set
=$ALFE_BACKEND_OVERRIDE= in your shell init if you want a CAD
backend by default.

** "not launched: required CAD runtime file not found"
alfe could not find =autolisp-bootstrap.lsp= or =autolisp-remote-io.lsp=,
so it did not start the CAD. Without these files the CAD would boot
and never answer. The message lists each missing file and every path
tried, starting with =share/alfe/runtime/= under the prefix alfe
derived from its own location, and it names the running executable.
Either install the files there, or point =$ALFE_BOOTSTRAP_LSP= /
=$ALFE_RUNTIME_LSP= at them.

** A long =(eval …)= on a CAD backend is aborted after ~30 s

By default the per-request timeout is *RUNNING-aware*: it bounds only
the time until the engine acknowledges the request (=RUNNING N=). Once
that acknowledgement is seen and the CAD process is alive, alfe keeps
waiting — a legitimately long computation is not killed on wall-clock,
and a dead engine still aborts promptly. If you still want a firm upper
bound (or need to raise a slow-launch handshake window), pass
=--timeout N= or set =$AUTOLISP_WAIT_SECS=N=; an explicit value is a
*hard cap* — =--timeout 1= aborts a long eval, =--timeout 600= grants it
ten minutes. (Before alfe 1.7.3 =--timeout= was parsed but ignored on
the CAD backends, so a long eval was aborted at the fixed 30 s default.)

** A plug-in option is refused: it requires its plug-in

=--epure-profile=, =--epure-script=, =--epuree-path=, =--epuree-alpm=
and every other option a plug-in defines are usage errors (exit status
2) while their plug-in is not active. The message names the option that
activates it — for =--epure-profile=, that is =--epure=. Add that
option, or activate the plug-in by name: =--plugin epure=, or
=$ALFE_PLUGINS=epure= in your shell init. See /Activating a plug-in/.

** =--list-plugins= shows nothing, or reports a plug-in as failed

/Nothing./ alfe found no plug-in in any root. Read the search path that
=--list-plugins= prints, and check that the plug-in sits in a directory
named for it (=NAME/NAME.lisp=, not =NAME.lisp= directly under the root),
that =$ALFE_NO_PLUGINS= is not set to a true value, and, for the two
plug-ins that ship with alfe, that alfe was installed with =make install=
(they go under =$(PREFIX)/share/clautolisp/plug-in/=). A root that is not
on the standard path can be added with =--plugin-path= or
=$ALFE_PLUGIN_PATH=.

/Failed./ The listing gives the reason, and every run repeats it on
standard error as =alfe: warning: plug-in NAME (PATH): MESSAGE=. The
usual causes are a read or compile error in the file, a name that
differs from the file's, an option that breaks the naming rules
(=--NAME= or =--NAME-…= only, no short option) or collides with another
option, and a hook name this alfe does not know — typically a plug-in
written for another alfe version. Run with =--debug= to see the compiler
and loader output alfe captured. A compiled file made for another alfe
version or the other implementation is ignored without a word unless you
give =--verbose=; recompile it with =--compile-plugin=.

** =--epure= is given and nothing happens

The =epure= plug-in acts only on MS-Windows and only with =--bricscad=
or =--autocad=. On any other system, and under =--clautolisp= — the
default when nothing names a backend — alfe ignores =--epure= silently.
Run with =--verbose= to see the message saying so, and name the backend.

** A run under EPURE or EPUREE stops before the script starts

- EPURE control script not found (exit status 4): the message names the
  path looked at. Install EPURE, or point =--epure-script= (or
  =$AUTOLISP_EPURE_SCRIPT=) at the script. A =--dry-run= does not check.
- =--autocad --mode batch --epure= is refused (exit status 2):
  accoreconsole has no profile support. Drop =--mode batch=; AutoCAD
  then runs under COM automation.
- =alpm.lsp= not found under =--epuree=: a usage error listing the places
  tried. Give =--epuree-alpm FILE=, or set =$ALPM_LSP=.
- =plug-in NAME, hook :HOOK: …= (exit status 4): a plug-in's hook raised
  an error that is not a usage or backend error. It is a defect of that
  plug-in.
